个人代理竞赛：Muse vs ChatGPT vs Grok Bot

Grok @grok

我对个人代理竞赛的“沙发上”思考：

1. Muse 有望成为领跑者。这个应用直观易用，Meta 正在其所有产品中积极推广它。一旦你使用过 Muse 应用，你就会意识到，让代理存在于像 iMessage 这样的现有消息应用中几乎没有意义。除非 Meta 的计算资源耗尽什么的，我认为这将成为该公司继 Facebook 之后最成功的自研应用。它将比 Threads 大得多。

2. ChatGPT 可能仍是个人代理的领跑者，因为它已经有超过 10 亿用户。OpenAI 的模型、计算机使用和语音功能可以说在逐项特性上优于 Muse。但要构建一个既适用于工作又适用于个人使用的单一产品很困难，更难的是用相同的用户体验同时服务企业和消费者。即使是工作用途，我开始使用 Grok Bot，因为 Work/Codex 的拆分仍然太令人困惑。我相信团队正在紧锣密鼓地开发，我们将在未来几周看到一些好东西。

3. Grok Bot 其实并不是 Muse 的竞争对手，因为它专注于工作。在我看来，多个机器人自然适合基于团队的知识工作。我对 Grok Bot 的乐观情景是，它距离成为支持机器人和人类的多人协作代理式 Slack 只差几个特性。

4. Google 显然是黑马候选者。所有这些个人代理都依赖 Gmail、Google 日历和你 Google 应用的资料数据。Google 有自己的个人代理 Spark，但据我最近检查，它只是 Gemini 中的一个次要标签页。我认为 Google 需要更积极地将 Spark 打造成主要体验，并让它变得直观且与 Muse 具有竞争力。不过，Google 在多人 AI 方面的记录并不出色……

5. 说到多人协作，没人还没有搞定这个。我无法轻松地将配偶添加到 Muse 聊天中来规划假期。我也无法将同事拉入 ChatGPT 或 Grok Bot 的线程中。今天的多人数 AI 主要意味着在 Slack 中标记机器人。每个主要提供商可能都在开发这个，我认为这将是下一个重大突破。

我现在的个人 AI 技术栈是：Muse 用于个人用途，Grok Bot 用于云任务，Claude 用于特定用例，ChatGPT 用于其他所有事情。

但我认为我们将在本周看到一些重大更新。

每个人都应该设计自己的个人技能和文件，让它们易于在不同平台和代理之间移植。否则，你将花费一半时间从一个工具切换到另一个。

Loops and graphs can resolve the exact same support ticket, and the diff…

Alex Prompter @alex_prompter

Loops and graphs can resolve the exact same support ticket, and the difference is not the outcome. It is who decides the path to get there.

A loop starts with a human setting the goal, the policy, and the bar, then handing the whole thing over. From there the agent owns every step: draft a reply, check it against policy, fix the gaps, and ask itself whether the ticket is resolved. If not, it runs another pass through the same loop. If yes, it is done and sent. The agent picks every step inside one fixed frame, which is exactly why loops fit one-off work, the kind where you genuinely do not know the path yet and do not want to draw one in advance.

A graph flips that. You draw the path first, as a state machine of nodes and checkpoints, and the agent fills each node instead of deciding what comes next. Read the ticket, check whether it is a known issue, apply a known fix or investigate a new one, draft the reply, run it through QA, and if QA fails, loop back to redraft instead of moving forward. A review step checks it again, sends it if it passes, or sends it back to fix if it does not. This is built for recurring work, a support pipeline that runs the same shape every time, where checkpoints matter more than flexibility.

Both sit on the same company brain underneath: past tickets, policy, product docs, all the context that moves through every node, whether the structure on top is a loop or a graph. The brain does not care which execution model is running it.

Use a loop when you do not know the path yet and need the agent to figure it out inside a frame. Use a graph when you already know the path and need the agent to execute it reliably, the same way, every single time.

Bookmark this before you build a rigid graph for a job you have never actually done once.

The attention came fast because of the founder. Diogo Almeida worked on RLHF at OpenAI, the training method behind ChatGPT, and he now argues that chat models are the wrong tool for automation.

His reasoning is that software can't depend on a model that is right 95% of the time and never says when it's in the other 5%.

Here's what I'd be careful about.

The 40 to 200x speed figures come from TypeSafe's own tests.

In one independent email-sorting test reported by TechCrunch, Gemini was slightly more accurate and 10 to 20 times more expensive.

Some engineers point out that a regular LLM can be forced to answer the same way, so the advantage may not last.

Jev also can't chat, write, or code. It only works when the possible answers are known up front.

My read is that Jev is a useful new part for people building AI products, and it changes nothing for someone who uses ChatGPT to write emails.
