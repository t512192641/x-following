1、安克和飞书的产品经理，可能对录音这个事情有什么误解，他们觉得一天录半个小时就可以了。如果你是想收集全天上下文，就算开了他们那个会员，额度都不一定够你用

安装：没有一行装完的命令，得从源码编——Linux、GCC 13+、Python 3.12、CUDA 13（昇腾用 CANN 9.2）；先 export DEEPINFER_ACCELERATOR=nvidia 或 ascend，再 ./build.sh，然后 python examples/offline_inference.py。默认自动拉 DeepSeek-V4.1-Flash-1017，用本地权重设 DEEPINFER_HF_MODEL_DIR。

能力：并行支持 Attention DP / balanced CP，MoE 走 EP + EPLB；推测解码是 DSpark 加置信度调度验证（DEEPINFER_ENABLE_MTP_VARLEN=1 打开，草稿长度由 DEEPINFER_USE_NEXTN_DECODE 控，默认 5）；SWA bounded replay 只重放有界后缀（默认 compact + KEEP_TOKENS=140）；异步调度默认开。做评测重点看：DEEPINFER_BATCH_INVARIANT=1 让不同 batch 组合结果一致，再叠 ENABLE_MTP_VARLEN=0 和固定 seq_seed 就是确定性采样。结构化输出支持 regex、JSON schema、EBNF（从 so_args 传）；硬件覆盖 NVIDIA SM100 和华为昇腾 950。

trim-1：Caveman 作者做的 1.2 MB 上下文剪枝小模型——给上下文加一句问题，只删 agent 用不上的行、不改写原文（删处留短标记）；712 棵梯度提升树，单核毫秒级、纯 Go 无 GPU 无网络；长文档检索用 balanced，编码 agent 工具输出省不了多少；不满足条件就原样返回

yibie @yibie

trim-1 是个 1.2 MB 的小模型，由大名鼎鼎 Cavman 的作者开发，它专门干一件事：给一段上下文加一句问题，它决定哪些行 agent 用得上，把用不上的删掉。

它跟"用模型总结上下文"反着走。摘要会把原文改成一段转述，标识符、路径、报错文本都可能变形；trim-1 只删行，返回的还是原文自己的行、原来的顺序，删掉的地方留一个短标记，一个字都不改写。

代价也小。712 棵梯度提升树，不是神经网络；单核毫秒级，不用 GPU、不发网络请求；纯 Go 标准库，模型嵌在里面。

用得对的地方和用不对的地方，README 自己说清楚了。长文档检索是它的主场，用 balanced。编码 agent 的工具输出又短又密，作者让你别期待太多——这种场景省不了多少。

它还有一条很值得学的设计：失败时不动。查询为空、上下文不到 2,000 字节、超过 8 MiB 或 20 万行、已经带标记、或者算下来删不掉 10% 的字节，它一律原样返回，并在 stderr 说明原因。

我的判断：上下文剪枝的单位应该是行，不是摘要。摘要等于二次改写，把"原文"这件事丢掉；而一行是被读完还是被删掉，是可以逐行判定的。另外，知道什么时候不该动，比总能剪更值钱。

用法一行：trim --query "why does the build fail" build.log > build.trimmed.log，--point 三档保守 / 平衡 / 激进，模型卡在 Hugging Face。

发现不少小伙伴很好奇我是怎么用 Mac 来开发Windows软件的，以及Windows软件现在一般用什么技术栈来实现，刚好有空，来和大伙随便聊聊关于多客户端下技术选择的思考以及我的一些想法。

以下是第一篇，给大伙介绍介绍各种桌面、移动端开发技术的选择以及对应选择的思考。

做过前端客户端的小伙伴应该都知道，这些年端的开发一般是这三条路。

第一种最简单方便的是，直接写 Web 代码，塞到浏览器就能跑，包括早年的 PhoneGap、Cordova 就是把网页塞进一个原生壳里，然后提供一些bridge的能力让js可以调用到一些原生的能力，比如唤起手机摄像头这类的 Web 不好做的事情。

第二种是跨端开发，也就是好多年前大家经常听到的一码多端，当时移动端有 React Native、Weex 这一类技术，当时主要是为了解决 Web 性能差的问题，一份代码同时打包出 iOS 和 Android，这里国内大厂使用跨端技术还有一个非常大的原因就是动态化和热更新，讲的土一点就是可以绕过商店审核直接下发新页面，这也是国内跨端在当时移动互联网高速发展时特别流行的重要原因。

桌面端大家熟悉的就是 Electron，大家熟知的现在不少AI桌面端、VS Code、Slack 是用这个做的，代价是相当于每个应用都自带一份 Chromium 和 Node.js，安装包一百多 MB，内存也占得多。但好处是在 Chromium 渲染引擎的统一下能够很好的保持多端的展示一致性，加上里面写的代码非常好写，后续不少桌面的速成就会用这个技术。

跨端后面也慢慢延伸出更多有趣的解决方案，类似Flutter 自己实现一套渲染引擎，早期靠 Skia，现在换成了自研的 Impeller 渲染引擎来保障多端一致和性能效率的均衡，包括桌面端上老牌的 Qt，和 Flutter 一样自己画界面。

这两年桌面跨端也出现了用 Rust 写的 Tauri、Go 写的 Wails，他们和 Electron 不一样的地方就是，他没有塞一个Chromium进去，而是使用的系统自带的 WebView，包会小非常多，但是整体还是基于 Web 这一套研发思路和对应实现语言去进行桥接交互，但是由于系统 Webview 每个平台不一样，Windows 上是 WebView2，Mac 上是 WKWebView，Linux 上是 WebKitGTK，所以多端显示的一致性反而不如 Electron，还是要写兼容代码。所以这种情况下，即使 Electron 很大内存占用也不低，还是会被选择更多。

第三种是原生开发，也是没有 AI之前，大家觉得开发难度很大的一种方式，特别是之前的苹果系使用的 Objective-C，Android 系使用的 Java、Windows 系 C、C#，均是我认为需要科班花非常多时间去学习、看书、手编代码，要想做得好，需要花大量时间研究对应的系统底层原理，能够方便你写出相比普通研发性能更好更稳定的代码，在我看来是前期投入大，后期用户很享受的技术，我当时17年时候刚工作 2 年多的时候，职业发展比较爽的一个很大原因是我抽了半年时间学习 Objective-C 和 iOS 研发，让我自己本质前端的工作提前往跨端方向走了，刚好可以解决一些这两个工种结合的不能解决的难题，也是我当时做一线开发非常快乐有趣的时间。

等到后面 Swift + SwiftUI、Kotlin + Jetpack Compose、C# + WinUI 3 慢慢出来成熟后，这些原生端语言的写法也慢慢像高级语言靠齐，也更易写了，声明式代码更短、更好读了。但是在国内完全被 React Native、Flutter、Electron 的广泛使用被盖过去了，导致开发者不多，生态发展完全靠官方推动，从而出现了出活很快，但是大家普通感觉怎么用久了卡卡的缘故的一个很大的原因，同时还占大头，而且想迁移到原生假如之前架构实现不好大概率只能重写，完全不能复用，实现得好比如说你把业务逻辑早就抽出，类似 Kotlin Multiplatform 这类方案把业务逻辑共享、界面各写各的原生，算是第四条路，也是最近几年的趋势。

聊到这里大家应该大概明白了，这里也有一个不可能三角，就是研发效率、体验、性能这三者，选择 Web 是多效率少性能，选原生是多性能体验少效率，选跨端就是刚好是这三者取一个中间，做得好容易都占，做得不好，容易没有一边占到好处的尴尬局面。

那么在 AI Coding 写代码已经不是问题的情况下，我们应该选择啥技术呢？很多时候也取决于你的场景，比如你就是一个 Web 场景的浏览、点点按钮、阅读这一类 Web1.0 阶段的东西，那还是非常建议直接 Web 技术来弄；假如你需要调用到系统底层的能力，或者需要操作更顺手更好分发，以及本身就是一个应用的场景，我还是非常建议使用原生技术来实现，这样可以第一时间享受到系统官方本身的众多调优，以及最原生的交互效果、最低的内存占用，加上 AI 让写两份原生代码的成本大幅下降，三角形的效率那一边被补上了，只是两个平台的调试和验证变成了新的成本，这里正是人需要重点做的事情了。

当然假如实在技术选型不那么重要，工作量非常之大，以及业务效果远大于技术体验选择，选择跨端技术也是可以的，这样快，迭代发布也快，可以第一时间让你的用户收到你的最新的特性更新。

不过说到底，技术是给业务服务的，最终还是需要往解决问题方向走，好比抢演唱会门票，大家不会关注你这个客户端怎么这么卡，只会关注我用你能不能抢到票，即使你做得十分顺畅，但是抢不到票也是会被骂得很惨，技术栈的选择在这里就选的好变成了锦上添花的工作，最终还是需要优先保障用户的最真实需求的解决，然后做好这里，再去想，我如何让用户体验更好，接下来才是考虑我是否需要使用原生技术来实现。

感谢分享，我说一下我在上一个版本 baocut 用 GPUI 踩的坑。

GPUI 挺好的，性能好，跨平台，AI 友好，但也有坑： 1. UI 复杂一点的话大概率你要 fork 一份改一下，有些功能原生支持不了，但也不是大问题

2. Accessibility 支持不太好，要支持一些键盘操作会比较麻烦（也可能我用法不对）

3. Rust 编译资源消耗很大 每次编译，无论是 CPU 占用还是磁盘占用，都巨大，对于我这样用 Mac Mini M4 16G + 1T 硬盘的来说简直太痛苦了，不敢并行多开编译任务，磁盘空间永远不够用（后来我把编译结果默认放到移动硬盘缓解了一点）

4. 编译时间很长，不支持热更新。 这点很要命，这意味着你如果改一点 UI 代码，要重新编译，然后要等少则几分钟多则十几分钟，这时间无论对于 agent 还是对于人来说都是很大的时间成本，加上不能随便多任务，会拖慢你的开发速度

5. agent 验证 UI 不算太友好 codex、claude code 都可以借助 computer use 去验证 GPUI 的结果，但一个是慢，另一个相对成本也不低。

---

后来我之所以换回 Electron，就是因为 Electron App 对于 Agent 相对友好，编译快、热更新，UI 改动很快看到效果，然后 Electron App 还能跑到 agent 内置的浏览器中，agent 验证起来很快，都不需要用 computer use 去打开 electron app。

至于网页渲染性能不够好的问题，我把原来一些需要复杂渲染的部分，都用 rust 编译成了 wasm，这样在浏览器运行也可以保证高性能。

以前 rust 做的转录、tts 模块也都以 worker 进程的形式保留下来了，electron 需要用到的时候可以直接起 rust 编译出来的进程（Codex 也是类似），和这些进程通信，后台的性能也比纯 TypeScript + Node 要好不少。
