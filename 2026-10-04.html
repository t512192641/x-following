《OptChat：一个 AI 记住一切的永不结束的聊天》

OptChat: an endless chat where the AI remembers everything

出处：Victor Taelin（HOC 创始人，HVM / Bend 作者）的 gist，2026-10-04｜括号内为原文小节编号

先说结论

这篇是一份完整技术规范，讲怎么让 agent 的上下文无限长、却永不腐烂。它的核心是一个翻转：记忆不该是 agent 去调用的工具，聊天本身即记忆——一条永不结束的对话，逐字只追加地存着，后台用便宜模型把它压成一棵由单行摘要构成的二叉树；每个回合都从零开始，只带一个恒定大小的"视图"，需要细节时用 zoom 往下钻。

要解决的问题有两个。一是遗忘：会话填满、被压缩或丢掉，下一个从零开始，于是你的人生散落在几百个会话里，agent 找不到其中任何东西。二是上下文腐烂：上下文越长模型越差，而压缩（"总结一下继续"）会把细节永久丢掉。

架构（1）

六个组件：日志（每条消息逐字、只追加）、树（摘要）、压缩器（后台用便宜模型建树）、视图（覆盖整个聊天的一组节点，保持在字节预算内）、回合循环（每条用户消息开一次全新调用）、缓存（请求布局与断点）。

节点 (l, i) 覆盖消息 [i·2^l, (i+1)·2^l)：第 0 层总结一条消息，第 l 层合并两个孩子 (l-1, 2i) 与 (l-1, 2i+1)。

参考实现的常量：

NODE 512 字节 一行摘要的目标大小 VIEW 128,000 字节 视图预算（≈ 62-64k tokens） JOBS 8 同时运行的压缩调用数 TRIES 5 每个节点尝试压进 NODE 的次数 RETRY 10 秒 失败节点重试前等待 CAP 30,000 字符 单条工具结果上限（保留头尾） MARKS 50,000 / 80,000 / 100,000 字符 视图内的缓存断点

所有尺寸都是 UTF-8 字节，从不用 token：分词器随模型变，字节数不变。

存储（2）

两条只追加流，一个目录：main/YYYY-MM-DD.jsonl 每行一条消息 {i, kind, text, size, date}；tree/YYYY-MM-DD.jsonl 每行一个节点 {l, i, text, size}。i 是永久 id；kind 是 user / talk / tool / echo / note 之一。

三条硬规则：每行一次 write 后 fsync 再返回，崩溃不丢；加载时跳过非法 JSON 行（写入中途崩溃留下的撕裂行）；同一份聊天只允许一个写者——参考实现用 Unix socket 做锁，拒绝连接的 socket 就是陈旧锁，删掉并接管。

树在原则上只是缓存（可从日志重建），但重建要花模型调用，所以存下来、从不重算。

还有一条反直觉的规范：模型的思考内容展示给用户，但从不写入日志。理由是压缩器必须去总结它们，而 Claude Sonnet 的推理提取保护机制在 630 次首次尝试里拒绝了 112 次；不含思考内容时，523 次里 0 次。

树（3）

node(0, i) 就是消息 i 本身（≤ NODE 字节）；node(l, i) 由两个孩子合并而来。它纯粹是二叉的——前身 OptMem 会从原始笔记直接构建最多 16 条的小块，作者自己说这没有真正的理由，还让结构混乱，于是去掉了。

如果源本身已经放得进 NODE 字节，它就是这个节点，不需要模型调用。

为什么是 512 字节：一开始是 128，模型写不出那么短的有用行；OptMem 用 280；512 字节是一段稠密段落，够放若干带名字和数字的条目。真实行平均约

我记得半年前我说自己不怎么 Review PR 了，评论区很多人不认同，觉得这样不靠谱。现在再看，不 Review PR 的人越来越多。比如我刚看的这期播客，在 SpaceXAI 做 Grok Bot 的 Lauren Tan，一个月合并 2500 个 PR，也是不逐个 Review 的：晚上让 AI 自己检查、自己合并，第二天早上她再抽查。

不 Review 不等于不管质量，她靠另外两个办法来保证： 一是让 AI 能像真人用户一样把程序用一遍，自己发现问题； 二是给代码定下很多规矩，让 AI 很难写出烂代码。

她把自己这套做法写成了一组 Skill，公开了出来，叫 pstack。

顺便说一下，这期播客的主持人 Matt Pocock 原本是知名的编程课讲师，他公开的技能库在代码托管网站 GitHub 上有二十多万个星标，是最受欢迎的技能库之一，所以这期算是两位同行对谈。Lauren 之前在 Meta 做网页开发框架 React，今年 3 月加入 AI 编程工具公司 Cursor；Cursor 今年 8 月被 SpaceX 收购，并入旗下的 AI 部门 SpaceXAI。

根据播客的内容，我把 Lauren 的这套做法简单总结一下，我自己的点评在结尾处。

一、先让 AI 能检查自己干的活

Lauren 说，就算不用她的 pstack，每个人最该有的一项技能也是“验证”：给 AI “手和眼睛”，让它能把自己写的程序跑起来，像普通用户一样点一遍，看看结果对不对。

这是她吃过亏之后得出的结论。今年 4 月她在 Cursor 解决一个窗口卡顿的问题，一开始全靠手工：她自己去看各种性能数据，再把看到的转述给 AI，AI 改完她再去看。她形容自己成了 AI 和检测工具之间的“人肉中转站”。她在 Cursor 写的第一个技能就是验证。在这之前，AI 看不到自己改动的效果，只能等她来回传话；有了验证，AI 可以自己改、自己看结果、不满意再改，一轮一轮往下做，不需要她守着。现在她所在的团队里每个产品都配有这样的验证技能，全团队都在用。

做这个技能时她还总结出一条原则：工作里有的部分需要动脑判断，有的部分只是照章办事，照章办事的部分应该写成固定的程序，只把需要判断的留给 AI。起因是她发现，每个 AI 在检查前都要自己从头写一遍检查用的小程序，各写各的，有的能用有的不能用，用完就扔，又慢又浪费。她把这部分做成一个现成的工具，所有 AI 直接调用。

二、AI 反复犯的错，去改规矩，不去改 AI

Lauren 不喜欢“软件工厂”这个流行说法，她更愿意把自己的工作比作经营一家米其林餐厅的后厨。主厨不用亲手做每道菜，但要安排好整个厨房：食材什么时候进、怎么存，每个人用什么工具，菜按什么流程出。工程师现在也一样，不再亲手写代码，却仍然要对结果负责。她认为工程师现在最重要的工作就是把这个“厨房”布置好。没花时间布置的人，信不过 AI 的产出，只能盯着它一步步干，忙到没空改进工具，就像一直拿钝刀切菜。

她举了自己的例子。Grok Bot 最早几版的代码挤在八个巨大的文件里，每个至少一万行，AI 加新功能时就接着往里塞，越塞越乱。她后来定了规矩：每个功能必须放在自己单独的文件夹里，做一件事只允许一种写法，不合规矩的代码会被自动检查拦下来。这样 AI 加功能时不用多想，按规矩放就行。她的习惯是一直观察 AI 在哪里出错，每看到一次就问自己：能不能加一条规矩，让这种错以后根本写不出来。

What regex teaches us about the tiny-model sweet spot

前几天我们深挖了 gpu-lexer（41K 参数做语法高亮）。一个自然的念头是：能不能把这个范式搬到正则上——做个"生成正则的微型引擎"？调研一圈之后，结论比预想的更有意思：两条路都有人走过，而它们恰好帮我们划清了"微型模型甜蜜区"的边界。

先看调研结果

方向一：从样例生成正则。这不是空白。学术界有一条连续的研究线：Regex+（2022，只正例合成，MDL 排序）、SplitRegex（神经网络分割正例再分治）、PRAX（2023，用博弈论方法自举训练数据）——直到今年最新的 ReSyn + Set2Regex：一个 10M 参数的合成器加递归分解框架，在真实世界正则基准上拿下 SOTA。也就是说，"用窄任务模型做正则合成"这件事，学术上已经做到了 10M 参数的量级，而且还在快速推进。LLM 时代更挤：让 Claude 直接生成正则已经好用。

方向二：正则预筛（先粗后精）。工业界十年前就解决了，而且不是用 ML。Intel 的 Hyperscan 用图分解把正则拆成"必含字面串 + 有限自动机"，配合 SIMD，把 Snort 的匹配提速 8.7 倍；它还支持 prefiltering 模式（粗匹配 → 完整正则确认）。关键：它的预筛是确定性的——从正则自动提取的字面串，假阴性为零。安全场景里"漏报"是致命的，所以确定性方案天然碾压"模型猜"。

我们的修正

这两条路各打掉一个假设：

第一，"窄任务"不等于"输出类别有限"。语法高亮的甜蜜区是 9 类标签；正则生成的输出是无限组合空间——所以 41K 参数的 gpu-lexer 能做前者，而正则合成的研究线一直在往 10M 参数爬。微型模型的边界不是"任务窄"，是"输出可枚举 + 错误可容忍"。

第二，"预筛"这个位置已经被确定性方案占了。ML 预筛唯一的优势是"语义相关性"（不是字面子串匹配，而是"这段文本大概率和哪类规则相关"）——但这要求一个"大量正则 × 大文本、且规则之间语义可分"的场景，目前想不到一个比日志分析/安全扫描更强的用例，而那些场景已经有 Hyperscan。

真正剩下的机会

如果真要做，参照物很清楚：Set2Regex 路线——把 10M 参数的合成器量化到几 MB，像 gpu-lexer 一样搬进浏览器/本地（"给几个例子，本地生成验证正则"的表单插件）。学术 SOTA 在，实用化空白在，成功标准也可测（真实 benchmark 上的准确率 vs 体积）。

但调研本身给我们的价值更大：它验证了 gpu-lexer 那篇文章里最该记住的一句话——微型模型不是"小号 GPT"，是"替代规则引擎的新工具"。规则引擎写得完的地方（语法高亮），微型模型能赢；规则引擎写不完但已被确定性算法占住的地方（正则预筛），微型模型没有窗口。甜蜜区比想象中窄，也比想象中清楚。

简单对比下：

ESP32 是乐鑫家的“联网全能选手”，WiFi + 蓝牙片上全集成，几块钱一片，跑物联网项目是真香。代价是功耗偏高，WiFi 收发时电流能冲到一两百毫安；深度睡眠倒是还行（10µA 左右），只要别一直联网，续航其实能救。

STM32 是 ST 家的工业级老将，ARM Cortex-M 内核，从 M0 到 M7 产品线随便挑。强项就是低功耗——尤其 L 系列，停机模式能压到 1µA 以内——外加外设丰富、可靠性久经考验。短板是没带无线，要联网得自己外挂模块。

所以结论很朴素：要联网、图省事、预算紧，选 ESP32；抠功耗、求稳定、跑工业场景，上 STM32。

推友说功耗 STM32 更好没毛病，但 ESP32 的存在意义本来就是“自带联网的便宜方案”，看项目要什么再选就好。
