《为真正的工程师准备的 skills》

清单：Matt Pocock 开源了他整套 .agents 技能

出处：https://t.co/oZvMmkKFHu（MIT，2026-10-04 核对 276,162 stars）· X 上 v1.3.1 发行公告

Matt Pocock（Total TypeScript / AI Hero）把他日常用的 agent 技能整套开源了，仓库自述就一句话：每天真在写工程的人用的 skills，直接来自他的 .agents 目录。

他对"流程框架"的判断很直接：GSD、BMAD、Spec-Kit 这类做法想帮忙的方式是拥有流程；但这样做的时候，它也拿走了你的控制权，并且让流程本身的 bug 变得很难排查。所以他这套反过来：小、容易改、可组合、任何模型都能用，基于几十年的工程经验。仓库里写的是"拿它们乱改，变成你自己的"。

一个设计轴：用户触发 vs 模型触发

这套 skills 只按一个轴分：谁能调用它。

用户触发的 skill 只在你敲它的时候可达（例如 /grill-me），它的职责是编排。模型触发的 skill 你可以调用、agent 也可以在任务合适时自动取用，它承载可复用的纪律。

一条硬规则：用户触发的 skill 可以调用模型触发的 skill，但永远不调用另一个用户触发的 skill。

它想修的四个失败模式

模式一：agent 没做我想要的。最常见的问题是没对齐——你以为对方懂了，看到结果才发现完全没懂。他的解法是一次"拷问会"（grilling session），让 agent 反问你细节：/grill-me（非代码场景）、/grill-with-docs（同上但顺带产出领域模型）。这是他的招牌技能，用在"每次你想改动点什么"的时候。

模式二：agent 太啰嗦。项目开始时，开发者和领域专家通常说着两套语言；agent 被丢进项目里自己现场猜术语，于是本来一个词能说清的事它用二十个词。解法是共享语言：一份帮助 agent 解码项目术语的文档。效果很直白，仓库里给了对照：

改前："课程里某一节被做成 real（在文件系统里得到了位置）的时候有个问题" 改后："物化级联（materialization cascade）有个问题"

模式三：代码跑不起来。这时候要看的是反馈回路——没有代码实际怎么运行的反馈，agent 就是在盲飞。需要的还是那老三样：静态类型、浏览器访问、自动化测试。其中红-绿-重构的循环是关键（agent 先写一个失败的测试，再修测试），所以他做了 /tdd；调试则包成 /diagnosing-bugs，按阶段逐个门禁。

模式四：我们造出一坨泥。agent 能大幅加速编码，也就会加速软件熵——代码库以前所未有的速度变复杂。解法是"关心设计"，它织进了每一层技能里：/to-spec 在写规格之前先问你这次要碰哪些模块；/improve-codebase-architecture 扫描代码库找出可以"加深"的地方，把候选交给你，建议每隔几天在你的代码库上跑一次——但请注意它的定位：这是一次普查，不是救援，在一个真的很老的代码库上它会找到真实的候选，但它不会替你解开那团泥。

Fox @indie_maker_fox

Cloudflare 上线了全新 CLI：cf。

光名字就赢了，比 wrangler 更短、更好记、更好敲。

🙋‍♂️ 为什么要再造一个 CLI？

Cloudflare 统计显示：上周 wrangler 的调用里，有 48% 来自 agent。太合理了。现在很多事我也几乎不亲手跑命令了：建 D1 / R2 / KV / Workflow，配域名、部署站点、拉日志、排查问题，都是 agent 直接通过 CLI 代劳。

那为什么要重做？我猜核心原因之一是：wrangler 的设计对象主要是“人”，而 cf 开始明显面向“agent”。比如它默认输出 JSON，更利于机器消费结果，减少上下文浪费，也更适合自动化链路。

cf 目前已覆盖 3000+ API 操作，支持用自然语言搜索命令；引入 TypeScript 配置（cloudflare.config.ts），还提供 cf migrate，一键从 wrangler 迁移。

我的结论：开发工具正在把 agent 当作第一用户。命令是否易发现、输出是否易处理、配置是否可类型检查，越来越关键。

👨‍💻 TanStarter 模板怎么办？

TanStarter 是 all in Cloudflare：数据库、存储、缓存、域名、部署全走 Cloudflare 基建。之前我还做了 TanStarter-CLI，实现“5 分钟部署上线一个网站”。之所以能这么快，wrangler 的接口能力功不可没。

现在 cf 接口更多、输出更友好、对 agent 更友好。我大概率会在不久后把 TanStarter 从 wrangler 全面迁到 cf，敬请期待。

LCU（amontlabs/lcu）：把 Codex 的 Computer Use 拆出来给 Claude Code / Codex CLI / Pi 用

宝玉 @dotey

学习研究了下 amontlabs/lcu 这个项目，它把 Codex 的 Computer Use（让 AI 看屏幕、点鼠标、敲键盘来操作电脑的能力）单独拆了出来，让 Claude Code、Codex CLI、Pi 等其他 AI Agent 工具也能调用。

我本来还以为它是模仿 Codex 实现了一套，原来是直接用的 Codex 的 Computer Use，在本机找到已安装的 ChatGPT 桌面版，启动其中 OpenAI 自带的 Computer Use 运行时，再通过 MCP 接到你用的 Agent 工具里。仓库文档写明，指令、执行和权限策略都以 OpenAI 原版运行时为准。

因此电脑上必须装有官方 ChatGPT 桌面版，但不需要登录 ChatGPT 或 Codex 账号。

它给模型的工具很少。常见的电脑操控方案会把截图、点击、输入、滚动各做成一个工具，LCU 只给两个：js 和 js_reset。

js 用来执行一段 JavaScript 代码，运行环境里预置了一个名为 cua 的对象。模型通过写代码来操作电脑：先调用 cua.getState() 拿到当前桌面状态和使用说明，再用 getApp 选定某个窗口，然后调用 click、typeText、pressKey、getScreenshot 等方法。点击、输入、读取结果可以写在同一段代码里，一次调用完成。

这个 JavaScript 环境会保留状态，上一次调用里定义的变量，下一次还能接着用；环境出问题时调用 js_reset 清空重来。除了截图，模型还能读取窗口的无障碍信息（操作系统提供给读屏软件的界面元素列表），按元素点击，不必完全依赖屏幕坐标。

js 加 cua 对象这套接口是 OpenAI 原版的设计，LCU 原样转发。仓库记录显示，在 macOS 上对比测试时，模型收到的初始化说明和首次调用返回的使用指南，与官方 Codex 收到的内容逐字节一致。

目前正式适配的 Agent 工具是 Pi、Codex CLI 和 Claude Code，Oh My Pi 和 Hermes 为实验性支持。系统支持 Apple Silicon 芯片的 macOS（需授予辅助功能和屏幕录制权限），以及使用 X11 桌面的 Linux（ARM64 和 x86-64）。Windows 11 尚在候选阶段，Intel Mac 和 Wayland 桌面不支持。

控制 Chrome 浏览器需要额外开启，走的是 OpenAI 官方 Chrome 扩展，每个网站仍需单独批准。安装需要 Python 3.12 以上，README 给出的做法是把一段提示词贴给自己的 Agent，让它按安装文档完成配置，也可以从 GitHub 手动下载安装包。

项目地址：https://github.com/amontlabs/lcu

根据播客的内容，我把 Lauren 的这套做法简单总结一下，我自己的点评在结尾处。

一、先让 AI 能检查自己干的活

Lauren 说，就算不用她的 pstack，每个人最该有的一项技能也是“验证”：给 AI “手和眼睛”，让它能把自己写的程序跑起来，像普通用户一样点一遍，看看结果对不对。

这是她吃过亏之后得出的结论。今年 4 月她在 Cursor 解决一个窗口卡顿的问题，一开始全靠手工：她自己去看各种性能数据，再把看到的转述给 AI，AI 改完她再去看。她形容自己成了 AI 和检测工具之间的“人肉中转站”。她在 Cursor 写的第一个技能就是验证。在这之前，AI 看不到自己改动的效果，只能等她来回传话；有了验证，AI 可以自己改、自己看结果、不满意再改，一轮一轮往下做，不需要她守着。现在她所在的团队里每个产品都配有这样的验证技能，全团队都在用。

做这个技能时她还总结出一条原则：工作里有的部分需要动脑判断，有的部分只是照章办事，照章办事的部分应该写成固定的程序，只把需要判断的留给 AI。起因是她发现，每个 AI 在检查前都要自己从头写一遍检查用的小程序，各写各的，有的能用有的不能用，用完就扔，又慢又浪费。她把这部分做成一个现成的工具，所有 AI 直接调用。

Lauren 不喜欢“软件工厂”这个流行说法，她更愿意把自己的工作比作经营一家米其林餐厅的后厨。主厨不用亲手做每道菜，但要安排好整个厨房：食材什么时候进、怎么存，每个人用什么工具，菜按什么流程出。工程师现在也一样，不再亲手写代码，却仍然要对结果负责。她认为工程师现在最重要的工作就是把这个“厨房”布置好。没花时间布置的人，信不过 AI 的产出，只能盯着它一步步干，忙到没空改进工具，就像一直拿钝刀切菜。

她举了自己的例子。Grok Bot 最早几版的代码挤在八个巨大的文件里，每个至少一万行，AI 加新功能时就接着往里塞，越塞越乱。她后来定了规矩：每个功能必须放在自己单独的文件夹里，做一件事只允许一种写法，不合规矩的代码会被自动检查拦下来。这样 AI 加功能时不用多想，按规矩放就行。她的习惯是一直观察 AI 在哪里出错，每看到一次就问自己：能不能加一条规矩，让这种错以后根本写不出来。

1. DeepSWE：评测的是处理已有项目的能力，给 AI 一个真实代码仓库和需求，让它自己读代码、找修改位置、实现功能、运行测试。

在需要持续试错、验证和调整路线的复杂任务上，Gemini 在这组评测里的表现明显落后。

3. Vibe Code Bench：评测的是从零做出完整应用的能力。给 AI 一段自然语言需求，比如做一个能注册、发帖、关注、点赞的网站，让它把前端、后端和数据库接起来，再通过浏览器实际操作，检查用户流程能不能走通。

它在从零搭建应用上表现很好，但另外两家也已经很接近。

4. Terminal-Bench：评测的是通过终端完成复杂实际任务的能力。AI 需要自己执行命令、操作文件、处理环境和依赖、编译程序、排查错误，最后交付符合要求的结果，整个过程都要靠它自己推进。

理论上来说，你手动稍微改写或换个开源模型润色修改下，标记就会变弱。
