Allow me to explain

One of the most useful things agents do is “wake up” and check on things for you, then take action depending on what it finds

This is what makes them proactive and feel like they’re working for you, not just a tool you use

We used to call them cron jobs, but someone smart rebranded them to routines - much better

The frequency that your agent wakes up and runs a routine is called the “heartbeat” and every time it wakes up, it has to read a bunch of context and possibly call tools - this uses a lot of tokens

In all the instances when it wakes up and doesn’t find anything that needs action, it wastes all those tokens

Ask your agents to estimate how many tokens are used on each run of your routines - it’s probably 15-40k and if you run a lot of routines frequently it really adds up

So when I see people complaining about hitting usage limits, a big reason is likely in the routines and tokens consumed as part of the wake up process

The difference is more like 1-5k tokens of a super cheap model vs 15-40k tokens of an expensive model

Added up over the course of a month and it can make a big difference

能解决问题这里不多说，更多取决于产品本身，它是去解决一个具体的需求，有人需要，有场景需要，刚好你这个产品可以提供一个解决方案让人或者 Agent 使用完成目标就好了，只不过解决问题有大有小。

yibie @yibie

Agent 正在从同步变异步。过去一个 agent 跑在单条 ReAct loop 里：模型调一个工具，死等结果，再决定下一步。工具或子任务一跑就是几分钟，整条 loop 被堵死，你发的新消息只能在后面排队。

LangChain 这篇文章讲的变化，是把 agent 拆成前后台两层。一个编排者留在前台跟你对话，长任务丢给后台子 agent 跑。Claude Code 默认在后台跑子 agent，OpenAI 和 DeepSeek Harness 也是类似的路由加后台 worker 结构。

关键区别在调用方式。老式子 agent 像一行 await，不返回就卡住。async 子 agent 像 asyncio.create_task，或者一个没 await 的 Promise：调用立刻返回，活在独立线程跑，结果稍后回来。于是 agent 能同时接的工作量，跟着后台 worker 的数量涨，而不是被一条 loop 的长度限死。

编排者靠五个工具管住这些后台任务：start_async_task 启动，check_async_task 查状态和结果，update_async_task 发新指令，cancel_async_task 停掉，list_async_tasks 列出全部。

运行中改任务有两种策略。默认 interrupt 是打断当前运行、带着新指令重启，适合“改用 Postgres”这种纠正。enqueue 是把新指令攒着、等这轮跑完再执行，适合“跑完顺手把测试跑了”这种追加。

结果怎么回来也分情况。编排者正忙，它会在每次调模型前扫一遍未完成任务，中途把结果捡走。它闲着，子 agent 会唤醒一轮新运行。它正卡在等你审批，审批不动，等你答完结果才到。需要审批的子任务在自己线程里等，不打断前台；在 Slack 的 Managed Deep Agents 里，请求会发回原帖线程。

怎么用，其实就一个字段。在 Managed Deep Agents 里给子 agent 加 async: True：

subagents=[ { "name": "researcher", "description": "Researches a topic in the background.", "async": True, }, ]

Python 和 JavaScript 版 Deep Agents 都已支持。每个托管 agent 还会自动得到一个通用子 agent 的 async 副本，运行时自己决定把活放前台还是后台。要注意任务通知还在 beta，API 可能变。

经常有小伙伴问我，怎么用 AI 做出好看的产品设计，不那么 AI Slop，其实不是很好答，因为自己也不是专业的，只能站在产品工程师视角来给大伙聊一聊，怎么做出不丑且易用的产品。

首先要知道一个前提，很多时候好看的设计也救不了不解决问题的产品，设计在这里只是锦上添花的作用，而非决定产品的成败，假如要我选择产品优先级，应该是能解决问题 > 易于使用 > 好看美观，好比先解决不饿着、再解决温饱、最好解决吃好一样。

能解决问题这里不多说，更多取决于产品本身，它是去解决一个具体的需求，有人需要，有场景需要，刚好你这个产品可以提供一个解决方案让人或者 Agent 使用完成目标就好了，只不过解决问题有大有小。

那么如何做易用且不丑的产品呢？哈哈，可以照着走一遍，也可以把下面的这一大段给你的 Agent 让他去帮你 Review 一下你的产品代码仓库。

1. 把自己当做一个普通不懂技术的小白，他拿到我们产品，能否把主链路走完产出他所需要的东西，哪些地方有卡点，哪些地方没有讲明白，哪些地方的衔接不通顺，全部去修复，让用户不用说明书也可以完成产品的使用，假如实在不能，可以适当补充提示说明。

2. 所有文案需要符合对应语言当地人的使用习惯，需要仔细斟酌词藻，不要干巴巴的翻译，可以从 Apple、Windows 系统以及知名网站去找同类词的最好翻译和解释，文案做到尽可能让本地人感觉非常简单、易懂、清晰。

3. 产品上能用产品本身表达清楚的地方就不要再加文案说明，不要啰嗦的解释一个东西，仔细思考每一个说明文案是否达意且不啰嗦，交互视觉可以说清楚的地方就不要用文案再表达一遍。

4. 在数字的表达上需要让用户明白这个数据指的内容，以及考虑到数据表达意思后的易读，比如钱、指标、距离各种单位需要考虑到本身的最佳实践，数据的准确性非常重要，不要为了偷懒少了数据的校验。

5. 对于用户确定的操作不需要反复找用户确定，只有在会产生不可逆影响的时候二次找用户确定是否需要执行，防止满屏都是各种弹框确定，对于危险的操作不要出现大片的红，需要考虑用户操作一个产品的愉悦度，用户不是傻子不要过度担心会犯错。

6. 视觉上，一个页面只留一个强调色，尽量不要使用橙色、陶土色和后台常见的那种老企业亮蓝色，灰色全部用偏暖的灰，不使用冷冰冰的蓝灰，找不到合适的颜色可以去中国传统颜色里面去找到合适的。

7. 字号类型尽可能少一点，一个页面最多控制4种不同的字号，需要考虑到页面整体的阅读节奏感，清晰感以及文字的对比度，确保符合无障碍，包括考虑到行间间、字间距、段落间距需要反复调整，同时保持整体的规范一致。

8. 少用斜体、等宽字体、全大写，要用的场景必须要有详细的理由说明，说明文案不要使用斜体，等宽字体只用于代码、路径、指标，按钮和标签里面的字不要大写，少用中间点 · 来连接内容。同一个动作在整个产品里面只用一个动词，此外动词的考虑尽量不要催促用户去执行，比如少用立即购买这种营销词。

9. 页面的按钮、间距、圆角、分割线、弹窗、动画、阴影这类设计规范保持一致，同时保持克制，不打扰用户，嵌套的圆角要同心，里面的圆角等于外面的圆角减去间距会更好看。页面默认是平的，不叠阴影、不发光、不加毛玻璃，阴影只给真正浮起来的弹窗，不要卡片套卡片。

10. 在多语言的环境下，优先考虑最长文案的排布，优先考虑达意而非为了好看而改变原意，可以改文案，但不要变字号和截断。需要特别考虑在不同尺寸下的展示效果是否都良好，考虑到用户常用的设备，全部去测试，遇到不好的地方全部修复。

11. 对于反复调整不好的设计，或者做了好多轮都感觉不好看的设计，让 Agent 帮你出3个他认为最好的方案来让你挑选，然后你选择一个更好的，告诉他去优化，直到改到你满意，我比较喜欢让 AI 生成对比前后的图片放到一个pdf里面，这样我的阅读对比体验会更好。

大概就是上面这些，不过还有一个非常重要的就是你自己的耐心和反复调整，我比较强迫症，经常会因为了一个文案、一个颜色、一个设计和 AI 讨论十几轮，直到自己满意了才舒服，虽然 AI 很聪明，但是很多时候你对他的要求要更多，以及你需要付出更多的时间和耐心，才可以做出满意的效果，或者说你多花时间，多去看好的设计，其实就可以做出易用不丑的产品了。
