2、研究主题，以及 AI 实际采用的信源

参考 GEO 表现好的竞品 + Fan-out Queries 拆解方式，整理用户问题，整理出 AI 回答这些问题时需要覆盖的主题。

同时检查它实际引用了哪些信源。如果经常引用 Reddit，就去参与相关讨论；如果引用知乎，就在知乎持续建设内容；如果偏好行业媒体、测评网站或垂直社区，就把运营资源投向这些渠道。

重点不是猜“AI 喜欢哪个平台”，而是根据目标主题验证它正在采用什么信源。

内容覆盖只是基础。

先让 AI 能理解你，再让它找到外部证据相信你。

工具增强的 LLM agent 要在几千个 API 的注册表里找到对的工具，而上下文窗口装不下全部工具定义。主流做法是先检索再规划（Retrieve-then-Plan，RtP）：把用户查询做 embedding，用近似最近邻搜出相似工具。Apple 这篇论文（EMNLP 2026 Industry Track）提出了另一条路——先规划再检索（Plan-then-Retrieve，PtR）：让 LLM 先生成"抽象工具桩"（描述所需能力的假想签名），再拿这些桩去注册表里检索。

他们在 ToolBench 上做了对照实验：46,984 个 API 端点、50 个类目，查询分成三类——单工具（G1）、同类目多工具（G2）、跨类目多工具（G3）。

结果是一个随复杂度翻转的交叉。

单工具查询（G1），RtP 全面领先：召回率 0.372 对 0.289（p=0.002）、精确率 0.274 对 0.209、通过率 0.884 对 0.840。逐查询看，G1 上 RtP 赢 63 条、PtR 赢 33 条。

多工具查询（G2）反过来，PtR 领先：召回率 0.188 对 0.143（p<0.001）、精确率 0.204 对 0.167、通过率 0.855 对 0.747。逐查询看，PtR 赢 69 条、RtP 赢 30 条。跨类目（G3，样本只有 100 条）PtR 保持方向性优势：通过率 0.820 对 0.732（p<0.001），召回率差异未达显著。

这个交叉很稳：每一个检索预算（k=1 到 20）都成立，PtR 在 G2 的优势随 k 增大而从 +0.014 涨到 +0.066；注册表从 1k 扩到 47k 个 API 也成立（召回率标准差 < 0.012）；换成 gpt-oss-120b 复现方向一致。而且规模越大越要紧——两种架构选出完全不同的 top-k 工具的查询比例，从 1k 时的 88% 升到 47k 时的 98%。

为什么翻转，论文给的解释是意图与注册表的耦合度。单工具查询里耦合度高：原始查询往往直接包含 API 的名字或品牌，RtP 的 embedding 能直接命中，而先规划这一步反而把信号抽象掉了。多工具查询里耦合度低：一个 embedding 装不下多面意图——G2 平均需要 6.5 个正确 API（G1 是 5.2 个），而 PtR 平均生成 2.4 到 2.5 个桩，每个桩锚定一个不同的功能子需求，各自独立检索。

他们也排除了一种怀疑：PtR 的优势是不是只是"搜得更宽"？用 k 消融回答——当 RtP 用 k=10（等效于 PtR 在 k=5 时的搜索宽度）时，G2 召回率 0.186，跟 PtR 的 0.188 几乎一样；但代价是它要塞 10 个 API 给规划器，精确率只有 PtR 交付 5 个时的一半。G1 的结论不受影响：即便 k=10，RtP 的 G1 召回率 0.453 也远超 PtR 在 k=5 的 0.279。

还有两个值得记的观察。第一，检索才是瓶颈：轨迹忠实度至少 96%——规划器几乎总是从检索到的集合里选工具，所以检索阶段选什么架构，基本决定了后面整条轨迹，两种架构在 G3 上规划的步数都不一样（PtR 4.1 步 / 点名 1.4 个 API，RtP 3.6 步 / 1.1 个）。第二，桩会幻觉：LLM 会编出看起来合理但不存在的 API——这是双刃剑，在简单查询上它毁掉高耦合信号，在复杂查询上它把多面意图拆成功能子需求。

代价也很明确：PtR 多一次发现调用，token 开销增加约 75% 到 104%，而且在关键路径上多一个完整的 LLM 往返（既是 token 成本也是延迟）。单工具查询上这是净亏（召回率 −0.072），多工具查询上是净赚（+0.042）。

所以论文给的落地建议是复杂度自适应路由：单工具走 RtP、多工具走 PtR，能省下约 16% 的总推理 token（相当于 PtR 发现开销的 36%）而不损失检索质量，并且对单工具类查询完全省掉那一次额外往返。路由信号不需要额外花钱——RtP 自己的 top-1 余弦相似度就是一个零成本信号；此外查询长度、从句数量、命名实体密度、是否含并列子目标，也都能在任何 LLM 调用之前算出来。

单机能跑多大：Qwen 3.8 27B 和 Mistral Medium 3.5 128B 在 512GB 统一内存的 Mac Studio 上都放得下，大上下文时分别占 68GB 和 158GB 内存。他们用三个指标衡量：首字延迟 TTFT、生成速度（token/秒）、和峰值功耗，上下文取 8,192 与 65,536 两档。

性能的瓶颈分两种。TTFT 基本是算力瓶颈，这正是 M5 Ultra GPU 里神经加速器的用武之地；生成速度则是内存带宽瓶颈，M5 Ultra 给到 1.2 TB/s 统一内存带宽，M3 Ultra 是 819 GB/s。

① 如何评估“上下文压缩”没有丢失关键信息？ 不能单纯依赖 ROUGE/BLEU 这类字面相似度，必须建立三层评估闭环： 1. 槽位守恒检验（Slot-Filling Invariance）： * 定义任务的关键状态 Schema（如：`{category: "camping", budget_tier: "mid-low", destination: "Sydney", constraints: [...]}`）。 * 压缩前后分别运行轻量解析器，校验约束槽位的保留率与一致性（Precision/Recall on State Slots）。 2. 逆向探针重构（Reconstruction Probing / LLM-as-a-Judge）：仅向评测模型输入压缩后的文本，提问反事实问题：“用户的预算限制是什么？”“配送地有什么特殊要求？”。若能无损推断出原约束，则证明语义信息量（Mutual Information）守恒。 3. 下游执行等价性（Execution Equivalence）：在 Eval 集上，对比（完整上下文输出的 Action 序列）与（压缩上下文输出的 Action 序列）的匹配度（Tool Call Signature Match）。

② 如何自动决定：直接调工具 vs 派发子 Agent vs 切换模型？ 这需要实现一个分层元路由器（Hierarchical Meta-Controller），其决策逻辑是分级递进的：

[用户请求] │ ▼ [轻量分类器 / 特征提取] ──(静态规则 / 小模型 Router) │ ├─► 复杂度评分 (Complexity Score) ├─► 依赖步数 (Dependency Depth) └─► 预估 Token 开销

* 决策规则 1：何时直接调工具（Direct Tool Call） * 特征：单步/少步逻辑、明确的 I/O Schema、低上下文膨胀（如：输入“悉尼”调用 `get_shipping_rates(dest="SYD")`）。 * 路由：当前主模型直接挂载 Function Calling，单轮即走。 * 决策规则 2：何时派发子 Agent（Multi-Agent Delegation） * 特征：任务具有探索性质（Exploration）、需要多轮环境交互、预估处理的中间 Token 数超过阈值（如 > 4k tokens）、存在独立的目标达成判定逻辑。 * 路由：主 Agent 生成 Sub-goal，Fork 独立子运行时。 * 决策规则 3：何时换模型（Model Cascading & Speculative Routing） * 分级降配（Cost-Down Routing）： * 意图分类、结构化槽位提取、格式转换、简单工具调用 -> 路由至 Small/Fast Model（如 8B 级别或 Flash 类模型）。 * 跨领域规划、复杂多约束仲裁、长文本反思 -> 路由至 Frontier Model（如 Claude 5.5 Sonnet / GPT-6 Astra 级别）。 * 推测执行与升级机制（Speculative Escalation）： * 默认由小模型快速生成，后置置信度打分器（Confidence Scorer）或 Guardrail 校验。若工具报错、JSON 解析失败或置信度低于阈值，自动静默升级（Fallback）至大模型重试。
