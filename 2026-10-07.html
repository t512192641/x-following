Anthropic 发布 Claude Haiku 5.5：小模型价格降到上一代的十分之一

Anthropic 今天发布了 Claude Haiku 5.5。Haiku 是 Claude 家族里最小、最便宜的一档，排在 Sonnet 和 Opus 之下，主要用来跑量大、对成本敏感的任务。

这次最大的变化是价格。处理 10 万 Token 以内的请求，Haiku 5.5 每百万 Token 输入 0.1 美元、输出 0.5 美元，比 Haiku 4.5 便宜 90%。超过 10 万 Token 的长请求是 0.5 和 2.5 美元，便宜一半。上一代 Haiku 收到的请求里约 90% 都在 10 万 Token 以内，所以按官方估算，平均运行成本降了约 75%。

10 万 Token 大约是一本中篇小说的长度，客服对话、文档摘要、分类打标这类日常任务，基本都在这个范围里。

价格降了，能力也上来了。官方公布的测试里，操作电脑完成多步骤任务（OSWorld 2.1）的成绩从 Haiku 4.5 的 15.7% 涨到 72.4%；在命令行里自主完成编程任务（Terminal-Bench 4.0）从 0 涨到 39.2%。Anthropic 说它是目前速度最快的模型（Opus 开快速模式除外），Asana 实测任务完成延迟降低了 30% 以上。

官方推荐的用法有两类。一类是批量的重复活，比如摘要、分类、数据库查询，以及实时客服、浏览器自动操作这种要求响应快的场景。另一类是给大模型打下手：写代码时让 Opus 5.5 或 Sonnet 5.5 当主力，把零碎的子任务分给 Haiku 5.5 去做，也就是当子智能体。

OpenAI Decisions API：与 Jev 正面同构的那一个

出处：OpenAI 官方文档（ https://developers.openai.com/api/docs/guides/decisions）+ Simon Willison 的实操报告与 llm-openai-decisions 插件

OpenAI 发布了 Decisions API：它评估文本、图像或两者，返回带类型的答案，比它自己的 Responses API 快约 10 倍。你可以拿到「某条件为真的概率」「从固定集合里选一个」「按评分标准打分」这三类答案，再把它们用于分类内容、路由请求、给工作排优先级。

目前是 public beta，官方说「数周内 GA」。现在只支持一个模型 gpt-6-luna，用专门的 POST /v1/decisions 端点。SDK 最低版本：Python 3.26.0、JavaScript 7.30.0、Go 3.73.0、Ruby 0.101.0、Java 4.78.0。

三种问题类型

一个请求由三部分组成：model（目前只有 gpt-6-luna）、input（共享证据：一段文本，或包含文本与图像的用户消息）、questions（要评估什么：每个问题的类型、指令、允许的选项或评分等级）。响应里是 answers 数组，每个问题要起唯一 name、API 会把名字回显。

predicate 检查某条件，比如照片里有没有可见损坏 / 段落是否相关 主结果是 probability：条件为真的估计概率（0 到 1） choice 从你给的选项里选一个，比如部门、内容类别 主结果是 choice：你提供的某个值 score 按有序等级给输入评级，比如问题严重度 主结果是 score：各等级索引的概率加权平均

choice 和 score 都会返回离散选项上的概率分布。没有顺序的类别用 choice（比如部门）；有顺序的等级用 score（比如严重度），它按数值索引做概率加权平均，所以得分可能落在两个等级之间。

官方给的分工很清楚：需要这三类答案就用 Decisions；需要按你自己的 JSON schema 生成对象（抽取字段、写解释）用 Responses API 的 Structured Outputs；需要模型请求一次带参数的工具调用，用 function calling。

几个会直接影响实现的细节

· 图像只能是内联 base64 data URL：这个端点不支持托管 HTTP/HTTPS 图片地址，也不支持 file_id。要把 input_text 和 input_image 拼在同一条用户消息里，才能让图与指令或上下文一起被评估。 · 需要依赖前一个答案的决策，请发两次独立请求：比如先判断有没有损坏，再用这个结果决定要不要问维修类别。 · 分类要给兜底选项（像 other），把落空的结果送进人工复核队列。 · 阈值要用你自己带标注的样本去定：按假阳性与假阴性的代价来选阈值。predicate 返回概率；choice 和 score 返回概率分布 + 一个独立的 confidence 字段。 · 写问题时围着可观测的标准写：不同关切拆成不同问题，选项之间含义要有区分，评分等级要让相邻两级有可分辨的标准。

定价与合规

· gpt-6-luna 的输入价格是 每 100 万 token 0.10 美元。只收输入 token：没有 cache-read、cache-write、output token 的费用。 · 区域处理溢价与长上下文输入的价格乘数照常适用；这些价格只适用于 /v1/decisions，用 gpt-6-luna 的其它请求按对应的模型与处理层级定价。 · 支持 Zero Data Retention（ZDR）与符合条件的客户用于 HIPAA；数据驻留与区域处理支持美国与欧洲（EEA + 瑞士）。

Simon Willison 的实操

Simon 已经有一个跟 Jev 对话的插件 llm-typesafe，于是他让 GPT-6 Astra 读了 OpenAI 这份新文档，照着 llm-typesafe 造出 llm-openai-decisions。装完之后一条命令就能连图带问题一起问：

llm -m openai-decisions/gpt-6-luna \ -a https://static.simonwillison.net/static/2025/two-pelicans.jpg \ -s 'Does this image contain any mammals?'

输出：

{"type": "predicate", "name": "evaluation", "probability": 0.0}

他点出了两个与 Jev 的关键差别：一是新的 gpt-6-luna 除了文本还支持图像输入；二是两家都只对输入收费、不对输出收费——OpenAI 是每百万输入 0.10 美元，Jev 是 0.042 美元（约 2.4 倍）。除此之外「API 的形状概念上非常接近 Jev」：Jev 支持的那三种问题类型（是/否、选择、打分），OpenAI 的 Decisions 也一样。

为什么这条值得单独拿出来看

昨天我们刚发完 Diogo Almeida 那篇访谈——他在里面说，当年在 OpenAI 做不成 Jev，因为「调用者是代码，不是人」这件事在那边得不到资源；他因此出去创业，做出了面向程序、只做判定、按美元买智能的决策模型。今天 OpenAI 自己把同构的东西做成了产品线的一部分。

三件事值得记住：价格（OpenAI 比 Jev 贵约 2.4 倍）、多模态（OpenAI 多了图像输入，Jev 目前没有）、位置（OpenAI 把它定位成 Responses API 的「快 10 倍」的判定通道，而不是通用对话能力）。换句话说，决策模型从一个创业公司的 niche，变成了大厂 API 目录里的一个端点。

但它离 Jev 那套主张还有距离，别急着当成等价物：它仍在 beta、只有一个模型、图像必须内联（不能给 URL）、而「类型安全的原语」这件事在 Jev 那边是从 API 形状到语义都设计过的，OpenAI 这边目前看的是一份工程文档。要判断它是否真的能替代，最实际的办法就是在自己的分类任务上把两边的阈值和错误率都量一遍。

Your company can adopt AI everywhere and still take just as long to get anything done.

People produce work faster, then wait for someone to review it, move it into another system or start the next step. The individual tasks improve while the process barely changes.

When I think about the move from AI tools to an agentic organisation, I break it into seven stages:

1. Tool adoption

People use AI to help with individual tasks. They still provide the context, start the work and decide what happens with the result.

This is a useful place to begin. It also reveals which recurring tasks might be worth building into a reliable workflow.

2. The context layer

Give agents access to the information they need: business rules, customer records, product knowledge and previous decisions.

That might come through documents, databases, search or APIs. Keep ownership and permissions clear so agents can retrieve relevant information without gaining access to everything.

3. Harness engineering and evals

Define what successful completion looks like. Start with real tasks, checked outcomes and the exceptions your team regularly handles.

Build the routing, tools and controls around those requirements, then evaluate the model and harness together.

Repeat trials to check consistency. Rerun relevant evals when you change the system, and turn production failures into new test cases. This gives you evidence for decisions about quality, model choice and cost.

4. Put automations into production

Move useful automations into managed services that can run on a schedule or respond to an event without depending on someone’s laptop or personal login.

Give them monitoring, failure handling and an owner who responds when something breaks.

An automation that works for its creator still needs engineering before other people can depend on it.

5. Manage governance at scale

Permissions and oversight should already be in place. As usage grows, maintain an inventory of agents, their owners, what they can access and whether they still serve a purpose.

Review performance and permissions regularly. Investigate deterioration, and retire agents that no longer add value, including removing their access.

6. Connect agents around a business process

Where multiple agents are useful, define what each handoff must contain and what happens when the next step cannot proceed.

Use code to check requirements you can verify deterministically. Use model judges for criteria that need interpretation, calibrated against human review.

Test the handoffs as well as the individual agents.

7. Run and measure the complete workflow

Coordinate the process across agents, conventional software and people, including retries, approvals and exceptions.

Evaluate whether the whole task gets completed correctly. Track failures, human intervention and cost per successful completion alongside production monitoring.

We walked a VP of Engineering through this framework. His organisation had more than a hundred tools and was still largely at tool adoption.

My advice in that situation is to choose one valuable workflow and make it dependable from start to finish.

That gives the business something concrete to build on: a process with an owner, measurable results and evidence that it works.

不知道纯想哥具体要做啥，但是我可以简单聊聊 IM 这块的复杂度，因为除了本身要的业务外，当你用 IM 这种形式的时候，IM 也变成了一个业务。

任何线上服务都涉及到后端架构设计，IM 这块尤为复杂，IM 的业务复杂度分为两个：消息可靠性和消息分发。

▍消息分发

单聊就不说了，没啥分发性，一个收件箱（你可以理解这是一个用户的未读列表）足以。

以最常见的微信群聊和 TG 群聊举例子，微信群聊的上限是 500 人，TG 则支持万人群，两者选用的消息分发策略截然不同。

微信采用的是写扩散：在一个 500 人群中，任何一个人发送的消息都会被写到其他群友的收件箱中，它的好处就是收消息、离线补偿的逻辑简单，坏处是群大了之后消息分发量级指数上升，所以微信群有个 500 人上限。

TG 采用的是读扩散：任何一个人发送的消息会被写到共享群消息流，其他用户只需要拉取共享群消息流即可，好处是群可以非常大，万人群也没有额外的消耗，坏处是需要维护各个群的用户读取索引，并且大热门的群会形成热点，有可能引发缓存击穿。

除了微信、TG 所有的社交平台其实都有这套逻辑，比如微博、朋友圈等，它们可以采用分层设计，比如对超级大 V 单独做读扩散，对普通用户做写扩散，这依然无法彻底解决刚才说的缓存击穿问题。

这也是为什么，微博天天有热点，有时候还是会被打挂，这不是单纯加机器可以解决的问题，某一个消息热点分布在某个机器/集群上，大流量冲击迅速打挂这个机器。

▍消息可靠性

对比上面的业务问题，消息可靠性是一个技术问题，更可控一点，它面对的问题如下：

1. 保证消息顺序：用户的两条消息在弱网情况下，可能后发的消息先到服务器。 2. 保证消息幂等：IM 客户端肯定有重发机制，重发的结果不能让用户发现误发了重复的消息。 3. 断网恢复：消息要保证有序展示、不丢失未在线情况下的消息。 4. 消息不丢：用户消息发出去了，无论经历了什么样的情况，当用户界面上没有消息发送失败的提示时，你都要保证用户消息真的被服务端接收并处理的。

上面这套东西起码会用到 MQ、Redis 缓存这样的中间件，成本不低，真实的业务不是一个简单的 CRUD 就完事的，不过业务做起来了这些都不是问题，比如 Cursor 前期就是乱做的技术架构，后面把核心数据库都换了。
