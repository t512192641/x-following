AI推理越长，显存越吃紧？

EdgeRock 提供了一种新的解法...

普通大模型在进行长文本或复杂推理时，要写很长的推导

它通常会把前文处理过的信息暂存在 GPU 的工作空间里，这个空间叫“显存”。推导越长，这部分信息占的显存空间就会越来越大

EdgeRock-4B 打破了这一规律： 无论模型推理思考了多长时间、上下文扩展到多少万字，每个请求占用的注意力和状态显存大小都锁定不变（仅需 97.76 MiB，其中注意力 KV 仅 72 MiB）

但解高难度题的水平几乎不打折...

实测有多强？

解题能力不缩水：在极难的 AIME 数学竞赛题上，准确率达到 82.9%，几乎追平了那些显存无节制暴涨的正常顶尖小模型，彻底粉碎了“定长内存模型不能做深度推理”的魔咒。

显存省了 99%：在 256K 超长文本下，注意力缓存显存从原来的 8 GB 骤降到 72 MB，降幅达 99.1%。

并发处理能力翻倍：在一张普通的 80GB 显卡上，由于显存不再膨胀，可以直接同时塞满 512 个长推导任务，跑起来的速度和总吞吐量是原本架构的 4.9 到 6.4 倍。

它是怎么做到的？（三件套分工）

模型把记忆工作拆分成了三件事：

看眼前（局部窗口）：随时看清眼下最新的 1,024 个字，保证当前说话、写公式顺畅。

记个大概（循环网络）：用一个固定大小的“印象表”，随时记录上下文的大致发展方向。

关键便签盒（磐石记忆锚点 RMA）： 挑重点写：模型每产生一个词，都有一个专门的小模块评估：“这句话在后面会不会是关键解题线索？”

限量 1,024 张便签：这个便签盒容量固定，只存最重要的 1,024 条信息。每攒够一批新候选，就进行打分淘汰，只留含金量最高的。

随时翻看原话：这些便签是原文高精度的记录。哪怕是 10 万个字之前定义的一条规则，后续只要用到，直接就能从盒子里原汁原味地翻出来。

Reticle：让 coding agent 在真实运行的应用里做验收（yibie）：开发构建注入 SDK，经 MCP 拿 live 状态，只回 pass / fail / cannot tell，专治「agent 说 done 但弹窗坏了/静默 500」

yibie @yibie

用 coding agent 写代码的人，最后都会多出一个角色：给 agent 当 QA。Reticle 解决的就是这个：让 agent 去真实运行的应用里验收，只回 pass、fail、cannot tell 三种结论。

agent 说 done 的时候，坏掉的弹窗、静默的 500、顶着成功提示的失败部署都不会自己冒出来，得你点一遍才发现。Reticle 在应用里放进一个只在开发构建生效的 SDK，agent 通过 MCP 拿到 look、act、observe、assert 四个工具，透过 SDK 读应用内部：请求和响应、store 状态、console 报错，以及每处的源码行。

每次检查返回的是结论，不是截图。只有 pass 算通过；判断不了的返回 cannot tell 并说明原因，从不悄悄给绿。附上决定它的证据，和要打开的 file:line。

通过的一次可以存成 flow。之后不用 AI 模型就能确定性重放，今天的修复不会悄悄弄坏上周的功能。CI 里 reticle gate 会让触碰了 flow 代码、却没跑出新的通过记录的改动直接失败。

安全上它按验证工具必须住进被验证的应用来设计：SDK 不进生产构建，本地 bridge 只听 127.0.0.1，不连接平台的话应用数据不出你的机器。

我的判断：Reticle 值得抄的不是能读请求和状态，而是把验证设计成生成的反面。agent 天生乐观，验证必须允许回来一个不知道；只有 yes 和 no 的检查器会逼 agent 硬给结论，多出的 unknown 才是让 done 可信的关键。落到你身上，就是验收这一步不再靠你手工点一遍。

yibie @yibie

用 coding agent 写代码，最说不清的就是：它到底帮我省了多少时间，又实际花了多少钱。

XTrace 是开源的 macOS 应用（Apache-2.0），直接读你 Mac 上已有的 Claude Code、Codex、Cursor 历史，把它拆成三个时间类别。

代理时间：把会话里记录的事件聚成活动区间，超过 20 分钟的间隙排除，重叠的会话相加。所以它测的是会话活动，不是纯模型计算时间，也不是墙上时钟时间。

估算人力时间：识别为你发送的消息，连续消息间隔不超过 60 分钟算同一个工作时段，单条孤立消息不计时。审查 diff 不直接检测，最后一条消息之后你做的事不会自动计入，阈值可在设置里改。

API 等价花费：按公开 API 价格估算会话花费，而不是你的订阅账单。测不到的值显示成横线，不是零。

三个时间类别放一起，它给出杠杆率（代理时长除以估算人力时长）、并发和 hands-off 时间，再配 7/14/30 天与上一周期的对比。README 自己也提醒：代理时长多不证明生产力提高，要对照你交付了什么、审查花了多少。

当时想用 Swift 手写实现这个能力，原本的就是用 JS 实现的，非常复杂差不多快要放弃了，洗澡的时候突然想到一个点子，其实在Swift里面我完全可以去调用一个 JavaScriptCore 的能力，它是可以执行JS的，那我是不是可以把杂乱的 md 当做一个字符串传到这个里面去运行，然后帮我输出非常清晰规范化的 md 字符串，我再解析渲染出来，立马去测试验证，真的可以，效果感觉非常不错，在当时没有 AI 的时代，假如我用 Swift 去实现这个格式化引擎，不知道要多久才搞得出。

再到后面，就更有意思了，当时写 Pake 这个桌面打包工具的时候，主要是 Rust 写的，但是 Rust 的生态在当时也非常差，比如我想写一些下载的能力，完成后弹出一个 Toast 的能力，它甚至都没有成型的 Toast 组件，既然我会前端，当时想到的点是，可以通过 Rust 去调用 JS，让 JS 生成一个 document 容器塞到 Web 里面去，这样在有消息通知的时候，我可以让 Rust 去调 JS，把这个东西渲染出来，效果也非常好，同时不会影响原有的性能，还能够更美观。

其实很多时候，假如你对各种语言都了解一点，碰到难搞问题的时候可以帮助你很快想到一些 Hack 的办法去解决，甚至你还会融会贯通，反过来调用，比如当时在渲染的 Web 里面，需要去调用下载的能力，这个时候还可以反向去调用Rust的成型的系统能力帮我去下载，性能就更高。

这个里面有一个很有意思的技术，讲土一点，你可以把它理解成通信，相当于不同语言之间可以通过一个中间层去交换信息，然后监听各自执行，刚刚上面 Rust 和 JS 相互调用这里就使用了这种技巧，甚至当你脑洞大开的时候，你甚至可以多个语言相互通信，当时做妙言的分栏编辑功能时候，一边是原生的 markdown 编辑器，一边是 webview 渲染的预览效果，Markdown 解析用的是 GitHub 开源的 C 语言库 cmark-gfm，性能和能力都非常牛逼，但是很底层，它可以在每一块 HTML 上标出对应原文的第几行，然后我用预览里的 JS 读这些标记，算出当前滚到了第几行，再通过消息通道告诉 Swift，编辑区同步跟着到这个位置，这样就很好实现了两边滚动预览效果是非常同步的。

类似这样的场景还挺多的，这种难题的解决是在前 AI 时代，我认为作为工程师最有意思的地方，你可以完全把各种语言当做一个工具，没有任何偏见的去使用，只基于场景选择最合适它的语言，而非我喜欢这个语言，就用这个语言去实现所有的功能。

宝玉 @dotey

月之暗面 10 月 23 日发布 Kimi K3.1 Pro，Kimi 网页版和 App、办公助手 Kimi Work、编程工具 Kimi Code 和 API 当天都能用。

官方说它是自家最强的开放权重模型，完整权重 11 月 4 日前放出。

K3.1 Pro 是在上一代 Kimi K3 基础上继续训练出来的，模型结构没换，多花了大量算力做强化学习，也就是让模型在几百个领域里反复做任务、按结果打分改进。

模型总共 2.8 万亿参数，处理每个 token 只动用其中约 1040 亿（token 是 AI 处理文字的单位，可以理解成文字碎片）。这种结构叫混合专家（MoE）：模型里有很多分工不同的“专家”小网络，每次只叫上一小部分干活，所以比同样大的普通模型算得快，但整个模型仍要全部装进内存。它一次能读 100 万 token，相当于一个中型代码仓库或几百页财报，也能看图和视频。

【和 Claude、GPT 比怎么样】

下面的成绩都来自月之暗面自己公布的对比表，对手是 Anthropic 的 Claude Opus 5.5、Claude Fable 5.1 和 OpenAI 的 GPT-6 Astra，所有模型开到最高推理强度。部分对手成绩是 Kimi 自己测的，内部测试外人无法复现。

写代码基本追平。

在命令行里完成真实开发任务的 Terminal-Bench 4.0，K3.1 Pro 65.7%，Opus 5.5 66.4%，GPT-6 Astra 58.2%；做大型软件项目的 SWE-Marathon，K3.1 Pro 51.7 分排第一，Opus 5.5 46.3。科学计算类的 Terminal-Bench Science 差距大，K3.1 Pro 38.1，GPT-6 Astra 68.1。

3D 建模稍逊。

K3.1 Pro 能直接写脚本操作 Blender、CAD 软件和 Unity、Unreal、Godot 游戏引擎，官方演示里做出了完整的 3D 游戏和能 3D 打印的台灯。在看几张渲染图、写 CAD 代码把零件还原出来的 BenchCAD 上，K3.1 Pro 92.7%，Opus 5.5 96.2%，GPT-6 Astra 95.9%。

金融是这次主打。

读真实财务文件、做多步计算的 OfficeQA Pro v2，K3.1 Pro 64.4 分排第一，Opus 5.5 62.2。Kimi 内部测试里，财务建模比 K3 高 7.2 分，写研究报告高 11.6 分。

推文说的“幻觉降低 65%”，来自 Kimi 内部一套专挑难题的事实核查测试：K3 说的每 100 个事实里有 23 个错的，K3.1 Pro 降到 8 个出头。同一测试里 Opus 5.5 是 15 个，GPT-6 Astra 是 5.5 个。官方注明这是压力测试，不代表日常使用的出错率。

【多少钱，能不能自己跑】

普通用户在 Kimi 网页版和 App 里就能用，免费用户能用多少官方没写。企业版默认关闭，要管理员手动开。

API 每百万 token 输入 2 美元、输出 10 美元，是 K3 价格的三分之二。Claude Opus 5.5 是输入 4 美元、输出 20 美元，贵一倍。快 2 到 3 倍的 Highspeed 版输入 4 美元、输出 20 美元，和 Opus 5.5 同价。API 账户要先充值至少 1 美元才能用。

开放权重是指模型文件公开，任何人都能下载，放在自己的服务器上运行、微调，数据不用经过月之暗面。但个人电脑跑不动：按 K3 采用的 4 位精度推算，光存放 2.8 万亿参数就要约 1.4TB 内存。许可证条款官方还没公布。

为了开放权重，月之暗面说训练时删掉了网络攻防相关的数据。同一套训练流程不删数据，内部漏洞利用测试能解 90.5% 的题，删了之后是 81.0%。官方称它的攻击能力仍落后于已经公开三个月以上的闭源顶级模型。

Alex Prompter @alex_prompter

I see AI agents fail inside big companies in two ways.

The first is obvious. The person who built it leaves, and the agent goes with them because it only ever ran on their laptop. Nobody hosted it because the company never decided where agents should run.

The second is easier to miss. The agent gets hosted and runs for months without anyone checking it. The model updates or a system it reads from changes, but it keeps answering just as confidently.

Before a company ships its second agent, I want these written down:

> Where every agent runs. One runtime for the whole company > Who registers new agents > Who owns each one, by name > Which tools and data it can access, and who approved that access > When it gets reviewed, and when it gets retired

Congrats, you just made your product dumber to save nothing.
