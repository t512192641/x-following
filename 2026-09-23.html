Alex Prompter @alex_prompter

Putting five agents in a group chat and hoping they self-organize is how you get duplicated work and nobody checking anybody else. Coordination has to be picked on purpose, and the right pattern depends on what kind of work you are actually running.

Generator-verifier is for quality-critical output. One agent generates, another checks the result, and rejected output loops back with feedback until it passes. Reach for this on code generation, fact-checking, and compliance work, where being wrong costs more than being slow.

Orchestrator-subagent handles clear task decomposition. One lead agent plans and delegates, subagents handle focused tasks in parallel like security, tests, and style, and all of them return results back to the orchestrator. This fits code reviews, parallel checks, and any task that breaks cleanly into bounded subtasks.

Agent teams are built for long-running parallel work. A coordinator assigns tasks through a queue to workers who persist across assignments, accumulating context and domain expertise instead of starting fresh each time. Use this for migrations, multi-step tasks, and anything that benefits from an agent actually specializing.

Message bus fits event-driven pipelines. Agents publish and subscribe to events through a shared bus, so new agents can join without anyone rewiring the system. This is the right call for security operations, growing ecosystems, and workflows that change shape over time.

Shared state works when the goal is collaborative findings. There is no coordinator at all, agents read and write directly to a shared store, and findings become instantly visible to every other agent. Reach for this in research synthesis, where you want no single point of failure and real-time collaboration between agents.

AI-native 服务切法：从已外包且可验收的工作切入

出海去孵化器 @chuhaiqu

AI-native 服务，最好从客户已经外包、也能验收的工作切进去。

服务业里有一大笔预算，本来就花在人身上。会计、理赔、合规申报、合同审核，客户买的是一份完成的结果。AI 可以先处理大部分标准工作，人工留在高风险环节。

找这两类工作

1. 客户本来就在为此付钱

医疗编码、报关归类、监管申报、租约摘要、房产税申诉、RFP、账单异常处理，都有成熟的外包市场。预算已经在，采购人也知道自己要买什么。

2. 结果要能验收

一份材料合不合规、一条编码对不对、一份报告有没有漏字段，都能按规则检查。那些更依赖经验的判断，也得把人工复核放进交付流程。

客户付钱的对象要有明确终点

可以按一份理赔、一份申报、一封 demand letter、一份月度账目、一条审核记录收费。按月收也可以，但服务范围必须写清楚。

按小时收费很难放大。收入会重新绑回人头。能反复报价、反复交付的单位，后面才有机会做成产品。

前 5 个客户，先人工兜底

一开始让 AI 干活，团队逐条检查后再交付。这个阶段最重要的产出，是错误清单

每发现一个问题，都记下这 3 件事 - 什么输入会触发 - 正确结果该是什么样 - 下次怎么查出来

规则库会越做越厚

模型、提示词和案例库负责把活干出来，规则库负责定义交付标准。

做了几十单以后，重复错误会集中起来。高频错误写进检查项，低风险结果直接交付。碰到法律、金钱、客户声誉相关的内容，继续交给人工审核。

把上下游也整理好

客户提交材料时，尽量让他填表、上传文件、补几项必填信息。每次都要开会确认范围，通常说明交付单元还不够清楚。

交付端也得让客户自己看得到进度。邮件、客户 portal、dashboard 都可以。每一单有状态、有结果、有待处理项，客户就不用一直追着人问。

定价看替代成本

客户原来给外部服务商付 2500 美元，你可以用 800 美元交付同一件事。对客户来说，这是一份更快、更便宜的替代方案。自动化把你的交付成本一点点压下来。

Kick 给小企业做记账，每月收 300 到 500 美元。EvenUp 给 injury firm 写 demand letter，按封收费。两种模式卖的都是已经完成的工作。

先跑一个小闭环

挑一个细分工作，找 5 个真实客户，用 AI 加人工把第一批单子交出去。

每做完一单，就更新规则库，把收集、审核、交付再压紧一点。

Skills vs MCP + Agent harness：模型不会替你做的 10 件事

Alex Prompter @alex_prompter

Skills and MCP solve two different problems, and mixing them up is why most agent setups end up either bloated or brittle.

A host agent does not load every skill it owns into context at once. It talks to a skill loader, which reads a folder of skill names and descriptions and pulls in only the one the task needs, a HuggingFace dataset skill, a writing skill, a code review skill. Each skill folder holds a SKILL.md as the main instruction file, plus any scripts it needs, so the agent gets full instructions only for the skill it actually loaded, not a wall of unused context.

MCP solves a separate problem, giving the agent access to live systems outside itself. A host like Claude, an IDE, or another AI tool talks through an MCP client to an MCP server, and each server wraps a real capability, Firecrawl for web scraping, a database, GitHub. Those servers then reach out over API to the actual website, database, or JSON endpoint and hand the result back through the same MCP connection.

The difference comes down to what each one is for. Skills package instructions and logic the agent runs itself. MCP packages a live connection to something the agent does not control. An agent that only has skills cannot touch a real database or a live API, and an agent that only has MCP servers has no repeatable instructions for how to use them well.

Bookmark this before you build an agent with one of these and wonder why it still cannot do half the job.
