官话版本：新站做 GEO，我会先抓三件事。

1、先建立 AI 对你的定位：这些是产品定位页，也是新站的 GEO 必做页

把首页、核心功能页、解决方案页和使用场景页补完整，让 AI 能回答：

你是谁？ 解决什么问题？ 服务哪类用户？ 和其他产品有什么区别？

2、研究主题，以及 AI 实际采用的信源

参考 GEO 表现好的竞品 + Fan-out Queries 拆解方式，整理用户问题，整理出 AI 回答这些问题时需要覆盖的主题。

同时检查它实际引用了哪些信源。如果经常引用 Reddit，就去参与相关讨论；如果引用知乎，就在知乎持续建设内容；如果偏好行业媒体、测评网站或垂直社区，就把运营资源投向这些渠道。

重点不是猜“AI 喜欢哪个平台”，而是根据目标主题验证它正在采用什么信源。

3、建设品牌信任

内容覆盖只是基础。

还要通过 PR、行业报道、第三方评测、专家引用、客户案例和持续一致的品牌信息，让更多可信来源提到你、解释你、验证你。

先让 AI 能理解你，再让它找到外部证据相信你。

定位 → 主题与信源 → 品牌信任

Google 打了个比方：把现代 Agent 塞进旧研发流程，等于给马车装喷气发动机。工具是快了，但协作摩擦也被等比放大，直接变成新的瓶颈。

具体会冒出三种问题：产出越快，同文件的合并冲突越多；巨型 PR 拆成套娃式依赖链，卡在跨时区评审手里；还有 AI 特有的，Agent 拿着过期快照，写出调用"已不存在函数"的代码，编译前毫无异常。

工具增强的 LLM agent 要在几千个 API 的注册表里找到对的工具，而上下文窗口装不下全部工具定义。主流做法是先检索再规划（Retrieve-then-Plan，RtP）：把用户查询做 embedding，用近似最近邻搜出相似工具。Apple 这篇论文（EMNLP 2026 Industry Track）提出了另一条路——先规划再检索（Plan-then-Retrieve，PtR）：让 LLM 先生成"抽象工具桩"（描述所需能力的假想签名），再拿这些桩去注册表里检索。

他们在 ToolBench 上做了对照实验：46,984 个 API 端点、50 个类目，查询分成三类——单工具（G1）、同类目多工具（G2）、跨类目多工具（G3）。

结果是一个随复杂度翻转的交叉。

单工具查询（G1），RtP 全面领先：召回率 0.372 对 0.289（p=0.002）、精确率 0.274 对 0.209、通过率 0.884 对 0.840。逐查询看，G1 上 RtP 赢 63 条、PtR 赢 33 条。

多工具查询（G2）反过来，PtR 领先：召回率 0.188 对 0.143（p<0.001）、精确率 0.204 对 0.167、通过率 0.855 对 0.747。逐查询看，PtR 赢 69 条、RtP 赢 30 条。跨类目（G3，样本只有 100 条）PtR 保持方向性优势：通过率 0.820 对 0.732（p<0.001），召回率差异未达显著。

这个交叉很稳：每一个检索预算（k=1 到 20）都成立，PtR 在 G2 的优势随 k 增大而从 +0.014 涨到 +0.066；注册表从 1k 扩到 47k 个 API 也成立（召回率标准差 < 0.012）；换成 gpt-oss-120b 复现方向一致。而且规模越大越要紧——两种架构选出完全不同的 top-k 工具的查询比例，从 1k 时的 88% 升到 47k 时的 98%。

为什么翻转，论文给的解释是意图与注册表的耦合度。单工具查询里耦合度高：原始查询往往直接包含 API 的名字或品牌，RtP 的 embedding 能直接命中，而先规划这一步反而把信号抽象掉了。多工具查询里耦合度低：一个 embedding 装不下多面意图——G2 平均需要 6.5 个正确 API（G1 是 5.2 个），而 PtR 平均生成 2.4 到 2.5 个桩，每个桩锚定一个不同的功能子需求，各自独立检索。

他们也排除了一种怀疑：PtR 的优势是不是只是"搜得更宽"？用 k 消融回答——当 RtP 用 k=10（等效于 PtR 在 k=5 时的搜索宽度）时，G2 召回率 0.186，跟 PtR 的 0.188 几乎一样；但代价是它要塞 10 个 API 给规划器，精确率只有 PtR 交付 5 个时的一半。G1 的结论不受影响：即便 k=10，RtP 的 G1 召回率 0.453 也远超 PtR 在 k=5 的 0.279。

还有两个值得记的观察。第一，检索才是瓶颈：轨迹忠实度至少 96%——规划器几乎总是从检索到的集合里选工具，所以检索阶段选什么架构，基本决定了后面整条轨迹，两种架构在 G3 上规划的步数都不一样（PtR 4.1 步 / 点名 1.4 个 API，RtP 3.6 步 / 1.1 个）。第二，桩会幻觉：LLM 会编出看起来合理但不存在的 API——这是双刃剑，在简单查询上它毁掉高耦合信号，在复杂查询上它把多面意图拆成功能子需求。

代价也很明确：PtR 多一次发现调用，token 开销增加约 75% 到 104%，而且在关键路径上多一个完整的 LLM 往返（既是 token 成本也是延迟）。单工具查询上这是净亏（召回率 −0.072），多工具查询上是净赚（+0.042）。

所以论文给的落地建议是复杂度自适应路由：单工具走 RtP、多工具走 PtR，能省下约 16% 的总推理 token（相当于 PtR 发现开销的 36%）而不损失检索质量，并且对单工具类查询完全省掉那一次额外往返。路由信号不需要额外花钱——RtP 自己的 top-1 余弦相似度就是一个零成本信号；此外查询长度、从句数量、命名实体密度、是否含并列子目标，也都能在任何 LLM 调用之前算出来。

yibie @yibie

Claude Code 团队自己说，Claude 写了 Claude Code 约 90% 的代码。那这些代码怎么审？这篇是他们的回答，也是这篇文章最值钱的地方：它没有讲"怎么让 AI 写得更准"，而是讲当代码产量翻倍之后，审查这件事本身要怎么重做。

先给两个数。6 月到 9 月，Claude Code 代码库合并的 PR 翻了一倍多，而被回滚的比例下降了 40% 以上。Anthropic 的 monorepo 更夸张：每天落地的变更从 5 月的约 2,500 次，涨到 30,000 多次。

他们没有取消审查，而是把大部分"阅读"交给机器，把人力和注意力留给只有人能干的事，并把重点放在"让出错容易撤回"。

先换掉那个问题

他们把"有人读过这段代码吗"这个判断标准换掉了——它太粗糙。他们换成：这次变更可能出什么问题，哪一道检查（自动的或人的）才是对的检查。

这个问题一换，审查的时机也跟着变。以前审查是终点站：写完、开 PR、等同事看。现在是持续的，更像打字时的拼写检查：大多数变更在被安排给人看之前，已经被 Claude 至少审过并修过一轮。

稀缺资源是人的时间和注意力

他们的目标写在明处：Claude Code 各个仓库（CLI、桌面/网页应用、移动应用）里，大多数 PR 最多经过一个人（这个人可以是作者自己），而回滚率和事故率不上升。

衡量人的成本，他们看三个数：每个 PR 的人工批准数（中位数和第 95 百分位）、人工评论数、PR 等一个人等多久。回滚率和事故率是护栏——如果这两个上升，那说明人时没有被省下，只是被挪走了。

一个变更要穿过七层

第一层在 PR 出现之前就开始。给 Claude 一些它能跑的东西——测试、构建、或者一张设计稿截图——要求它拿出输出而不是说"做完了"；然后让一个带着干净上下文的子 agent 去审这个 diff。这两个习惯写在他们自己的最佳实践里。

这一层还靠两份文件。CLAUDE.md 说明这个项目是什么：技术栈、约定、目标和反目标；每次审查都会加载它，所以在大仓库里要保持短，再用它指向别的文档。审查器也会标出违反其中约定的代码，以及让里面某一行过时的变更。REVIEW.md 由代码所有者写，说明他负责的那部分什么才要紧——好的 REVIEW.md 很短，会写清"在这个仓库里失败长什么样"（文档是"它说谎"，配置是"它路由错"），限制鸡毛蒜皮的条数，列出要跳过的路径，并且要求证据给出文件和行号而不是从名字猜；它还要求综述以数字开头，没有要修的就说没有。

第二层：每个 PR 在被看到之前，先过一遍 Claude 审查。它拿 diff 对着整个仓库和 PR 声明的意图读，问：这个变更解决了它的问题吗、符合系统吗、会不会弄坏别的地方？如果是修 bug，它去找根因。对外产品叫 Code Review for Claude Code（Team 和 Enterprise 版已正式可用），本地用 /code-review 跑轻量版。

一个可对照的数字：研究预览推出时，内部拿到实质性审查评论的 PR 占比从 16% 升到 54%。超过 1,000 行的大 PR 大多能拿到问题，小的基本是干净的。管理员可以按仓库设 Quick／Standard／Deep 三档；Deep 只在"漏一个 bug 的代价高于多花审查时间"的地方才值得。

第三层：发现的问题先由别的 agent 验证，再到人。多个 agent 同时找 bug，然后另一组 agent 对每条发现投票，票数够才发出来。只关乎风格、诊断信息、清理的建议直接丢掉——这两类过滤他们先在自己的 PR 上做过 A/B。留下的是按严重度排序的行内评论，每条标为 Important、Nit 或 Pre-existing，这样"不是这个 PR 引入的 bug"就不会被当成作者的错。

第四层：安全审查可以阻断合并。只要 bug 审查或安全审查还有未关闭的发现，PR 就合不了——要么改，要么给一句简短理由关掉线程（这也是误报的出口）。后续提交修好了，发现会自动消失。开源侧可以用安全审查的 GitHub Action 或 /security-review。

第五层：常规 CI。lint、类型检查、各平台测试、构建；一个典型的 CLI PR 在人看之前可能已经跑了几十个检查。PR 模板要求写清"怎么测的"和"怎么撤回"——Claude 可以代填，但要求这个变更的人要签字。

第六层：合并队列会带着这次变更、针对 main 重跑所有检查，所以两个单独能过的 PR 不会合出一个坏掉的 main。新行为通常先放在开关后面、只给 Anthropic 员工用，靠内部的高频使用把回归暴露在用户之前；公开版本先进 latest 通道，stable 跟在后面。

第七层：错误仍会有，最后一层是尽快抓住。开关不用部署就能关；Claude Code 有每周的值班轮值，事故复盘会问：哪一层本该抓住它。

让审查器本身变好

任何事故都会变成一条评测。他们收集过去导致事故的 PR，连同它的前滚修复与回滚，请熟悉那块代码的工程师确认每个 bug 以及它藏在哪；这个集合每天跑到审查器上。

噪音则是看人怎么处理评论来量：每条评论都按 PR 上那个人的反应归类——改了、说它错了、说这个行为是有意的、或者认为不重要。他们还会拿明知干净的 PR 去跑审查器，数它误报"会引导人做出有害改动"的比例。他们写下来的优先级是：先保证抓到真 bug，再谈减少审查轮次。

第二份工作：让全组读懂代码

审查一直有第二份工作——把代码库的理解传开。读同事的 diff 是你知道什么变了、各块怎么拼起来的方式。如果机器读了大部分，人怎么学？

文章没有给出完整答案，但把这件事点出来了：At Anthropic，他们的工作从"读每一个 diff"变成了"做机器不擅长的那些决定"。

怎么把这套搬过去

给 agent 一些它能跑的检查，写进一份短的 CLAUDE.md，加上跑格式化和 lint 的 hook；本地跑 /code-review 与 /security-review，或者用干净上下文的子 agent 审；加一份 REVIEW.md，把重复的评论搬进去；要求 CI，并在 PR 模板里加"测试""风险""怎么撤回"；先在一个仓库上接 AI 审查器，调几周 REVIEW.md 再铺开；加自动安全审查，并要求合并前所有审查线程关闭；按风险匹配审查强度；限制审查轮次，前几轮之后只重审新增的 diff；对信任的作者保留轻量审批；用 CODEOWNERS 和分支保护让鉴权、计费、CI 与发布流程、安装器这类路径永远需要人；用合并队列、特性开关、内部先用、分阶段发布、一步回滚；把事故和回滚变成评测集，审查器的提示、工具或模型一变就重跑；最后，量人时，用回滚率和事故率当护栏。

文章结尾那句值得单独抄下来：Code Review 的发布说明写着，批准一个 PR 仍然是人的决定——产品只发布发现，不发布批准。他们自己的仓库更进一步，让所有者决定哪些低风险变更可以只靠自动检查合并，"而这条线还在移动"。

我们的判断：这篇文章真正可迁移的不是那七层——七层是 Anthropic 这个规模的答案，照抄会压死小团队。可迁移的是它换掉的那个问题：不问"人读了吗"，问"这次变更可能怎么坏、哪一道检查才对"。这一问会让审查从一道闸门变成一套分层检查，而回滚率与事故率必须一起量——否则省下人时只是把成本挪到后面。

Anthropic 这篇聊 Claude Code 团队怎么做 Review 的文章有点干货，推荐收藏！

他们 90% 的代码都是 Claude 写的，每天合并几万次提交，肉眼逐行去看早就不可能了。

结果：PR 翻倍了，revert 率反而降了 40%。

他们的几点很实操的做法⤵️

1. 别让人当第一道靶子 改完不能直接丢给同事。Claude 必须自己跑完测试、比对完截图，再叫另一个没上下文的 subagent 独立扫一遍 diff。

2. 多 Agent 投票，治好了 AI 废话多的毛病 平时大家不用 AI review，主要是烦它总挑一些缩进、命名的刺。他们是多个 agent 并行找 bug，再拉另一组 agent 投票，纯样式的吐槽直接被刷掉，最后报出来的基本都是硬伤。

3. 分级放权，谁 prompt 谁背锅 改个文档或者加个带 flag 的增量代码，自动化检查全绿就可以直接合了；动到核心模块或 CI 配置才拉工程师看。责任界定也很简单：谁指挥 AI 写的，谁就算 reviewer，出了 bug 自己来兜底。

4. 敢合的前提是回滚够快 只要出了事能在秒级关 flag 甚至直接撤回，这样就不用为了防错而把全流程卡死。

Apple 的机器学习团队发了一篇实测：用 MLX 加 RDMA over Thunderbolt，在 Mac Studio 上跑近万亿参数的前沿模型——从一台起步，再横向堆到多台。

单机能跑多大：Qwen 3.8 27B 和 Mistral Medium 3.5 128B 在 512GB 统一内存的 Mac Studio 上都放得下，大上下文时分别占 68GB 和 158GB 内存。他们用三个指标衡量：首字延迟 TTFT、生成速度（token/秒）、和峰值功耗，上下文取 8,192 与 65,536 两档。

性能的瓶颈分两种。TTFT 基本是算力瓶颈，这正是 M5 Ultra GPU 里神经加速器的用武之地；生成速度则是内存带宽瓶颈，M5 Ultra 给到 1.2 TB/s 统一内存带宽，M3 Ultra 是 819 GB/s。

功耗这条写得挺具体：M3 Ultra 的 Mac Studio 峰值约 200W，M5 Ultra 约 300W——约等于一台常见烤面包机的一小部分。更重要的是，这个量级意味着 Mac Studio 可以放进任何家里或办公室做 AI 工作。

但近万亿参数的模型单机放不下：Muse Spark Open 是 816B 总参数、42B 激活参数，按原生精度要超过 1.6TB 内存。所以进入多机。

MLX 支持两种切法：流水线并行按深度切（一半的层放一台机器），张量并行按宽度切。切换的命令很轻：

mlx.launch --hostfile hostfile.json --backend jaccl --env MLX_METAL_FAST_SYNCH=1 -- mlx_lm.benchmark --model mistralai/Mistral-Medium-3.5-128B -p 8192 -g 128 -b 1 --prefill-step-size 8192 --pipeline

其中 --backend jaccl 指定的是 RDMA Thunderbolt 驱动后端，MLX_METAL_FAST_SYNCH=1 打开一个实验性的同步特性。

结果（Qwen 3.8，8K 上下文）：首字延迟从 M3 Ultra 的 18.2 秒，到单台 M5 Ultra 的 4.1 秒，两台张量并行的 3.1 秒，四台的 1.7 秒；解码速度从 12.46 到 19.69、33.27、50.89 token/秒。Muse Spark Open 在两台流水线并行下是 8.4 秒 / 15.74 token/秒，四台张量并行是 4.8 秒 / 36.73 token/秒。他们提到，机器数量少时张量并行的通信开销会抵消一部分算力收益，但这只影响预填充阶段。

最后一段落到 agent：把 mlx_lm.server 也套上 mlx.launch，就能在多台 Mac Studio 上并行起一个本地推理服务，然后任何兼容 OpenAI 接口的客户端指过来就行——文章里给了 opencode 的配置示例，模型名写 Muse-Spark-Open-816B-A42B-NVFP4，baseURL 指向 http://127.0.0.1:8080/v1。

3/ 上下文压缩评估与元控制器（Meta-Router）自动化

① 如何评估“上下文压缩”没有丢失关键信息？ 不能单纯依赖 ROUGE/BLEU 这类字面相似度，必须建立三层评估闭环： 1. 槽位守恒检验（Slot-Filling Invariance）： * 定义任务的关键状态 Schema（如：`{category: "camping", budget_tier: "mid-low", destination: "Sydney", constraints: [...]}`）。 * 压缩前后分别运行轻量解析器，校验约束槽位的保留率与一致性（Precision/Recall on State Slots）。 2. 逆向探针重构（Reconstruction Probing / LLM-as-a-Judge）：仅向评测模型输入压缩后的文本，提问反事实问题：“用户的预算限制是什么？”“配送地有什么特殊要求？”。若能无损推断出原约束，则证明语义信息量（Mutual Information）守恒。 3. 下游执行等价性（Execution Equivalence）：在 Eval 集上，对比（完整上下文输出的 Action 序列）与（压缩上下文输出的 Action 序列）的匹配度（Tool Call Signature Match）。

② 如何自动决定：直接调工具 vs 派发子 Agent vs 切换模型？ 这需要实现一个分层元路由器（Hierarchical Meta-Controller），其决策逻辑是分级递进的：

[用户请求] │ ▼ [轻量分类器 / 特征提取] ──(静态规则 / 小模型 Router) │ ├─► 复杂度评分 (Complexity Score) ├─► 依赖步数 (Dependency Depth) └─► 预估 Token 开销

* 决策规则 1：何时直接调工具（Direct Tool Call） * 特征：单步/少步逻辑、明确的 I/O Schema、低上下文膨胀（如：输入“悉尼”调用 `get_shipping_rates(dest="SYD")`）。 * 路由：当前主模型直接挂载 Function Calling，单轮即走。 * 决策规则 2：何时派发子 Agent（Multi-Agent Delegation） * 特征：任务具有探索性质（Exploration）、需要多轮环境交互、预估处理的中间 Token 数超过阈值（如 > 4k tokens）、存在独立的目标达成判定逻辑。 * 路由：主 Agent 生成 Sub-goal，Fork 独立子运行时。 * 决策规则 3：何时换模型（Model Cascading & Speculative Routing） * 分级降配（Cost-Down Routing）： * 意图分类、结构化槽位提取、格式转换、简单工具调用 -> 路由至 Small/Fast Model（如 8B 级别或 Flash 类模型）。 * 跨领域规划、复杂多约束仲裁、长文本反思 -> 路由至 Frontier Model（如 Claude 5.5 Sonnet / GPT-6 Astra 级别）。 * 推测执行与升级机制（Speculative Escalation）： * 默认由小模型快速生成，后置置信度打分器（Confidence Scorer）或 Guardrail 校验。若工具报错、JSON 解析失败或置信度低于阈值，自动静默升级（Fallback）至大模型重试。

出海去孵化器 @chuhaiqu

买了一个标着"GDPR 合规"的 SaaS，不代表你的产品就合规了。

作为 Controller 的责任不会因为采购转给供应商。签之前要看：DPA、子处理方列表、数据存在哪、安全措施、出事多久通知你、能不能导出和删除、备份怎么处理、终止以后怎么办。供应商后来加了新的子处理方、换了地区、默认开启拿数据训练，或者删不掉数据，都得重新评估。

另外，大家画数据流的时候通常只记主数据库，但 GA、Plausible、Clarity、Hotjar 这类分析和录屏工具，支付、客服、邮件工具，还有 Onboarding 里收的那些字段，都是个人数据的去处，都得进数据地图。

Onboarding 表单也要回头看。每个字段都要对应一个目的，核心服务必需的和"顺便调研一下"的分开，调研类的做成选填，写清楚用来干嘛。

隐私这块书里没法给一个通用答案，不同地区规则差很多。但先把数据地图画出来，之后和律师沟通会高效很多。
