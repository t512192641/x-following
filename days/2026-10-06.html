Alex Prompter @alex_prompter

AI agent groups agreed 98.7% of the time on a logic puzzle.

In 74% of those groups, they agreed on a wrong answer.

A researcher at Waseda University took 100 real group discussions and replayed each one with AI.

The people were solving a classic logic puzzle. You see four cards, and you pick which ones to flip to test a rule.

Each person got an AI twin that started with that person's original answer. Then the twins discussed the puzzle the way the people did.

In the 45 groups where every person spoke, 51.1% ended with everyone on the same answer. The rest stayed split.

DeepSeek V4 Flash, the model behind the twins, got there 85.2% of the time with thinking off. With thinking on, it got there 95.6% of the time.

The researcher ran a second version with the cards renamed maple, birch, lantern, and candle. The logic stayed the same, but the textbook answer no longer applied.

With thinking on, 84% of groups agreed on the right answer to the original puzzle. After the rename, 24.7% did.

A second model, Qwen3-14B, over-agreed on the same groups.

About 20% of the people never wrote a single message. Of the AI agents, 0.2% never spoke.

Companies sell AI personas as stand-ins for real people in focus groups and survey panels. Researchers use them in studies. This paper is a test of that idea.

It tested one logic puzzle. In a small side test on an opinion question, the agents went the other way and agreed less than the people did.

So the error can run in either direction. Either way, the simulated groups didn't land where the real groups landed.

If a panel of AI agents tells you everyone agrees, check the answer yourself. Their agreement doesn't tell you whether they're right.

什么是 Codemode

（副题：如果你只需要 bash，为什么还需要 codemode？）

一年多前我在这里写过几篇文章，建议人们不要把自定义工具（或 MCP server）加载进上下文，而是直接用更多脚本。其中最重要的两篇是《代码就是你需要的全部》和《MCP 需要代码》。到 Pi 1.0，我们通过 Codemode 加上了 MCP 支持——这件事某种程度上姗姗来迟，但对一些人来说可能又有点意外。所以我想借着这个博客分享一些更新后的想法，说说这一切意味着什么。

什么是工具

当 Pi 这样的 harness 把工具提供给 LLM 调用时，它做的第一件事是提供若干工具定义，这些定义随后在服务端翻译成某种 token 结构。而一个模型是否被鼓励去调用某个工具，是强化学习过程的结果——这一点我以前写过，想了解可以去看那篇。

我们强烈偏向 CLI 和 bash 的原因之一，是它让调用变得容易组合；另一个原因是模型在训练时就学会了文件系统是怎么工作的。所以当它调用 echo foo > /tmp/test.txt 这样的工具时，模型同时也学到：这次调用之后，/tmp 里多了一个叫 test.txt 的文件。

但 bash 有一个根本限制：它只能组合"能跑的程序"。 有些东西不是程序，却是 LLM 的原生工具，而且它们只能如此。

最明显的例子是 read 或 view_image。如果一个多模态模型要读一张图，它没法用 cat——因为 harness 必须把真正的图像载荷注入进 LLM 的协议里。

另一个很鲜活的例子是子 agent。要派生和编排子 agent，很难绕开由 harness 提供的工具。理论上 agent 可以提供一个 CLI 工具，通过环境变量和 Unix socket 和外部 harness 通信，但这是个相当粗糙的做法。而它还有另一个问题：代码在哪里运行。

大脑与手

要理解这一点，值得再想一下所有这些零件分别跑在哪。通常确实涉及两个不同的系统。第一个是大脑，也就是 harness：它跑在一台机器上，是被信任的。第二个往往是同一台机器，但它是工具真正执行的地方：手。在 Pi 里我们现在把它叫执行环境，但你可以把它理解成所有操作的目标。

对我们来说关键的是：harness 这个大脑与运行 bash、执行工具的目标环境之间存在一条分界线。

把它一分为二有几个非常重要的后果。首先，它们跑在不同的文件系统上，并且有不同级别的信任。举例来说，如果你用像 Gondolin 这样的沙箱方案，你的 bash 那些东西会被很好地沙箱化，但 harness 本身不会。

编排 harness

这就引出了 Codemode 真正做的事：它是让 LLM 在 harness 一侧（而不是执行环境一侧）表达和编排复杂操作的方式。 Codemode 跑在 harness 里，在它自己的沙箱中。在 Pi 的情况下，它跑在 WASM 运行时里的 QuickJS 中，并带有刻意的限制：没有网络、没有文件系统、没有定时器、内存有限。唯一的出路是调用更多工具。你也可以想象让 Codemode 跑 Scheme 或别的语言。

如果你不熟悉 Codemode，它基本上就是一种"从某种语言内部发出工具调用"的方式——在我们这里是 JavaScript。它让你可以组合这些调用，而不必事事都经过 LLM 的上下文。这个命名的功劳归于 Cloudflare 的朋友们，是他们创造了这个词。

举个例子：如果你把一次 bash 调用作为普通工具调用发出，我们只会把末尾 2000 行放进上下文，agent 想要更多就得自己去读那个溢出文件。但如果 agent 是通过 Codemode 发出这次调用的，Codemode 这一侧会以结构化方式拿到更大的输出。

最重要的是，因为 Codemode 是 JavaScript，agent 可以表达并发操作和基本工作流。现在很常见的一种 agent 用法是：先从某个工具的响应里探测 5 到 10 条看看长什么样，然后写一个 Codemode 脚本去处理接下来的 n 条。

Codemode 还允许你把状态丢进 transcript。也就是说，一次 Codemode 调用可以把数据存下来，这个会话里下一次调用再把它读回去。记住：这发生在 harness 主机上，不是沙箱里。

在 Pi 的情况下，Codemode 还允许你发出一些在 Pi 的传统接口里完全不合理的调用。比如你想用图像模型生成图片，或者想用一次性分类模型给某段文本分类——这些 Pi API 通过 Codemode 暴露，而不是做成普通工具（做成工具只会白白浪费上下文）。

有个观点挺有意思：LLM 时代，最好的编程语言可能是 Common Lisp。

逻辑是这样的。LLM 写代码太快了，写代码不再是慢的那一步，慢的是验证：改完要重新编译、重启，等好几分钟。以前人写代码，写本身就够慢了，等编译那点时间不算啥；现在反过来了，反馈循环有多快，直接决定你造东西有多快。

Common Lisp 在这事上是作弊级的。它是 image-based，程序就是内存里一个活的镜像，新函数直接替换旧的，不用重启任何东西，读时编译时运行时的区别几乎被抹平，反馈循环约等于不存在。

更狠的是出错处理。别的语言一报错程序就崩了，LLM 得去读 crash log，改完再跑一遍。Lisp 不崩，它停下来打开 debugger，完整堆栈和变量全摆在面前。你直接把 LLM 指到 debugger 那儿，它修完，程序接着跑。

还有代码即数据那套。Lisp 里代码就是 list，程序可以改写程序，宏就是这么来的。你可以先给业务造一门语言，再用这门语言写程序。作者举了个 ERP 的例子：每家公司流程都不一样，都得改；如果 ERP 本身是用自己的领域语言写的，用户直接让 LLM 在这门语言里改，改出来的东西天然带着产品本身的设定，不会改散架。

Lisp 写出来还短，作者的经验是比 Python 短 6 到 7 倍。对 LLM 来说代码少就是 token 少，省钱，而且整个程序更容易塞
