psychic：用 LightGBM 排序的终端文件选择器

yibie @yibie

psychic：使用了机器学习模型的文件选择器

psychic 是终端里的文件浏览器，用法类似 fzf：敲字符、从列表选文件。不一样的是，它在你本机记录每次搜索和点击，用这些数据训练一个 LightGBM（梯度提升树）模型给结果排序，效果不错。

LightGBM 本身就是机器学习模型，所以这里的取舍不是用不用模型，而是用哪一类：几秒训完、纯本地跑的树模型，还是要联网、推理慢的 LLM。我最在意的是，开发者对模型的选择，如何明确把 LLM 排除在外，以及排除的理由。

理由是延迟：每次击键后，结果要在一帧内更新，UI 渲染低于 16ms。作者的取舍是宁可在两秒内做十次快搜索，也不要一次聪明但要等好几秒的搜索。

现在网络调用的时间间隔，就可能超过 10ms，任何非本地模型直接出局，LLM 和 transformer 同理；线性和逻辑回归够快，但作者实测效果明显比 LightGBM 差，也放弃了。

剩下树模型，还有第二层原因：这个任务的信号天生是表格数据。文件修改时间、大小、近期点击次数、query 与文件名的 fuzzy 匹配分，全是数值特征，LightGBM 正擅长，而且几秒就能从零重训一次。模型甚至不直接读文件名，而是靠「这个 query 历史点过哪些文件」这类特征记住关联。

效果数字是作者自己的使用统计，来自内置 stats 命令，只有他一个人的样本：2025 年 10 月以来打开 1450 次，平均敲 1.6 个字符，29% 的时候一个字符不打直接回车，80% 选第一条，中位耗时 2 秒。

作者在 HN 评论里把适用边界讲得很清楚。这套思路目前只用于文件和目录，因为能拿到文件系统元数据当输入；如果扩展到选进程、选容器这类一般文本输入，他说自己暂时没有既快又好的办法，transformer 能处理那种数据，但目前太慢。

所以这不是一个「小模型打败 LLM」的故事。是结构化信号加毫秒级延迟预算，两头一起把模型选型收窄到了一棵树；任务换成自由文本，结论可能就反过来了。读者备注里说的那种开发思路，我觉得落点在这里：先看清任务的延迟约束和数据形态，再决定要不要请出大模型。

methodology-appendix：给数据报告追加可复现的复制附录 skill

Garry Tan @garrytan

I send around PDFs and markdown files to my coworkers so much and they use their agents to make sense of the world too, so I started using this skill methodology-appendix to make sure their agents could replicate what my agents found.

--- name: methodology-appendix description: "Every data-backed report or memo ends with a Methodology / Replication Appendix: the signal choice and its sensitivity, verbatim queries, derivation pseudocode over named constants, the rebuild command, and drift/limits. Appended by default, without asking." ---

# Methodology / Replication Appendix

## Rule

Any report, PDF or page whose conclusions rest on data queries ends with a **Replication Appendix**. It is a working recipe, not a citation list. The test:

> A reader with an agent and equivalent data access can regenerate the document > end to end from the appendix alone, without contacting the author.

If a reader would have to ask "which column did you use?", "what date was this pulled?" or "how do I rebuild the PDF?", the appendix failed.

## Body voice

The body states conclusions plainly. No process narration ("I was asked...", "on the first pass..."), no self-grading. The first sentence after the title contains a finding. Everything about how you got there goes in the appendix at the end, written for forensic recreation.

## When this fires

Always, automatically, for: - analysis memos backed by database or API queries - any PDF sent to partners, executives or external stakeholders - pages presenting quantitative findings - anything with tables of counts, rates or percentiles

Skip for narrative or qualitative writing, meeting notes, personal memos, short ephemera, and documents with no data spine. Do not ask permission.

## The six sections

### 1. Header

```markdown ## Replication Appendix

A reader with an agent and equivalent data access can regenerate every number and rebuild this document from this appendix alone.

**Access required:** <tool/CLI + auth, internal APIs> **Snapshot date:** <ISO date>. Live-data documents won't reproduce exactly after this date; see Drift. ```

### 2. Signal definitions and the choice that mattered

The most important section. Analyses usually turn on one column or threshold choice. Name it, name the alternatives, state the impact.

```markdown ### Signal definitions

| Field | What it is | Why chosen / rejected | |---|---|---| | `score_a` | Ensembled score | **Primary.** More predictive per <source>. | | `score_b` | Single-model score | Rejected as primary; kept for contrast. | | final_decision | Human decision object | Not queried. Known gap. |

**Outcome sensitivity:** switching from score_b to score_a moved the headline count from N1 to N2 and changed claim X. A replication that changes the signal column will not match these numbers. ```

Always include an **Outcome sensitivity** line. If a different defensible choice changes the conclusion, the reader must know before quoting it.

### 3. Verbatim queries

Every query that produced a number, copy-pasteable, in document order, labelled by the finding it supports. Never paraphrase SQL. Never write "similar to the above." Add schema notes a replicator would otherwise get wrong: enum meanings, non-obvious joins, columns that seem to exist but don't.

### 4. Derivation pseudocode

Queries give raw counts; the document has derived figures. Show the arithmetic, with assumptions as named constants a reader can swap.

``` ITEMS_PER_DAY = 8 # observed median, <period> YIELD_HAIRCUT = 0.10..0.15 # marginal cases convert below observed rate

gap = count(status = REJECTED and score >= threshold) extra_days = gap / ITEMS_PER_DAY added_wins = gap * YIELD_HAIRCUT ```

Different constants change the recommendation, not just the number, so they must be visible.

### 5. Rebuild command

Exact commands from source markdown to verified PDF, plus a visual check (e.g. `pdfinfo` page count, `pdftoppm` a couple of pages and look at them). Name the source of record: the PDF is a render, never the original.

### 6. Drift, limits and known gaps

- **Live data moves.** What was mid-flight at snapshot; what is closed and stable. - **Coverage gaps.** Fields only populated for part of the range, and how tables were restricted rather than shown with misleading denominators. - **What this cannot see.** Inputs to the real decision that the data lacks. - **Retractions.** Any claim withdrawn between versions, and why.

## Procedure

1. Log queries verbatim as you run them. Reconstructed SQL is how appendices go wrong. 2. Write the analysis. 3. Append the six sections before rendering. 4. Name the signal choice and its outcome sensitivity. 5. Render, check visually, then send. 6. On revision, update the appendix in the same commit as the finding. An appendix describing a superseded method is worse than none.

## Quality bar

- [ ] Could a reader re-run this without asking me anything? - [ ] Is every headline number traceable to a pasted query? - [ ] Is the signal/threshold choice named, with alternatives and impact? - [ ] Are derived figures arithmetic over named constants? - [ ] Is the rebuild command present and correct? - [ ] Are drift, coverage gaps and retractions stated?

## Anti-patterns

- **Citation theater:** table names instead of runnable queries. - **Reconstructed SQL:** retyped from memory, drifted from what ran. - **Silent signal choice:** one column presented as "the score" when a defensible alternative changes the answer. - **Buried assumptions:** constants hard-coded in prose. - **Stale appendix:** findings revised, appendix untouched. - **Asking first:** this is a default, not an offer.
