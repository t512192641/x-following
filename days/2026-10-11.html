发之前也看一眼 Featured 范围，纯 Waitlist、目录、模板、课程、服务这类，现在通常进不了首页。

Linear 里几乎每个常用操作，都把快捷键写在你本来就会看到的提示框里。

看起来只是个小便利，实际上它更接近一套极其便宜的用户培训系统。不需要弹新手教程，不需要十分钟教学视频，只是在用户已经在看的地方多放了几个字符。

第一次你还是会点按钮，第二次可能顺手试一下快捷键，几周之后，你的手指比你的记忆更熟悉这个产品。

有意思的是它对切换成本的影响。大多数软件的学习成本停留在记忆层面，换一个工具，重新熟悉几天也就适应了。Linear 把其中一部分变成了肌肉记忆，那部分重建起来慢得多。

这套机制成立的前提，是 Linear 早就选好了用户。工程师每天泡在终端和编辑器里，Linear 接的是一个已经存在的习惯，不需要从零教育。Asana 或 Notion 明天也可以加同样多的快捷键，但收益会小很多，因为它们的用户里仍有很多人习惯点击。

**功能很少自己形成优势。功能和特定用户的既有习惯结合之后，才可能形成优势。**

所以更值得问的问题不是要不要加快捷键，而是产品里哪些操作正在变成习惯，以及那些习惯换到竞争对手那里还能不能用。

Alex Prompter @alex_prompter

Stop overcomplicating AI agents.

An agent is a loop:

1. Give the model a task and a list of tools 2. The model picks a tool 3. Your code runs it and sends the result back 4. Repeat until the model has an answer

Underneath the layers, agent frameworks follow that same basic loop.

Yet teams spend months comparing them before shipping a single agent.

Write the loop yourself with plain API calls, and a lot of the confusion clears up.

This summer, we built one for a PE-backed healthcare billing company. Whenever a client questioned a revenue report, an expert had to write SQL by hand against a legacy schema to find the answer.

Now they can ask those questions in plain English, and the agent finds the answers in their claims data.

Building the loop was straightforward. The actual work was in the evals: checking the agent’s answers against verified results from their claims data.

We built the answer key alongside the agent from day one. Their team gave us real questions and the SQL they’d write to answer them. We started with 10 questions, ran the full set every cycle, and kept adding more. By the first deployment, we had 60.

The agent answered 59 correctly. Its answer to the key question, “Which denials were preventable?”, reconciles to the penny with the database.

Six weeks in, their CPTO was testing it with real questions. When they challenged one answer, the agent acknowledged the mistake and corrected it.

That’s what you need to get right: the loop, a check on every output, and a set of real questions you run again after every change. RAG, MCP, and multi-agent setups come in when you have a specific problem for them to solve.

So pick one question your business still answers by hand. Build the loop with one tool. Put together 10 questions with answers your peo

We started running "pirate and architect" pods at Coinbase back in May of this year and I used this slide to talk the team through it. It works.

1 pirate, 1 architect, and a part-time designer.

It lets each archetype lean in to their superpower and get more shit done without all the coordination overhead and "what if-isms".

The pirate ships like mad, is product-minded and customer-obsessed. Always willing to throw-away code for a better version. The pirate is usually the DRI at the beginning too, working with customers, driving requirements, and a ship plan.

The architect makes sure stuff is built for scale, takes the pirate's prototype, and drives its scale-out through spec for agents.

The designer is building with both to constantly shape the experience and hill-climb to delight.

There's a helpful mental model that I like: -Make it possible. -Make it reliable. -Make it delightful (or efficient).

Previously, those 3 were done in a waterfall approach and was slow. Most people were just stuck on "make it possible."

With agents and a new way of working, you have every opportunity to parallelize them and go 100x faster.

How to build good evals without getting lost or in trouble.

You should see evals as saving past work and replaying it with new models or prompts/skills to see if it improved.

This helps you do 3 things: 1. see where it fails so you can tell your boss/users 2. optimize it until it improves 3. make it work on a cheaper / open source model

Measuring "if it improved" is 90% of the work and 10% is infra.

For infra just tell your agent to store tasks in Cloudflare R2 (a cheap/free way to store files in the cloud) in Harbor task format.

This means saving the instructions for the task and how the folder looked before you started the task (does the agent have all the files you had access to, in the state they were in?).

When you run a task your agent should pull down the files, run a docker container (a sandbox on your computer so your agent can't peek at the answer), and send the instructions. Ideally you copy across your auth credentials so you can use your codex/claude sub (otherwise it has to use expensive API tokens).

That's probably all the sophistication you need but one more cool thing you can do is mock any tools your agent might use i.e. if your agent usually reads slack channels or searches google or searches your documents you just need a way to fake it and send back something without touching the real services (otherwise it'll get something new every time you run it).

Ok onto the good stuff: measuring performance.

他做不了微观管理

Dwarkesh 说他以爱钻细节出名，他先开了个玩笑，「请叫纳米管理」，一路说到普朗克常数（0分14秒）。

他也会钻进某个具体问题，「因为这个具体问题正是公司进展的限制因素」，「不是随便去钻那些小事」。「但有时候，小事就是决定胜负的关键。」（1分10秒）

紧迫感和截止日期

被问到 SpaceX、Tesla 这么大了怎么还保得住紧迫感，他说「我有一种近乎疯狂的紧迫感」，「这种近乎疯狂的紧迫感会传导到公司的其他人身上」（2分41秒）。

截止日期他一般定在「我觉得至少有一半把握的位置」。「不是不可能完成的日期，而是我能想到的最激进、又有 50% 概率做到的日期。」「也就是说，有一半的时候会延期。」（3分13秒）

当然物理会设上限，扩大生产得「沿着产能曲线一步步爬上去」（3分58秒）。

接着他自己问了一句，「我说点什么对大家真正有用呢？」他的回答是「总的来说，近乎疯狂的紧迫感非常重要」，还有「你要定一个激进的排期，然后在任何时候都要搞清楚限制因素是什么，再帮团队把这个限制因素解决掉」（4分26秒）。

时间跟着限制因素走

4/ 它是一个超级节点，天然就有网络效应。
