我一直说 Claude 是我的剪辑外挂。但有个误区要先讲清楚：Claude 能“做”视频，不等于能“生成”视频。

Claude 做视频走的是 Video as Code 路线。它用 Remotion、HyperFrames 这类框架，把画面写成时间轴上的代码，排版、动效、转场、调色、字幕，都能精确到帧。它最强的是编排：给它一段 BGM，它能分析出 BPM 和鼓点，精准卡点。 但它画不出一个真实的人，也做不出一束流动的光、一次转身扬起的发丝。这种像素级的真实画面，还是得交给视频生成模型。

所以我以前的流程一直是割裂的：图在一个平台生成，视频去另一个平台跑，配音再换一家，提示词另开窗口写，最后把一堆文件拖回来交给 Claude 剪。Claude 的品味和编排能力再强，也只能在你喂给它的素材里发挥。

医疗软件 CTO 案例：保险入驻 agent 一字段错就停付——演示易、生产难

Alex Prompter @alex_prompter

A CTO at a healthcare software company asked us to build AI agents that enroll doctors with insurance companies, a job where one missed field means the doctor doesn't get paid.

The first thing they told me was why they were sceptical. "I could build an AI demo in about four seconds for any one of them," they said. "And then it would be completely useless in the product. It doesn't work even on the one payer."

They described the industry as complex. But no single task is hard, there are just a huge number of them, and every insurer, specialty and provider type wants something slightly different. Miss one and the claim bounces.

In the CTO's words, "This isn't compliance. Your providers either can't work or don't get paid. It's top line."

They also had a framework decision hanging over them, which tool to build the agents on, and whether to wait until they'd exposed everything properly to agents first. My answer was not to overthink it. The work that makes agents useful, the rules, the examples and the tests, moves with you whichever framework you pick.

We'd build inside the cloud they already run, and connecting through the systems they already have is enough to start.

I also wanted to know something else. They had a team doing these enrolments by hand every day. "Was there any record of how that team actually does the work?". Because that's where the real rules live, and the more of that variation you capture early, the less the agent has to guess.

The last thing the CTO said is the one I wish more buyers said out loud.

They didn't want to end up dependent on us. They wanted to walk out "with a team that's stronger" than the one they had before, as opposed to just being handed an application.

An agent that only works while the vendor is in the room doesn't do anything for the business long term.

yibie @yibie

在终端里用 Claude Code 画架构图，它只把 mermaid 源码原样贴给你，图要复制到别的 app 里才看得见。merman 是个 Claude Code 插件，把回复里的 mermaid 代码块直接画成彩色字符图，图跟着回答一起出现在屏幕上。

它不注册工具，也不走 MCP，Claude 从不会调用它。做法是一组 TypeScript 钩子，接在回复和屏幕之间，重画 Claude Code 本来要显示的那段 markdown。流程图、时序图、状态机都能画，ER 图和饼图也在。插件只碰回复，Claude Code 自己的界面不动，停用它，自带渲染立刻回来。

装：

claude plugin marketplace add iamrohithrnair/merman && claude plugin install merman@merman

要 2.1.311 以上。装完 /reload-plugins，/merman setup 选主题。17 套配色，/merman theme nord 当场换，/merman demo 看它能画什么。

图是字符画的，有边界。宽度超出窗口、或超过 80 行的图它不画，仍旧显示源码，大的时序图还是会退回别处看。C4 图目前不支持。

模型的账只有一笔：一条约 355 token 的说明，告诉它这个会话里可以放心画图，只加在第一条提示里，压缩掉之后补一次。把 diagramHints 关掉就一个 token 也不发。渲染这边，一条带六张图的完整回复首画中位 1.8 ms，重画 0.29 ms。插件 616 KB，没有网络请求，MIT。

我的判断：它的价值在迭代成本。改一支箭得把源码复制出去，切到别的 app 看一眼再回来重说一遍，一轮几分钟；它把这个循环压进同一条回复。图最终要拿给别人，还是得点 ▣ png 导出成图片。

合同里的「第 3 条例外」、技术文档里的「排障第 5 步」，这类信息必须连着上下文才有意义。一切成块，连续性就断了。而在术语密集的法律、金融、技术文档里，语义相近的词和答案真正写着的位置，经常不是同一个地方。

他介绍的开源项目 PageIndex（2026 年以来多次登上 GitHub Trending）把前提翻了过来：不做向量化，而是从文档的标题结构生成一棵可推理的目录树，让 LLM 像人翻长文档一样检索。

机制分四步。加载文档，抽出章、节、条的层级，变成一棵树。让 LLM 给每个节点写一句该节讲什么的摘要。提问时从根逐层下钻，每层让模型判断「要回答这个问题该读哪个子节点」。定位到末端小节后，取回正文生成答案。

1. 先看目录，猜问题大概在第 4 章。 2. 再看第 4 章的小节标题，继续往下缩。 3. 到末端小节，读正文作答。

副作用也实在：不用再搭和运维 embedding 数据库，索引重建、向量库版本管理、相似度阈值调整这些活都没了。

他拿一份约 80 页、4 级标题的内部业务手册实测。问「退货处理的例外条件」时，传统向量检索好几次命中了含相似词的其他小节；换成目录导航后，一次走对章节的概率明显提高。

但它不是万能的。聊天记录、纯要点笔记这类几乎没有标题结构的文本，根本没有可跟随的树，建目录没有收益。而且每次提问都要多调几次 LLM 来下钻，延迟和成本对实时场景要提前估算。

他第一次实现也失败过：只把标题文字丢给模型，碰到「第 3 章 运营」这种抽象标题，每个章节看起来都可疑，缩不下去。解法是给每个标题补 1–2 句「这一节具体处理什么、谁在什么时候该读」的摘要，并人工核对一遍。自动生成的摘要不能盲信，人工看这一遍反而是最省时间的一步。

小范围验证成本很低：挑一份标题清晰的文档，只抽标题做成层级列表，每个标题配一两句摘要，再准备 5–10 个常见问题，让模型只看目录回答「该打开哪个标题」，和正确章节对一下准确率。准确率低就回去改标题命名或摘要粒度。

客户端、前端和服务端的错误及崩溃都会统一收集到 Sentry，任何一端出现异常，都能及时发现。
