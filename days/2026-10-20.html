Oppo 心力球和 Anker 录音豆的区别

1、安克和飞书的产品经理，可能对录音这个事情有什么误解，他们觉得一天录半个小时就可以了。如果你是想收集全天上下文，就算开了他们那个会员，额度都不一定够你用

2、心力球的产品经理绝对是一个重度 AI 用户。这个产品续航长达 24 个小时，只要挂在身上，你就不用管了。它不留录音，会自动概括文本内容。然后你的所有的 Agent 都可以通过 MCP 获取这个内容，你的微信 Clawbot 也可以。所以虽然心力球 APP 里面内置了一个 Agent，但这个 APP 是不用打开的。通过微信、飞书、codex、claude code、grokbot 都可以访问

3、一天录音几个小时，一个月下来就是几百个小时。真要处理这么长的音频文件，对我来说成本极高，收益也不大。录音只是在高密度对话的时候有价值，那个时候用手机录音就可以了，我不太需要单独买个硬件。

4、对我来说，有价值的就是把每天大量的文字总结出来。让我知道我什么时间干了什么。我可以随口一句话告诉这个心力球：我喝咖啡了，我喝奶茶了，我喝酒了，我睡觉了，我醒了。就算你带了 Apple Watch，也不知道你今天下午 3 点吃了维生素。但是我可以一句话告诉心力球这个数据。

缺点：只能连接Oppo手机 优点：我恰好有个Oppo手机🤣

trim-1：Caveman 作者做的 1.2 MB 上下文剪枝小模型——给上下文加一句问题，只删 agent 用不上的行、不改写原文（删处留短标记）；712 棵梯度提升树，单核毫秒级、纯 Go 无 GPU 无网络；长文档检索用 balanced，编码 agent 工具输出省不了多少；不满足条件就原样返回

yibie @yibie

trim-1 是个 1.2 MB 的小模型，由大名鼎鼎 Cavman 的作者开发，它专门干一件事：给一段上下文加一句问题，它决定哪些行 agent 用得上，把用不上的删掉。

它跟"用模型总结上下文"反着走。摘要会把原文改成一段转述，标识符、路径、报错文本都可能变形；trim-1 只删行，返回的还是原文自己的行、原来的顺序，删掉的地方留一个短标记，一个字都不改写。

代价也小。712 棵梯度提升树，不是神经网络；单核毫秒级，不用 GPU、不发网络请求；纯 Go 标准库，模型嵌在里面。

用得对的地方和用不对的地方，README 自己说清楚了。长文档检索是它的主场，用 balanced。编码 agent 的工具输出又短又密，作者让你别期待太多——这种场景省不了多少。

它还有一条很值得学的设计：失败时不动。查询为空、上下文不到 2,000 字节、超过 8 MiB 或 20 万行、已经带标记、或者算下来删不掉 10% 的字节，它一律原样返回，并在 stderr 说明原因。

我的判断：上下文剪枝的单位应该是行，不是摘要。摘要等于二次改写，把"原文"这件事丢掉；而一行是被读完还是被删掉，是可以逐行判定的。另外，知道什么时候不该动，比总能剪更值钱。

用法一行：trim --query "why does the build fail" build.log > build.trimmed.log，--point 三档保守 / 平衡 / 激进，模型卡在 Hugging Face。

原文： https://github.com/caveman-ai/trim-1 #Agent #上下文工程 #小模型

dontbesilent @dontbesilent

我开源了 x-reply-guard，一个浏览器扩展，支持 Chrome、Arc 和 Edge。它用来识别 X 上的 AI 回复和 AI 推文，也可以一键隐藏或拉黑发布者

它有三个功能：

1️⃣识别评论区的 AI 自动回复。每条回复旁边显示 0–100 的 AI 分数，鼠标悬停能看到判断理由。自己推文下的回复会自动检测，别人推文下的回复要点按钮检测

2️⃣识别一个账号发的 AI 推文。在个人主页点按钮，插件会分析这个人自己发的推文，并显示高嫌疑推文的数量

3️⃣一键隐藏、一键拉黑。「隐藏」会静音发布者；「拉黑」会先隐藏这条回复，再屏蔽发布者

AI 识别需要你自己的 API Key，支持 DeepSeek、OpenAI、Claude、OpenRouter 和自定义的 OpenAI 兼容接口。Key 只保存在你的浏览器里，分析内容只发给你自己选的服务商

判断标准基于 dbskill 里的 /dbs-ai-check，可以在设置页修改

目前需要手动加载，安装方法见仓库 README。项目使用 MIT 协议

dontbesilent @dontbesilent

/dbs 升级到 3.0 之后超牛逼

因为解决问题常常可能需要调用多个 skill，而本地的 skill 有很多，有时候我也不知道该如何组合使用比较好

现在可以直接问 /dbs，它会给你推荐多个 skill，并且告诉你多个 skill 是按顺序使用还是并行使用

而且我本地可能还有正在开发中的 beta 版的 dbskill，它会自动识别到，一起调用

在调用之前还会向用户明确意图，进行 Skill 调用安排，还会告诉用户为什么要这样安排

我觉得真的解决了 Skill 数量膨胀的问题

dbskill 的复杂很大程度上源于做内容本身是一个复杂的事情

直接在 skill 层面上简化，就意味着我们要接近于「一键出爆款」，我觉得这个就走向做内容的反面了

所以现在的解决方案就是，做一个能调度 Skill 的 Skill（/dbs）

一方面不简化 Skill 本身，另外一方面降低大家使用难度
