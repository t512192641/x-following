医疗数据公司自建 AWS 上的 AI 代码审查平台：只建议不阻断，8 月以来主仓库审了 110 个 PR

Alex Prompter @alex_prompter

一家美国医疗数据公司请团队把技术负责人的代码审查负担接过来，并在客户自己的 AWS 账号里搭建受治理的 AI 基础设施。四个约束从第一天就定好：不能拖慢或阻断交付、源码和密钥不出 AWS 边界、AI 花费有上限。四个月后，客户自己运行这套平台，主产品仓库的每个 PR 先由 AI 审一轮。\n\n每条 PR 会拉起隔离的 AWS Fargate 任务，跑五段流水线：加载上下文、扫描、审查、门控、发布。确定性扫描（Semgrep、import 解析检查、已提交密钥检查）和 Bedrock 上的 Claude 并行；模型只读仓库，密钥路径被拒绝，对照关联工作项的验收标准看 diff。真正送到团队的评论由普通代码决定：diff 锚定、指纹去重、置信度规则、评论条数硬上限、出站密钥脱敏。它只建议、从不阻断合并，扫描或模型失败则 fail open。夜间任务把团队裁决喂回后续运行，无需重新训练；被驳回的评论会保持驳回。\n\n8 月以来主仓库：审查了 110 个 PR（最近合入 master 的 82 个里有 80 个）、首次评论中位 22 分钟、96 个可测 PR 里有 89 个先于人工评论、324 条评论中 53% 被团队解决、15% 被驳回。每次改提示词都先走离线测试套件和真实 PR 评测再上线。他们还在同一 AWS 账号里立了自己的 AI 平台：LiteLLM 网关转到 Bedrock、自建 Langfuse 做追踪、OpenTelemetry sidecar 剥掉敏感属性，只存用量和成本、不存提示词正文。客户自己的 DevOps 跟着部署并运维，背后有 65 份变更说明和完整 runbook。接入第二个仓库现在只需一个配置文件和一条流水线。下个月会在同一基础上试点「工作项变成带测试的 PR」，仍由人来合并。

内容格式会过时：50% 已验证、25% 改版、25% 全新实验

出海去孵化器 @chuhaiqu

出海去孵化器转述同一团队的两条 Instagram reel：播放差 5.8 倍，涨粉差 10 倍（1426 万播放、新增 3951 粉，对 247 万播放、新增 390 粉；分享 11 万对 2.7 万，数据来自做营销 agent Helena 的 Seijin Jung 团队）。格式本身差距大，也会老化：First Chair 靠一个房间 reel 系列 50 天从 3111 涨到 5 万粉，七月高峰后周播放掉一半，日增粉从 1500 回到 1000、后来接近 500；Ernesto Lopez 的菜谱轮播图账号 193 条 860 万播放，一月份停更账号也就停了。对付这件事，可以给内容定配比：50% 发已验证格式保住基本播放，25% 发这些格式的改版去赌变量，25% 发完全新的实验。这个配比来自 Matt Gittleson 做 CiteSure 时的用法。大多数账号只做第一个 50%，格式一死就什么都没有；比例最好在顺的时候定下来。再细一点，每周固定测表现最好的 3 个 hook、最差的 3 个 hook、一个格式变化、一个行动引导变化。
