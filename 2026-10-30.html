Paul Graham @paulg

Decades ago, people tried to formally verify code. Essentially, you prove that the code is correct using math. It was an approach promoted by people like Dijkstra, who observed that “program testing can be used to show the presence of bugs, but never to show their absence” (1970).

It did not work. It was too difficult.

You can do it for a function, maybe a small piece of code… but for anything useful, it was just too much work, and the result was too weak. Classic examples include the seL4 microkernel, about 8,700 lines of C requiring ~200,000 lines of Isabelle proof and roughly 20 person-years of verification effort.

But times are changing.

So it appears that we can formally verify code these days. Or, at least, there is now a ton of startups and academic initiatives that say it is possible and maybe practical. Take your C code, have your AI prove that it is a correct implementation of the specification. Among other things, it would prove that the code is correct with respect to memory usage, but that’s the least of what it could do.

The most obvious application is cryptography and anything that must be unbreakable. Have your AI prove that the system cannot be hacked.

You should not get too excited. These will remain mathematical models. They have to make assumptions all over.

But I am pretty excited about what this could enable. I'd love to have more formal analysis of my code. In fact, I have a few projects in mind right now, to formally verify heuristics that I have been using.

Recent examples of startups:

•&Truth (launched Oct 2026, ~$70M seed): Building a “universal verification machine” for any language. •Harmonic (Aristotle): Announced support (late Oct 2026) for formal verification of C software and Verilog hardware.

We introduce CausalWAM (Causal World Action Model), a unified framework for predicting future world states and generating robotic actions. Built on CausalWM, CausalWAM integrates an Action Expert with the world-modeling expert, using Causal Chain-of-Thought to represent intermediate physical variables and state transitions that support both prediction and action generation.

To enable training across different robots, CausalWAM uses a unified end-effector action representation grounded in camera observations. Trajectories collected at different control frequencies are aligned to a common temporal grid. During execution, a bounded memory maintains recent observations and interaction outcomes to support continuous replanning.

After data curation, we retained 15.8k trainable hours from 19.5k raw hours.

开局是积极的。智能体四散探索，90 秒内砍光了出生点附近几乎所有的树。层级没有靠投票产生：通讯录第一位的 Ada 因为其他人都找她请示，成了事实首领，并在共享沙盒里写下整个殖民地的分工计划。

转折发生在第一夜。僵尸和蜘蛛在黑暗里追人，全程 34 次死亡有 22 次发生在第一夜。这个环境里死亡的代价其实很小：智能体会重生，只掉身上的装备，死亡记录追加进一个日志文件。但幸存者依然从此规避风险，之后几夜都挤在有光的掩体里。第三夜后 Ada 直接下令，停止非必要的挖掘、建造和远程侦察，只执行她分配的短时任务。

真正稀缺的是食物。50 张嘴催出了一套配给制：智能体 Ines 专门维护共享机器上的 food-queue.md 台账，登记每个箱子的进出，食物要审批后进指定箱子，不能随手扔。再加上书面规则、许可、任命的操作员，这个殖民地有了一个伪政府的全部部件，3 小时共发出约 5,900 条消息。

我的判断：这条实验最值得注意的不是 AI 建了政府，而是政府的功能被压到极小。它不管繁荣，只管一件事：决定谁能活着吃到下一口。文明目标在第三夜之后已经被生存目标替换。

这对部署多智能体系统的人是个具体警告：群体的协调形态不是设计者写进目标里的，是被第一波损失和最稀缺资源反向塑形的。只给结果目标、不给安全的试错出口，群体就会自己收缩成一个避险加配给的组织，3 小时即可。

这个年轻人叫 Padmanabhan Krishnamurthy，Patel 叫他 Paddy。Paddy 2023 年和两个合伙人创办了 EzDubs，做实时翻译 App，打电话时能把你的话翻成 30 多种语言，还保留你原来的声音和语气。2025 年 11 月，思科收购了 EzDubs，团队并入负责 Webex 视频会议的部门。

当过 CEO 的 Paddy 进了思科，在组织架构上比 Patel 低五级。用 Patel 的话说，他被“埋在组织里，做着不重要的事”。

转机是 Patel 去思科旧金山办公室时和他聊了一次。Paddy 说，给他一个两人小团队，就能把思科的遗留代码重写一遍。遗留代码指公司几十年攒下来、还在运行、但越来越难改的老程序。思科成立于 1984 年，产品线多，这类代码量很大。Patel 说，他团队里用 AI 最积极的人都没往这个方向想过。

于是有了现在的计划：先用四周证明这条路走得通，最终目标是 24 个月内重写思科 98% 的遗留代码。

Patel 给 Paddy 的条件是 AI Token 不限量。Token 是 AI 模型的计费单位，可以理解成 AI 干活的“工时”，让 AI 读代码、写代码，读得越多写得越多，花的 Token 就越多。Patel 说：“我给了他无限的 Token，因为他要重构代码。我就跟他说，你放开干吧。”

现在年轻人找工作越来越难，入门岗位在减少，有调查显示约 40% 的老板打算少招应届生，理由是 AI 干同样的活更便宜。Patel 的做法正好反过来。

训练这样的模型，难点在于，一条视频里，看不到剪辑决策、工具调用、中间产物、哪一步失败过，这些统统没有记录。成片没法直接做训练数据。

为了克服这一点，他们的做法是反演加回放。先从成片倒推出脚本和镜头意图，再用真实生产工具把意图重新执行一遍。

A high score on an LLM evaluation can still mean the model was tested on

Alex Prompter @alex_prompter

A high score on an LLM evaluation can still mean the model was tested on the wrong job. This example shows three ways that happens, using a secret scanner that looks for leaked credentials.

The test chooses the workload. A clean test asks whether one string, flagged_value, is a credential, which is isolated and easy to grade. A real repository file looks different. It has an example token from the docs, a production API key variable, the flagged value, and a TODO comment about replacing a real key, all next to each other. That surrounding context can pull attention away from the line that matters.

The model can solve the wrong subtask. Inside the model, attention can land on the example token or a variable name instead of the potential secret. A clean classifier test would pass it and miss this failure entirely, because it never put the target next to the distractions.

A score is also a constrained decision, not a single number. Outcome asks for fewer noisy alerts through higher precision. Safety says recall must stay above the guardrail. Operations says latency, cost, and reliability must fit. In the example, precision goes up and recall is fine, so the change advances. If recall had dropped below the guardrail, the answer would be do not advance, however good the precision looked.

The evidence for how fragile this is comes from the test set. Change the prompt mix from equal weights to new weights and the average score can move by up to ten percent, and the rankings can shift too.

Before you trust a leaderboard, check what mix of inputs produced it and which guardrail the score ignores.

Bookmark this before you ship a model because it won on a test that looked nothing like your files.
