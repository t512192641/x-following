Linear 里几乎每个常用操作，都把快捷键写在你本来就会看到的提示框里。

看起来只是个小便利，实际上它更接近一套极其便宜的用户培训系统。不需要弹新手教程，不需要十分钟教学视频，只是在用户已经在看的地方多放了几个字符。

第一次你还是会点按钮，第二次可能顺手试一下快捷键，几周之后，你的手指比你的记忆更熟悉这个产品。

有意思的是它对切换成本的影响。大多数软件的学习成本停留在记忆层面，换一个工具，重新熟悉几天也就适应了。Linear 把其中一部分变成了肌肉记忆，那部分重建起来慢得多。

这套机制成立的前提，是 Linear 早就选好了用户。工程师每天泡在终端和编辑器里，Linear 接的是一个已经存在的习惯，不需要从零教育。Asana 或 Notion 明天也可以加同样多的快捷键，但收益会小很多，因为它们的用户里仍有很多人习惯点击。

**功能很少自己形成优势。功能和特定用户的既有习惯结合之后，才可能形成优势。**

所以更值得问的问题不是要不要加快捷键，而是产品里哪些操作正在变成习惯，以及那些习惯换到竞争对手那里还能不能用。

Alex Prompter @alex_prompter

Stop overcomplicating AI agents.

An agent is a loop:

1. Give the model a task and a list of tools 2. The model picks a tool 3. Your code runs it and sends the result back 4. Repeat until the model has an answer

Underneath the layers, agent frameworks follow that same basic loop.

Yet teams spend months comparing them before shipping a single agent.

Write the loop yourself with plain API calls, and a lot of the confusion clears up.

This summer, we built one for a PE-backed healthcare billing company. Whenever a client questioned a revenue report, an expert had to write SQL by hand against a legacy schema to find the answer.

Now they can ask those questions in plain English, and the agent finds the answers in their claims data.

Building the loop was straightforward. The actual work was in the evals: checking the agent’s answers against verified results from their claims data.

We built the answer key alongside the agent from day one. Their team gave us real questions and the SQL they’d write to answer them. We started with 10 questions, ran the full set every cycle, and kept adding more. By the first deployment, we had 60.

The agent answered 59 correctly. Its answer to the key question, “Which denials were preventable?”, reconciles to the penny with the database.

Six weeks in, their CPTO was testing it with real questions. When they challenged one answer, the agent acknowledged the mistake and corrected it.

That’s what you need to get right: the loop, a check on every output, and a set of real questions you run again after every change. RAG, MCP, and multi-agent setups come in when you have a specific problem for them to solve.

So pick one question your business still answers by hand. Build the loop with one tool. Put together 10 questions with answers your peo

Elon Musk 怎么管自己的时间，原话摘录

这支片子拼了两期播客里 Musk 讲时间管理的部分，配好了中英双语字幕。前两段来自 Dwarkesh Patel 和 John Collison 对他的长访谈，片尾彩蛋来自 Katie Miller 的节目，原视频链接在回复里。下面按片子顺序摘，引号里是中文字幕原话，括号里是这段话在这支片子里开始的时间。

他做不了微观管理

Dwarkesh 说他以爱钻细节出名，他先开了个玩笑，「请叫纳米管理」，一路说到普朗克常数（0分14秒）。

然后他认真回答。「因为我每天的时间是固定的，随着公司变大、管的事越来越多，我的时间必然会被摊薄。」真要做微观管理，「意味着我每天得有几千个小时」（0分42秒）。

他也会钻进某个具体问题，「因为这个具体问题正是公司进展的限制因素」，「不是随便去钻那些小事」。「但有时候，小事就是决定胜负的关键。」（1分10秒）

紧迫感和截止日期

被问到 SpaceX、Tesla 这么大了怎么还保得住紧迫感，他说「我有一种近乎疯狂的紧迫感」，「这种近乎疯狂的紧迫感会传导到公司的其他人身上」（2分41秒）。

截止日期他一般定在「我觉得至少有一半把握的位置」。「不是不可能完成的日期，而是我能想到的最激进、又有 50% 概率做到的日期。」「也就是说，有一半的时候会延期。」（3分13秒）

他说排期有一条「气体膨胀定律」。「如果你说这件事我们要五年做完，在我看来五年就跟无穷大差不多，它就会膨胀到把整个排期占满，真的花上五年。」（3分38秒）

当然物理会设上限，扩大生产得「沿着产能曲线一步步爬上去」（3分58秒）。

接着他自己问了一句，「我说点什么对大家真正有用呢？」他的回答是「总的来说，近乎疯狂的紧迫感非常重要」，还有「你要定一个激进的排期，然后在任何时候都要搞清楚限制因素是什么，再帮团队把这个限制因素解决掉」（4分26秒）。

每周的工程评审

「我每周都有非常细的工程评审。」他说不知道还有哪个管公司的人，至少在制造业公司里，会像他钻得这么细（5分27秒）。

他很信越级会议，技术评审上会让所有向他直接下属汇报的人都讲一讲，「而且不能提前准备」，不然听到的「全是吹捧」。做法就是在会上轮一圈，每个人都讲一下进展（6分00秒）。

会是每周一两次，每个人讲的都是一个快照。他在脑子里把这些点画到一条曲线上，「看我们是不是在收敛到一个方案」（6分38秒）。

「我只有在得出结论、认定成功已经不在可能的结果里时，才会采取激烈的行动。」（7分09秒）

时间跟着限制因素走

他跟 The Boring Company 没有固定的会，「一件事如果运转得好、进展顺利，我在上面花时间就没有意义」（8分25秒）。

「所以我其实是按照限制因素或问题在哪、哪里有麻烦来分配时间的。」（8分38秒）

「讽刺的是，他们就不怎么见得到我。但一件事要是进展不顺，我就会出现得很多。」（9分03秒）

成了限制因素的事，大多每周过一次，有些每周两次。AI5 芯片评审就是每周两次，每周二和周六都开（9分33秒）。

John Collison 说企业里的时间常常切成半小时甚至 15 分钟一个会，Musk 说他们的会「大多数会其实差不多都按时结束」。那天的 Starship 工程评审开得长了一点，因为「要想清楚怎么把每年送上轨道的量扩大到一百多万吨」（10分22秒）。

彩蛋，睡眠和上下文切换

「你平均每晚睡几个小时？」「六个小时。看我发的 X 就知道。」（11分07秒）

他试过睡不到六个小时，「虽然每天醒着的时间多了，我的认知能力却下降了」。他用手机 app 测过，自然睡眠大概是五个小时 56 分钟（11分22秒）。

「找我的信息特别多，所以要做信息分拣。」「我会尽量把一天分成几段，避免太多上下文切换，因为可以说，恐惧不是思维杀手，上下文切换才是。」（11分43秒）

要是每三秒、每 30 秒或者每三分钟就得切换一次，「上下文切换带来的认知代价会非常高」（12分05秒）。
