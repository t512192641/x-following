宝玉 @dotey

GitLab 六周内第三个满分漏洞：不用登录就能控制服务器，2014 年以来的自建版本都要升级

如果你们公司装了 GitLab，得赶紧升级了。10 月 21 日，GitLab 修复了一个满分 10 分的漏洞：在某些条件下，外人不用登录，就能在服务器上运行任意程序。2014 年的 7.0 版到现在，所有自建版本都受影响，10 月 12 日刚打过补丁的也在内。

这是 GitLab 六周里修的第三个满分漏洞，第一个已经被黑客用来攻击。

GitLab 是管代码的平台，很多公司把它装在自己的服务器上，全部源代码、部署用的密钥、自动打包上线的流程都在里面。服务器被人控制，对方就能翻看所有代码、取走密钥，或者悄悄改代码埋后门。

【六周里的三个满分漏洞】

9 月 10 日，GitLab 修了第一个：不用登录就能读取服务器上的任意文件。安全公司 watchTowr 和 Rapid7 发现有人在用它攻击，watchTowr 说可能泄露密码和密钥。美国网络安全机构 CISA 第二天把它列为“已被利用”，要求联邦机构三天内修好。

后两个满分漏洞都出在正则表达式引擎里。正则表达式是描述文本规律的公式，比如“找出所有 11 位手机号”，GitLab 用 Ruby 语言自带的引擎把这种公式翻译成程序。

研究者 joaxcar 一个月里在这个引擎上找出四个能远程运行程序的漏洞：9 月 23 日修了两个，要先登录，9.9 分；10 月 12 日修了一个，不用登录，10 分；第四个就是这次的，也是 10 分。

前三个只影响 19.2 以后的版本。这次的问题是翻译公式时有个数字超出上限，像里程表跑满一样归零（整数溢出），攻击者能借这个错位把自己的指令塞进服务器。GitLab 每个版本都带着这个引擎，所以十二年的版本都跑不掉。10 月 12 日补到的 19.2.8、19.3.5、19.4.2 也照样中招。

【我要不要管，升到哪个版本】

用 https://GitLab.com 网站的不用管，官方说已经修好；GitLab 代管的专属版 GitLab Dedicated 也已修复。要动手的是自己装 GitLab 的公司和个人。

19.5 升到 19.5.1，19.4 升到 19.4.3，19.3 升到 19.3.6，19.2 升到 19.2.9，19.1 升到 19.1.9，19.0 升到 19.0.10。18.11 及更老的版本，统一升到 18.11.13。

GitLab 平时只给最近三个月度版本打补丁，这次破例多补了四条老版本线。版本很老的不能一步跳到 18.11.13，要按规定经过几个中间版本，官方工具能算出要停哪几站： https://gitlab-com.gitlab.io/support/toolbox/upgrade-path/

19.4.3 和 19.3.6 升级时要改数据库，只有一台服务器的会停机一段时间。多台服务器的可以按官方的零停机流程升级。

【这次的被利用了吗】

GitLab 公告没提。The Hacker News 报道说，GitLab 表示没发现被用于攻击的迹象。CISA 10 月 21 日更新的“已被利用漏洞”目录里也没有它。

“某些条件”具体是什么，官方没说，管理员没法靠检查配置排除自己。官方也没给临时缓解办法，升级是唯一确定有效的做法。GitLab 另外发了两条检测规则，管理员可以用来翻日志，看有没有人试过攻击。

静态逆了一遍 Claude，发现100台Mac Mini都救不了的八大天坑：

1. 手机插国区 SIM 卡：Sift 会记录下来，和出口 IP 国家对不上，直接完蛋

2. 清 App 数据换新号：基本没用，Sift 的 installation_id 就是 ANDROID_ID，硬件级绑定，服务端仍能判断

3. CLI 多账号共用 ~/.claude.json：device_id 不变、account_uuid 变，赤裸裸的一机多号

4. 桌面切号只换账号不换 userData：ant-did 特征会跟着，如果整包复制到新机等于把识别信息原样搬过去

5. 只给 https://claude.ai/ 配住宅IP：Sentry / Datadog / Sift / Segment 走机场，同一账号两条 IP 轨迹

6. 注册/支付/KYC：Turnstile、hCaptcha、Stripe 3DS、Persona 都会看提交那一刻的 IP

7. 已被限制的情况下换着 IP 反复请求：每请求一次，风控分数继续叠加

HiTw93：在 Mac 上开发原生 Windows 软件（Mole Windows 版一个月 8 万多行、4000 多个测试）

Tw93 @HiTw93

书接上回，接着聊昨晚聊的多端技术选型，今天我们来聊第二篇，说说我是怎么在 Mac 上来开发原生 Windows 软件的，以及我是如何搭建编译、测试环境的，还有最近一个月做 Mole Windows 版踩过的一些有意思的坑。

技术栈上，Mac 版本的 Mole 使用的也是原生的 Swift + SwiftUI，能够让我很好调用系统能力以及非常好的性能体验，想着不将就，所以在 Windows 上我也是想着直接用本身写 Windows 软件最直接的语言， C# 加 WinUI 3，跑在 .NET 10 上，过程虽然难搞，但是相比十年前我了解轮子哥谈的 Windows 开发要简单好理解一些了。

Windows 上的原生界面框架其实挺多的，包括很多年前了解过的 Win32、WinForms、WPF、UWP 这一波，WPF 是 2006 年出的，到现在还在维护，但控件和设计语言不是很好看，非常上一代的感觉，然后 UWP 又被沙盒和应用商店给绑定住，现在微软主推的是 Windows App SDK 里的 WinUI 3，界面框架从系统里面拆出来单独发版，这样就有一个好处，普通的 Win32 程序也能用，基础组件就是 Windows 11 自己的 Fluent 风格，我还挺喜欢，高分屏缩放和 ARM64 都是原生支持。

然后这里 .NET 10 是去年 11 月发的长期支持版本，打包时我把运行时一起打进去，用户不需要另外装 .NET，x64 和 ARM64 这里各出了一个原生安装包，骁龙的 Windows 笔记本就不要走转译了，相当于尽量让用户使用简单不折腾。这里安装和更新用的是开源的 Velopack 框架，可以很方便做增量更新，也很好用。

工程师开始写代码时候肯定会想到能复用尽量复用，所以我开始写的时候也非常想复用 Mac 的 Swift 代码，后面让 AI 分析了一下，十几万行代码 Swift 代码可以脱离 AppKit、SwiftUI 这些系统框架使用的20%都没有，处理的逻辑也是 ~/Library 这类 macOS自己的路径规则，基本用不上，所以 Windows 版几乎是从零开始写的。

两边的关系其实非常简单，外观和交互我尽量完全一致，尽可能让大家意识里面认为的 Windows 软件不那么精致美观的感觉在这里也保持我认为好的水平，然后底层代码各写各的，关于视觉的一致性还原有了AI以后很简单，我把原本的 Mac 版写在 Swift 里的颜色、字号、间距、圆角这些设计 token，直接写了一个脚本生成为 Windows 里面XAML 资源，文案也是从 Mac 的多语言文件转成 Windows 的格式，11 种语言一起转过来，甚至大家看到的菜单栏里面的那个runner动画也是用的同一个脚本同步来的。

虽说同步，可能大家会觉得很简单，其实这里需要花点精力防止 AI 直接给你跑偏了，每次同步其实我会记录对应的是Mac的哪一个提交，这样两边就不会走偏去，然后功能上会有一份 SYNC.md 当做对账表，Mac 每加一个功能、修一个安全问题，Windows 这边都会标清楚哪些是已经实现、哪些是刻意不同还是不适用，以及为什么这样判断。

通过这两个机制，我可以很好的让两边的底层完全各写各的，但是又能很好地保持功能对齐，完全不需要刻意去硬写一层兼容去磨平，反而会变复杂，这里能复用的反而是设计、文案以及踩坑后定下来的各种规则，反而这些是 AI 非常喜欢的“能力抽象层”，也就是说随着时代发展，慢慢所谓的代码抽象没有那么重要了，反而是规则抽象更重要。

另外 Windows 开发还有一块比 Mac 要麻烦不少，就是证书签名，没有签名的，一打开会出现「Windows已保护你的电脑」，甚至 Windows 11 的智能应用控制会直接不让运行，国内不少安全软件也会把没签名的程序当成可疑报毒，这和 Mac 上没签名、没公证的软件提示「已损坏」差不多，平时 Mac 上大家还可以跑一条命令解掉，Windows 上想正规分发，这一步没有啥好办法，就是需要。

调研下来微软的签名生态的确比苹果差太多了，微软有自己的 Azure Artifact Signing，一个月 9.99 美元最省事，居然个人只开放给美国和加拿大的开发者，没办法使用，很奇葩的规定，然后行业还规定从 2023 年起签名私钥必须放在硬件或者云端 HSM 里，不能再是电脑上的一个文件，今年起单张证书最长只能用 460 天，差不多一年多就得换一次证书

最后我买的是 Certum 的云端 OV 证书，3 年 3百多美元，签名时登录电脑上的 SimplySign，再用手机上的 App 给一个动态码，SmartScreen 的信誉也跟着证书上审核过的名字慢慢积累。刚开始一段时间的签名包在 ThinkPad 上也会一样被 SmartScreen 拦了下来，后来我每次发版都把安装包提交到微软的恶意软件分析门户，让信誉慢慢积累起来，而且 SimplySign 的登录会话闲置几个小时就会断开，需要再次输入动态码才能继续签名，所以这里其实很难做成云端自动打包。

证书搞定后，就是开发环境的事情了，我的研发要求是代码和 AI 的上下文必须全留在 Mac 上，Mac 用习惯了，真的很难使用 Windows 去研发，这里 Windows 只负责编译和验证效果和各种测试，所以我在 Mac 上装了 Parallels Desktop，大概 3 百多块一年，之前也挺不少小伙伴吐槽过这个软件，不过在我的 M5 Pro 上跑 Windows 11 还挺顺滑，让我感觉这个钱花得很值。

它最好用的一点是我的 Claude 能很顺手地操作它，仓库直接作为 Parallels 的共享文件夹挂进虚拟机，变成一个 X 盘，Mac 上改完代码，虚拟机里直接编译，不需要来回 Copy 文件，只是两边的编译产物要分到不同的目录，对于编译、启动、看日志的工作都被我写成了脚本，通过 Parallels 自带的 prlctl exec 直接在虚拟机里执行，程序启动就崩的时候 Windows 只给一个 0xc000027b，Mole 会把真正的异常写进日志，脚本跑完顺手打印出来，Claude 直接就能读到。相当于写代码还是在 Mac 上的 Claude Code 里，调试和运行都在虚拟机里，脚本不能解决的地方，直接用 Codex 的 computer use 去点，只有少部分那种系统确定弹框点不了，我在这里就是这个职责，点点系统弹框确定，哈哈。

说到这里，可以和大伙分享一下 Mole Windows的架构分层，一共四层，最底下的 Core 只依赖 .NET，不碰任何 Windows 接口，清理规则、路径安全检查、卸载残留的判断都放到这里，测试用的是一个按 Windows 路径规则模拟出来的内存文件系统，这样在 Mac 上也可以很好的跑；往上是 Platform 层，注册表、文件系统、Win32 调用这些真正的系统接口都放在这一层，打开 EnableWindowsTargeting 以后，Mac 上也能编译通过；再往上就是写过应用同学非常熟悉的界面状态的 ViewModel 层，这里和 Mac 版本会一一对应，这样也能够在 Mac 上测，只有最上面这一层的 WinUI 界面必须去 Windows 里编译。
