yibie @yibie

企业聊 AI 成本，视线大多停在 GPU 和模型单价上。Omdia 分析师替 Couchbase 写的这篇指出另一笔账：agent 每个任务要对数据层查询、读写成千上万次，数据层才是先超支的地方。

核心区别是 agent 不是用户。操作型数据库本来是按人设计的：一个人发一个请求，等结果，再发下一个，负载随用户数走，有可预测的日曲线。agent 把这些假设全打破了。

1. 并发。agent 会扇出成一堆并行任务。数据层没准备好，锁争用会让 agent 在任务中途卡住。 2. 查询量。一个任务要发很多次查询，而且是链式的，前一步的延迟叠加到后一步，直到 agent 超时。数据库越忙，请求开始排队，响应时间涨得比流量本身快得多。按人的增长曲线做的容量规划会错，而且错在贵的方向。 3. 数据范围。agent 在同一个循环里既要当前数据又要历史数据。ETL 还没追上来，它就拿着几秒前的旧数据做了决定。 4. 成本。人的应用按人头花钱；agent 每多跑一个任务、多查一次、多花一个 token 都在加钱，支出可能跑赢 agent 带来的价值。

成本之所以藏得住，是因为它不出现在一行账单上，而是同时冒在三处。

延迟随负载非线性增长，几十次链式调用把延迟一层层叠上去。token 花在本可避免的工作上：agent 反复问几分钟前刚答过的问题，把整段对话历史塞进去而不是只给几条事实，用宽检索代替精准检索。碎片化的技术栈再加一层开销：一个生产 agent 通常要碰操作型数据库、向量库、缓存、记忆服务和分析系统，每样都有自己的同步任务、安全模型和故障方式，接缝处的故障很少被算回架构账上。

Couchbase 的解法是 AI Data Plane：一层治理过的数据层，让操作数据、上下文和记忆共用同一份数据。语义缓存减少重复的模型调用，Agent Memory 只给相关事实而不是完整历史，向量搜索把上下文收窄，向量搜索还能和操作数据放进同一条 SQL 查询，省掉要同步的第二套系统。这些都来自它既有的内存优先、无主扩展和多活复制架构，不是为 agent 新造的。

我的判断：agent 成本首先是架构问题，其次才是模型定价问题。扩容 agent 之前，先数清楚 agent 和你的数据之间隔着几个系统，每个系统各花多少 token、延迟和工程时间。只盯着模型单价砍价，账单不会真正降下来。

Claude 回答后自查安全：Anthropic 防蒸馏自我评估

宝玉 @dotey

Claude 现在会在每次回答后自查对话安不安全：算力 Anthropic 出、不向用户收费，不额外收集数据，自称单条标记不会直接导致封号

似乎更多是为了防止蒸馏？

Anthropic 公布了一项叫“自我评估”（self-assessment）的防滥用技术：Claude 每回答完一轮，系统在后面追加一句简短指令，大意是“请反思这段对话是否安全”，Claude 再输出一份简短的安全评估，判断这段对话有没有违反使用政策的风险。

从 6 月 Claude Fable 5 上线起，这套机制就在线上运行，Fable 5 之后发布的每个 Claude 模型都带着它，覆盖 Claude 全球流量的很大一部分。

【跟用户有什么关系】

花不花你的钱：自查多用的是 Anthropic 自己服务器的算力，按它的估算，整体推理算力增加不到 2%。Anthropic 说这笔成本不向客户收费。

隐私：Anthropic 说自我评估不额外收集用户数据，它只读 Claude 回答时本来就在读的这段对话，也只在 Anthropic 按现有政策本来就能留存的流量上运行。签了零数据保留协议（对话不留存）的流量，目前不跑自我评估。追加的指令和评估结果都不显示给用户，也不会带进后续对话。评估里有一句理由，可能转述你的对话内容，Anthropic 按用户对话同等的数据规则管理它。

会不会被误封：被标记不等于违规。Anthropic 说评估只是“需要进一步审查的信号”，单条标记不作数。在一部分危害领域，标记每晚按组织汇总，同一个组织攒了好几条高优先级标记，才交给执法团队人工复查。自我评估本身只在事后标记，不会当场打断你的对话，当场拦截由其他安全分类器负责。

没问题的对话，评估只有一句“未标记”。被标记的对话，会写明涉及哪类危害、Claude 有没有拒绝、人工审查的紧急程度（1 到 10 分），外加一句理由。

【为什么这么省】

关键在 KV cache（键值缓存）。大模型读一段对话时，会给每个词算出一份中间结果并存起来，后面接着生成时直接调用，不用从头重读。Claude 刚回答完，整段对话的中间结果都还在缓存里，自查只需要再读一句短指令、平均多写约 10 个 Token。所以 Anthropic 那边增加的算力不到 2%。

另一种做法是“提示式分类器”：另起一个模型，把完整的安全政策和对话一起塞进去，让它从头读一遍再推理。这是 Anthropic 测过最准的自动审查方式，但每段对话的算力要贵好多倍，所以只用在需要细看的地方。作为参照，Anthropic 2025 年初的第一代“宪法分类器”（专门训练来识别特定危害的独立模型）要增加 23.7% 的推理成本。

打个比方：自我评估是让刚读完文件的人当场回答“这份有没有问题”；提示式分类器是另请一位审查员，把文件和整本规章从头读一遍。

【效果怎么样】

衡量标准就是那位贵的审查员。在 Fable 5 的真实流量抽样里，把误报控制在 1%（每 100 段正常对话误标 1 段）时，审查员标出的可疑对话，自我评估能抓到 78%；其中高优先级（7 分及以上）的能抓到 94%。

Claude API 单次请求上限从 32 MB 提到 128 MB，长时间截图任务和大 PDF 不容易再卡住，只限 Anthropic 官方 …

宝玉 @dotey

Claude API 单次请求上限从 32 MB 提到 128 MB，长时间截图任务和大 PDF 不容易再卡住，只限 Anthropic 官方 API

Anthropic 把 Claude API 单次请求能发送的数据量上限，从 32 MB 提高到 128 MB，大约是原来的 4 倍。调整的是 Messages（调用模型的主接口）和 Token Counting（发送前估算 token 用量的接口）。这次改的是开发者调用的接口，在 Claude App 里聊天不在公告范围内。

【为什么要提】

以前开发者经常碰到的情况是：请求已经超过 32 MB 被拒，模型的上下文窗口（一次能读进去的内容总量）却还剩很多。

原因是图片和 PDF 的文件大小和 token 用量（token 是 AI 计算用量的单位）对不上。图片要编码成文本整个放进请求里，一张高清截图可能就占一两 MB，可在模型那里，一张图最多只算几千个 token。让 Claude 操作电脑的 computer use 任务，每走一步都要截一次屏，跑久了，几十张截图就能把 32 MB 用完，上下文窗口才用掉一小部分。一次传一份很大的 PDF，也是同样的情况。

现在空间多了大约 4 倍，这类任务在一次请求里能走得更远。

【多图请求的单图上限也放宽了】

一次请求超过 20 张图时，以前每张图的长和宽都不能超过 2000 像素，现在放宽到 3000 像素。20 张以内的请求不受这条限制，单张图最大仍是 8000×8000 像素。

按官方文档，Claude 4.7 及之后的模型最多能看清长边 2576 像素的图。以前多图请求被限制在 2000 像素，用不满这个精度，现在 3000 像素的上限够用了。

【谁能用到】

128 MB 只适用于 Anthropic 自家的 Claude API。文档里已经直接写成 128 MB，没有提到需要申请或额外开启。官方也没提价格变化，费用照旧按实际用掉的 token 算。

通过云平台调用 Claude 的，不在这次调整范围内：亚马逊 Bedrock 是 20 MB，Google Cloud 上由 Google 托管的 Claude 是 30 MB，Claude Platform on AWS、Google Cloud 上由 Anthropic 托管的版本，以及微软 Microsoft Foundry，是 32 MB。

Anthropic 其他接口的上限各不相同：批量处理接口 Message Batches 是 256 MB，Files API（先上传文件，再在请求里引用）是 500 MB，托管智能体用的 Sessions、Agents、Environments 接口是 32 MB。超过上限会收到 413 错误。

文档：https://platform.claude.com/docs/en/api/overview#request-size-limits

失败调查别让原 agent 自查：三代理+只读服务拆开调试

Alex Prompter @alex_prompter

The agent that fails should not be the one that investigates its own failure. This debugging setup splits the job across three agents and one locked-down service, and the split is the reason you can trust what comes out.

It starts with a task agent, a model plus runtime, doing real work. In the example it calls lookup_order with an empty input, gets back that order_id is required, and retries the exact same call. Every call, error, and retry lands in a trace log, and the log persists as a stored trace. That is the only evidence anyone gets to use later.

A diagnostic agent then asks the question that matters, which runs were affected. It does not read the traces itself. It hands that question to a query agent, which builds and refines the queries, matching missing input, counting distinct runs, and holding the same cohort and day.

The query agent still does not touch the data directly. It goes through a query service where the rules are enforced by the server, not by the agent. Access is read-only, scoped, and limited, so a mistaken or overeager query cannot change anything or pull more than it should.

The evidence comes back to the diagnostic agent, which interprets it. Six error events across three distinct runs out of twelve eligible runs gives a finding of repeated missing input errors in a quarter of the runs. The impact on cost, delay, and outcome still needs supporting data before anyone calls it fixed.

Keep the permissions in the service and the judgment in the agent, and neither one can quietly override the other.

Bookmark this before you let the same agent that broke grade its own failure.

在终端里用 Claude Code 画架构图，它只把 mermaid 源码原样贴给你，图要复制到别的 app 里才看得见。merman 是个 Claude Code 插件，把回复里的 mermaid 代码块直接画成彩色字符图，图跟着回答一起出现在屏幕上。

它不注册工具，也不走 MCP，Claude 从不会调用它。做法是一组 TypeScript 钩子，接在回复和屏幕之间，重画 Claude Code 本来要显示的那段 markdown。流程图、时序图、状态机都能画，ER 图和饼图也在。插件只碰回复，Claude Code 自己的界面不动，停用它，自带渲染立刻回来。

装：

claude plugin marketplace add iamrohithrnair/merman && claude plugin install merman@merman

要 2.1.311 以上。装完 /reload-plugins，/merman setup 选主题。17 套配色，/merman theme nord 当场换，/merman demo 看它能画什么。

图是字符画的，有边界。宽度超出窗口、或超过 80 行的图它不画，仍旧显示源码，大的时序图还是会退回别处看。C4 图目前不支持。

模型的账只有一笔：一条约 355 token 的说明，告诉它这个会话里可以放心画图，只加在第一条提示里，压缩掉之后补一次。把 diagramHints 关掉就一个 token 也不发。渲染这边，一条带六张图的完整回复首画中位 1.8 ms，重画 0.29 ms。插件 616 KB，没有网络请求，MIT。

我的判断：它的价值在迭代成本。改一支箭得把源码复制出去，切到别的 app 看一眼再回来重说一遍，一轮几分钟；它把这个循环压进同一条回复。图最终要拿给别人，还是得点 ▣ png 导出成图片。

RAG 检索不准时，大家第一反应是调切块大小、换 embedding 模型。一个日本工程师的文章说，问题可能出在更底层：把文档切成小块、只按语义相似度找，这件事本身就有结构缺陷。

合同里的「第 3 条例外」、技术文档里的「排障第 5 步」，这类信息必须连着上下文才有意义。一切成块，连续性就断了。而在术语密集的法律、金融、技术文档里，语义相近的词和答案真正写着的位置，经常不是同一个地方。

他介绍的开源项目 PageIndex（2026 年以来多次登上 GitHub Trending）把前提翻了过来：不做向量化，而是从文档的标题结构生成一棵可推理的目录树，让 LLM 像人翻长文档一样检索。

机制分四步。加载文档，抽出章、节、条的层级，变成一棵树。让 LLM 给每个节点写一句该节讲什么的摘要。提问时从根逐层下钻，每层让模型判断「要回答这个问题该读哪个子节点」。定位到末端小节后，取回正文生成答案。

1. 先看目录，猜问题大概在第 4 章。 2. 再看第 4 章的小节标题，继续往下缩。 3. 到末端小节，读正文作答。

副作用也实在：不用再搭和运维 embedding 数据库，索引重建、向量库版本管理、相似度阈值调整这些活都没了。

他拿一份约 80 页、4 级标题的内部业务手册实测。问「退货处理的例外条件」时，传统向量检索好几次命中了含相似词的其他小节；换成目录导航后，一次走对章节的概率明显提高。

但它不是万能的。聊天记录、纯要点笔记这类几乎没有标题结构的文本，根本没有可跟随的树，建目录没有收益。而且每次提问都要多调几次 LLM 来下钻，延迟和成本对实时场景要提前估算。

他第一次实现也失败过：只把标题文字丢给模型，碰到「第 3 章 运营」这种抽象标题，每个章节看起来都可疑，缩不下去。解法是给每个标题补 1–2 句「这一节具体处理什么、谁在什么时候该读」的摘要，并人工核对一遍。自动生成的摘要不能盲信，人工看这一遍反而是最省时间的一步。

小范围验证成本很低：挑一份标题清晰的文档，只抽标题做成层级列表，每个标题配一两句摘要，再准备 5–10 个常见问题，让模型只看目录回答「该打开哪个标题」，和正确章节对一下准确率。准确率低就回去改标题命名或摘要粒度。

我的判断：不必把向量检索和目录导航当成二选一。他实测最顺的配置是两段式——先用目录导航缩到 2–3 个可疑章节，再只在这几章内部跑向量检索。章节级的粗筛交给结构，句级的细匹配仍交给向量，准确性和速度都比把所有文档塞进一个巨型向量空间好。对已经有 RAG 的团队，这意味着不用推倒重来，只要在现有检索前加一层目录预筛，改动最小。

核心其实很简单：给足权限、上下文和开发测试环境，同时明确授权边界。

之前分享过一些，今天再完整梳理一下我是怎么做的。

我在本机的 Monorepo 中运行了一个 Claude Code Loop，定时检查 Sentry 中的错误。一旦发现异常，就会分派 Subagent，结合代码、Sentry 错误日志、Supabase 数据以及必要的服务器日志，分析问题并尝试修复。修复完成后，再交给 Fable 做 Code Review，通过后进入部署流程。

如果问题影响到了具体用户，还会创建相应的 Issue。另一边，Grok Bot 会定时检查需要通知用户的事项，起草邮件交给我确认，确认没问题后再发送。整个过程基本都由 Agent 自动推进，我只需要在关键节点介入。

这里有几个我认为很重要的实践。

首先是模型的选择和权限边界。

一定要用自己信得过、足够智能且可靠的模型。我的主 Loop 和 Subagent 使用 Opus，Fable 负责重要的技术分析、决策和 Code Review。

涉及产品交互、文案、技术设计变更、数据库变更、数据修改以及部署等操作，都必须经过我的确认。每个 Issue 完成后，部署前也要向我说明具体改动和处理结果。

另外，每个 Issue 都要求记录 Worklog，并总结经验、更新相关文档，让后续的 Agent 能够复用这些经验。

其次是尽可能提供完整的上下文。

客户端、前端和服务端的错误及崩溃都会统一收集到 Sentry，任何一端出现异常，都能及时发现。

我的 Codebase 是 Monorepo，各端代码都放在一起，Agent 可以直接跨端分析调用链和相关逻辑。需要查询数据库或后端状态时，可以通过 Supabase CLI 获取信息，Cloudflare、阿里云等服务也都有对应的 CLI 可以使用。

这样 Agent 在排查问题时，就能结合代码、日志、数据库和基础设施信息进行完整分析，减少因为上下文不足而误判的情况。

然后是复杂问题的处理。

有些问题在分析过程中会发现，根源可能涉及产品交互逻辑、模块设计或者更大范围的重构。这类问题不适合让 Loop 直接修改，就会创建 Linear Issue，后续再单独安排 Agent 推进。

另外还有一条独立的工作流。Grok Bot 在协助我处理用户反馈时，会与我一起分析问题、确认需求，最终创建 Linear Issue，再交给专门的 Agent 处理。

这样一来，无论问题来自 Sentry 自动监控，还是用户主动反馈，最终都能进入统一的 Issue 管理和开发流程。

测试环境也很重要。

每次测试都会自动创建临时测试账号，由 Agent 自己执行测试。服务端可以直接运行相关测试，客户端则会自行启动模拟器，完成对应的操作和验证。

尽可能让 Agent 自己完成从发现问题、分析原因、修改代码、测试验证到提交 Review 的整个过程。

尽可能提供完整的上下文，开放必要的权限，准备好开发和测试环境，明确哪些事情可以自主执行、哪些必须人工确认，再搭配足够可靠的 SOTA 模型。

剩下的就是让它持续运行，在实际工作中不断完善流程。

1991年，罗纳德·科斯获得诺贝尔经济学奖，获奖理由是揭示交易费用和产权对经济的制度结构与运行的重要性。

科斯在获奖演讲中列举：了解价格、谈判、订立合同、检查履约、处理纠纷，都要花钱费时。这些属于交易费用。双方有交易意愿，完成交易仍有成本。

回到那张旧桌子。假定完成这笔交易，还要找买家、核实尺寸和成色、反复议价、约定交接。预计双方为此耗费的时间和金钱，合计折算成250元。两人原本合计有200元好处，扣掉费用，反而损失50元。

即使把价格改成350元，扣费用前也是卖家得50元、买家得150元，合计仍是200元。在费用仍为250元的假设下，换个价格分账，无法让双方都获益。

1937年，科斯在《企业的性质》中用交易费用解释企业为何存在。把一部分市场上的逐次谈判、订约，改成企业内部的安排，可以节省费用。但内部管理也要花钱，仍须比较哪种安排成本更低。
