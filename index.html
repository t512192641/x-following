日常让 Agent 堆业务代码，很多人踩过的最大一个坑：

上下文塞得太满，Agent 开始“脑补默契”。

写到第十轮，模型以为自己什么都懂，架构漏洞全被历史对话掩盖过去； 一换新会话或者真正跑测试，全线崩盘。

Google 开源的这个 Elephant-Goldfish Model 插件，思路非常接地气，直戳多 Agent 协作的痛点。

它把这个过程暴力拆成了两个极端角色：

大象（Elephant）：长记忆。吃下你所有的业务背景、历史需求和全局代码，专门负责输出一份详尽的技术规格（Spec）。

金鱼（Goldfish）：零上下文。完全不带任何历史包袱，拿到的只有刚才那份 Spec，直接以“白盒新手”的视角去硬碰硬压测这份规格。

很多时候不是模型写不出代码，而是 Spec 根本没闭环： - 是不是默认漏了环境变量？ - 接口边界有没有漏写兜底类型？ - 离开当前这个 prompt 堆出来的语境，这份 Spec 到底能不能独立跑通？

今天拆一个模型，CPA。很多人听过这个词但不一定真正理解它背后的逻辑。

CPA，Cost Per Action，按行动付费。用户完成了一个指定动作，推广者就能拿到一笔收益。

这个模型为什么存在？你从平台的角度想就明白了。

一个网盘平台要发展用户，有两个选择：一是自己花钱投广告，二是让别人帮它推广，按效果付费。

自己投广告，成本不可控。投了可能有效果，可能没效果，钱花了就花了。你看不少平台砸了几千万广告费，转化出来的活跃用户少得可怜。

但如果让别人帮推广、按效果付费，就不一样了。只有用户真的来了、真的注册了、真的用了，平台才付钱。这对平台来说是零风险的获客方式。

所以CPA的本质就是平台把获客成本直接分给帮它获客的人。

这意味着什么？意味着你赚到的钱是平台获客预算的一部分。这笔钱平台不给你，也要花在广告上。给你反而更划算，因为效果可控、成本透明。
