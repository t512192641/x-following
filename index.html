GPT-6 Intelligent UI 怎么做的：原生可流式组件库（模型只挑组件、怎么拼）+ 界面编译器（边生成边渲染），训练时按清晰度、有用性、完整性给界面打分

M. @wlzh

GPT-6 开始全面推送了，覆盖"每周超过 12 亿"的 ChatGPT 用户。这次真正的看点不是模型变强了多少，是一个叫 Intelligent UI 的东西：回答不再只是一堆字，可以直接带出图形、按钮、表单、图表，甚至现成的交互工具。

逻辑很简单粗暴。问对比类问题，给你并排呈现；问原理类，给交互式图解；问简单的，还是纯文本。一句话：什么问题配什么形式。

技术上分两层，都在解决过去生成式 UI 的硬伤。第一层是原生可流式组件库，不让模型现场写代码，而是给它一套统一的组件，模型只管选哪些、怎么拼，跨 Web 和移动端体验一致，速度也快。第二层是界面编译器，模型边生成边渲染，不用等整个回复写完才出界面。之前这类产品的最大痛点就是延迟，这个算治本。

训练方法也跟着变：生成的界面按清晰度、有用性、完整性打分，模型自己学会什么时候该上交互、什么时候纯文本就够。OpenAI 自己都说"模型的设计判断仍需改进"，这话挺诚实的。

演示里几个场景还挺能打：烤肉计划直接带时间轴和食材用量表；自驾游路线落在地图上；中心极限定理、Monty Hall 问题都能交互着讲，改输入看结果变化；账单分摊、退休储蓄计算器、小游戏随口一说就造出来。

最扎心的是对比。同样问"周日烤羊腿"，GPT-5.6 给你一大段文字，GPT-6 直接甩出一个完整界面：人数调节器联动购物清单，烹饪时间线还能勾选。Adam.GPT 转发时那句"Dynamic, generative UI"，兴奋都快溢出来了。

在编程能力的四项评测里，两项小幅超过，还有两项仍然有差距，四项评测集的含义如下：

1. DeepSWE：评测的是处理已有项目的能力，给 AI 一个真实代码仓库和需求，让它自己读代码、找修改位置、实现功能、运行测试。

在需要持续试错、验证和调整路线的复杂任务上，Gemini 在这组评测里的表现明显落后。

3. Vibe Code Bench：评测的是从零做出完整应用的能力。给 AI 一段自然语言需求，比如做一个能注册、发帖、关注、点赞的网站，让它把前端、后端和数据库接起来，再通过浏览器实际操作，检查用户流程能不能走通。

它在从零搭建应用上表现很好，但另外两家也已经很接近。

4. Terminal-Bench：评测的是通过终端完成复杂实际任务的能力。AI 需要自己执行命令、操作文件、处理环境和依赖、编译程序、排查错误，最后交付符合要求的结果，整个过程都要靠它自己推进。

agent 范式下让人不适的真相：人的理解才是真正的瓶颈。（而不是 agent 和模型能力）

如推文所说，常见的失败模式是：人们在自己专业领域之外做事时，不知道怎么把 prompt 和计划写得精确，结果只能靠大量轮次"模糊地反复迭代"，既费时又费 token。

解法很简单：直接让模型先教你不懂的东西。

核心结论：ai 编程的瓶颈不在模型能力和 agent 能力，而在使用者能否精确表达需求。领域知识决定了表达的精度；缺知识时，先让模型补课、再动手，比盲目迭代高效得多。

一句话结论：agent 时代，甚至实现 agi 之后，人本身的理解会一直是瓶颈。

The model was never the hard part. The foundation was.

Not the model, the budget, the talent.

The data underneath.

AI was ready. The data wasn't.

1) One place to query An agent hunting across 30 systems guesses. An agent querying one warehouse can reason.

2) A controlled door Permissions down to table, row and column. No database credentials handed out. Every future agent inherits that boundary on day one.

3) Fresh enough to act on Day-old data runs a weekly report. Hour-old data can run agents that act.

4) Clean inputs Fields buried in concatenated strings become hallucinations. Structured, masked columns become answers.

5) Documented context Every table documented and checked against production. That's the context an agent needs to stop guessing.

→ 30+ databases and file feeds into one warehouse, ~1.5B records → Key query from 68s to 3s → Transaction data loaded hourly, against a 24-hour target → 401 transaction attributes decoded into structured, masked columns → A business analyst now runs reports that used to need a data engineer

Fix the data first. The agents get easy after that.

懂了不少 SEO 概念，真正动手时还是不知道第一步做什么。

原因往往不是知识不够，而是缺少执行顺序。

如果你正在从 0 到 1 做 AI 工具站，可以先保存这份顺序：

1. 明确 SEO 用户是谁 2. 研究他们搜索什么、想完成什么任务 3. 根据关键词和搜索意图规划网站结构 4. 搭好抓取、索引和性能等基础设施 5. 按页面类型持续生产有信息增量的内容 6. 通过外链建立站外信任 7. 检查收录、排名、流量和转化，继续迭代

这个顺序的价值，是让每一步都有上游依据。

不知道用户是谁，关键词可能选偏。

没理解搜索意图，页面类型可能做错。

没有技术基建，再好的内容也可能无法被正常抓取和收录。

只有流量、没有转化，则需要重新判断这类流量值不值得继续做。

如果只能先修一个断点，你会选用户定义、网站结构，还是转化复盘？

小册子开篇对这套顺序做了完整说明，链接放在第一条评论。

现代 SEO 不是内容团队多写几篇文章，也不是技术团队改完 sitemap 就结束。

它至少包含四层，而且必须一起工作：

1. 产品层

把搜索需求变成页面和功能。

页面要交付用户真正想要的结果，而不是只放进更多关键词。

2. 内容层

提供准确、可验证的信息增量。

真实案例、实验数据、产品截图、效果对比、失败情况，通常比重写 SERP 前 10 名更有价值。

3. 技术层

让搜索引擎看得懂，也让用户用得顺。

抓取、索引、规范 URL、多语言配置、速度、移动端体验和功能稳定性，都是这层的工作。

4. 运营层

让页面持续被发现和改进。

通过相关外链建立信任，再根据抓取、收录和真实搜索数据，补内容、调内链、改 Title，重新验证。

这四层最终只完成一件事：

让搜索用户在你的页面把事情做完。

alex_prompter：agent 真架构是薄模型 + 运行时 harness（memory / skills / protocols），智能外置不塞进权重

Alex Prompter @alex_prompter

Most people picture an agent as a model with tools bolted on. The real architecture flips that. The model stays deliberately thin, and the harness around it composes intelligence at runtime.

The harness is the real system. A harness core reaches outward to memory, skills, and protocols, plus sandboxing, observability, compression, sub-agents, approval, and evaluation. Intelligence is externalized, so state flows through the harness instead of living inside the model.

Memory holds the state. It stores what a model should not carry in its weights or a bloated context window, and each type has its own lifecycle. Working context, semantic knowledge, episodic experience, and personalized memory all get retrieved only when needed. Stable knowledge lives here, lifecycles stay separate, and you get less context rot.

Skills hold procedure. They capture the procedural knowledge that specializes a general model for a task, procedures, decision heuristics, and normative constraints that combine into task behavior. Think learned playbooks and reusable task patterns that specialize the model without retraining it.

Protocols define the contracts. They describe how the agent interacts across three surfaces, agent to user, agent to agent, and agent to tools. Mediators like sandboxing, observability, evaluation, and approval loops govern the loop on top of those surfaces.

Each concern gets its own home. Stable knowledge goes in memory, learned playbooks in skills, communication contracts in protocols, and loop governance in mediators.

那为什么要重做？我猜核心原因之一是：wrangler 的设计对象主要是“人”，而 cf 开始明显面向“agent”。比如它默认输出 JSON，更利于机器消费结果，减少上下文浪费，也更适合自动化链路。

cf 目前已覆盖 3000+ API 操作，支持用自然语言搜索命令；引入 TypeScript 配置（cloudflare.config.ts），还提供 cf migrate，一键从 wrangler 迁移。

我的结论：开发工具正在把 agent 当作第一用户。命令是否易发现、输出是否易处理、配置是否可类型检查，越来越关键。
