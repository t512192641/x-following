这个人似乎发现了GPT 屎山代码的问题

GPT学会了“把当前任务做过关”，却没有真正学会“把工程做好”。

1. 模型学会的是「怎么拿分」

他认为GPT 的强化学习可能过于强调那些容易量化的结果：

测试通过了吗？ 程序运行了吗？ 有没有报错？ 任务完成了吗？

这些都非常容易给 reward。

但一些真正决定代码质量的东西很难量化，比如：

架构设计是否合理、以后是否容易维护、模块边界是否清晰、代码是不是容易读、半年后别人能不能继续开发。

所以作者怀疑模型会形成一种倾向：

只要测试能过、结果能出来，就算完成。

哪怕内部实现很烂。

⸻

2. 模型可能被过度优化成「少想、少输出、快完成」

他观察到 GPT 有时候会生成这种代码：

一大坨代码塞在一起、模块拆分很少、抽象不足、为了完成任务直接走捷径。

推测是 OpenAI 很重视 inference efficiency，也就是：

尽量少用 Token、少推理、少消耗算力，同时把任务完成。

但真正的软件工程往往需要先设计：

需求 → 数据结构 → 模块 → 接口 → 边界情况 → 性能 → 测试 → 重构。

这显然比「直接把代码写出来」消耗更多推理资源。

所以他认为：

模型可能越来越擅长快速交付，却未必越来越擅长做工程。

3. 最大的问题之一是「训练视野太短」

这个观点其实挺重要。

模型训练时很容易形成：

任务 → 输出 → 测试通过 → 奖励

比如今天让 AI 加一个登录功能。

✅ 全通过。

操，之前这个架构根本扩展不了。

这就是他说的 training horizon too short。

模型更容易学会：

Dead functions

写了一些函数，最后根本没人调用。

以及：

empty else if

这种东西如果一个经验比较好的程序员写完以后完整 Review 一遍，通常很容易发现。

所以作者认为模型可能是：

写 → 测试通过 → 结束。

缺少：

写 → 测试 → 重新完整阅读自己的代码 → 质疑设计 → 删除垃圾代码 → 重构 → 再测试

也就是缺少真正意义上的 self-review / self-reflection。

Taste 可以理解成「工程审美」。

两个程序员都能实现同一个功能。

B 写出来：

两个人：

如果训练模型的 evaluator 主要看：

最终结果对不对？

A 和 B 得分可能差不多。

久而久之，模型就很难真正学会 B 那种「工程品味」。

Claude Code 烧 token 的速度快得惊人。

于是这个：

Fix the navbar.

《如何在 harness 里造一个模型路由器》

How to Build a Model Router in the Harness

出处：LangChain Blog

前沿 LLM 依旧昂贵。随着 agent 变得无处不在、并且以极大规模运行，这种成本已经无法承受。好在大多数 agent 并不需要每个任务都用前沿级别的智力。模型厂商自己也这么说：Anthropic 的选型指南里就提到，「对许多应用来说，从一个更快、更省钱的模型开始，比如 Claude Haiku 4.5，可能是最优做法。」

过了某个点之后，你就会碰到收益递减：能力更强的模型几乎不带来质量提升，而成本和延迟继续攀升。一个好的 agent 拥有的是模型—harness—任务三者的匹配：合适的模型，配上针对特定任务的合适上下文。而模型路由器（model router）就是为每个任务挑出这个模型的东西。我们认为这个路由决策属于 agent harness，而不是通用网关——因为选对模型所需要的领域与任务上下文，恰恰是 harness 已经在组装、而通用网关通常拿不到的。

我们自己最近就撞上了这个痛点：LangChain 的月度编码 agent 开销开始快速上涨。听到客户有同样的担忧后，我们着手为自家的开源编码 agent Open SWE 做一套真正有效的模型路由器。跟我们此前「永远使用顶级前沿模型」的基线相比，它把每个 thread 的中位成本砍掉了 64%，而质量没有可测量的变化。这篇文章讲我们怎么造出这个路由器、学到了什么，以及你如何在自己 agent 里开始做模型路由。

第一步：理解任务

我们的试验台是 Open SWE，我们的工程师从 Slack 和 Web UI 里用它来询问代码库问题、请求代码变更。在造路由器之前，我们需要先弄清开发者用 Open SWE 干的都是什么类型的活。我们从 LangSmith 的 trace 里拉了 thread 级别的数据：进来的请求类型，加上每个 thread 的成本和轮次（作为复杂度的近似度量）。探索是在 LangSmith Custom Apps 里做的，界面直接搭在 Open SWE 的 trace 之上。

一颗芯片里塞了 CPU、内存、WiFi、蓝牙，再加几十个能接传感器、屏幕、按键的引脚。它跟 Arduino 算同类，都是微控制器。树莓派是另一种东西，那是能跑 Linux 的完整小电脑。ESP32 上没有这套，程序烧进去，上电就贴着硬件跑。跑起来几十毫安，深度睡眠压到微安级，所以电池供电的小设备能待很久。

便宜是另一半原因。最小的开发板十块上下，带屏带壳的也就几十。代码可以用 Arduino 那套写，官方的 ESP-IDF 功能更全，例程和教程满地都是，周末点第一盏灯没问题。

Fine-tune a search agent with multi-turn RL on Amazon SageMaker AI

出处：AWS Machine Learning Blog（作者 Huibin Shen、Pooja Karadgi、Sifei Li、Lorenzo Stella）

由 LLM 驱动的搜索 agent 正在改变企业获取信息的方式。用户不必再费心构造完美的查询，搜索 agent 会自主决定搜什么、用哪种检索策略、以及什么时候停止搜索。它通过多轮交互完成这些事，并根据已经检索到的内容不断修正自己的做法。

然而，要让这种多步行为真正跑好很难。没有任何基础模型天生就懂你的工具和环境。拿一个小模型来提示，你几乎得不到可靠的多轮行为。拿前沿模型来提示，它通常能用，但你要为这份能力付出延迟和成本。微调提供了第三条路：你直接把工具和环境教给一个小模型。结果是既有小模型的速度和成本，又有原本只有前沿模型才能给的可靠性。

即便微调是顺理成章的下一步，传统做法各自都有短板。监督微调（SFT）依赖专家给出的理想多轮轨迹示范，收集成本高，而且对你的场景来说通常根本不存在。单轮强化学习（RL），比如带可验证奖励的 RL（RLVR），一次只给一个回复打分。但搜索 agent 在多轮之间做出的是一连串相互依赖的决策，每一步都建立在之前的上下文之上。孤立地优化单步，会完全错过这些依赖关系。

你需要的是一种把 agent 放在整条多轮轨迹上去优化的训练方式，而奖励信号只需要反映最终结果好不好。这正是多轮强化学习（MTRL）所提供的东西。它训练 agent 在一整串步骤中做出好决策，把环境特有的行为固化进去，并让你能控制输出质量。而且因为你跑的是一个更小的专用模型，你还能得到更快、更便宜的推理。

在这篇文章里，我们讲如何用 Amazon SageMaker AI 多轮强化学习（MTRL）微调一个搜索 agent，并分享我们在检索质量和可靠性上观察到的结果。我们先解释 Amazon SageMaker AI MTRL 是什么、怎么工作。

什么是 Amazon SageMaker AI MTRL？

有了 Amazon SageMaker AI MTRL，你就能在多轮交互场景下用强化学习微调 LLM。它把一个 agent 任务表述为一系列决策，用多轮 rollout 生成训练数据，并用策略梯度算法优化模型。

Amazon SageMaker AI MTRL 提供：

· 模块化的 agent—环境接口：集成保持低代码。你自定义奖励、自定义工具循环、自定义多轮对话形态。 · 无服务器执行：按 token 计费就能拿到生产规模的 agentic RL，不需要自己开或管 GPU 集群。 · 异步 rollout 与轨迹收集：生成和梯度更新并行进行，并带有有界的离策略陈旧度，所以训练既保持快，又不会偏离当前策略太远。 · 原生算法库：可以从 PPO、CISPO 和重要性采样（IS）损失里选，搭配基于组的优势估计器（GRPO、GRPO pass@k、RLOO 等）。 · 可恢复训练：可以把长训练拆到多个 job 上，从而越过单 job 的时间上限。 · 轨迹与奖励可观测性：在由 Amazon SageMaker AI 托管的 MLflow 里，逐轮、逐训练步地检查你的 agent 做了什么。 · 评测 job：在部署到 Amazon SageMaker AI endpoint 或 Amazon Bedrock 之前，报告奖励、pass@k 和轨迹指标。

Arduino 是 2005 年从意大利一个小城里出来的东西。伊夫雷亚，都灵北边，打字机大王 Olivetti 的老巢。

当地一所交互设计研究所的老师 Massimo Banzi 要带学生做电子产品原型，学生只有三十天学电子，市面上的工具却贵得离谱。

当时的主流选择是加州 Parallax 的 BASIC Stamp，在美国卖五十美元，运到意大利加上关税要一百多，学校只买得起几块，用完还得从学生手里收回来。

Banzi 的目标价很具体，一块板三十美元，一顿比萨的钱。他学生 Hernando Barragán 的毕业设计 Wiring 已经做出了雏形，一块板加一个简单的编程环境。Banzi 在这基础上换掉贵的芯片，用便宜的 ATmega8 从头重写了一遍，全套开源。名字来自他常去喝酒的一家酒吧，Bar di Re Arduino，酒吧名字纪念的是公元 1002 年的伊夫雷亚国王阿尔杜伊诺，当了两年王就被德国国王亨利二世掀翻了。第一批判三百块板，USB 版上 Banzi 把 D+ 和 D- 两个焊盘搞反了。别人板子做绿色，他们偏做蓝色，背面还印了张意大利地图。

所以 Arduino 是三层东西叠在一起。一块电路板，一个写代码的 IDE，再加一套简化到不像话的 C++ 接口，setup 里写初始化，loop 里写循环，digitalWrite 一行就能点灯。不用先学寄存器和汇编，插上 USB 当天就能让东西动起来。这套思路后来成了开源硬件的事实标准。

跟 ESP32 的渊源从这里说起。经典 Arduino 板用的是 Atmel 的 AVR 芯片，性能弱，更关键的是没有无线。物联网的年代大家要 WiFi，乐鑫的 ESP32 恰好是颗自带 WiFi 和蓝牙的芯片。2016 年起，乐鑫自己动手给 ESP32 写了一套 Arduino core，让你用 Arduino 的语法和 IDE 直接写 ESP32，这个仓库至今挂在乐鑫 GitHub 名下维护着，全家族芯片都支持。芯片厂亲自给别人的生态写适配，图的就是 Arduino 身后那群买单的开发者。

到 2023 年两边干脆合流了。Arduino 官方发布了 Nano ESP32，官方原话，第一块完全基于 ESP32 的 Arduino 板，芯是 ESP32-S3，板卡包直接从乐鑫那套 core 衍生。

一句话总结，Arduino 是工具箱和门派，ESP32 是一颗芯片。门派当年没赶上无线这波，芯片厂就自己带着芯片来拜山，最后门派把这块芯片收成了嫡系。今天入门，纯学点灯买块 Uno 也行，想顺手玩 WiFi，十几块的 ESP32 小板加 Arduino IDE，一样能点灯。

An engineer can deliver every requirement and still build something nobo…

Alex Prompter @alex_prompter

An engineer can deliver every requirement and still build something nobody needs.

That’s the product gap in engineering: the distance between understanding what to build and understanding why it should exist.

Take a sales team asking for an AI proposal generator. An engineer can build document generation, connect the CRM, and get the output looking good.

But what if writing the proposal takes twenty minutes, and getting pricing approved takes four days?

You can ship a technically excellent feature and barely change the customer’s experience.

Closing that gap requires engineers to ask questions before implementation starts. Where does the work actually get stuck? Who will use this? What happens before and after? What would make the change worth adopting?

And the organization has to give them access to the answers. If engineers only meet the problem after it becomes a ticket, the company has designed that gap into its process.

This is why I care about people who can talk to an operator, build a rough prototype, watch them use it, and revise their understanding. That conversation can change the entire scope before a team commits weeks to delivery.

Product managers and business analysts have a responsibility here too: bring engineers into the reasoning behind the requirements.

As AI makes implementation easier, product judgment deserves more attention in how we hire and develop engineers.

Being able to build ten versions is useful. Knowing which assumption to test with the first version makes that ability valuable.

苹果这次要收紧的，是 macOS 里权限最大的那一项，全盘访问。

10 月 2 日，苹果在开发者网站发了一篇不到两百词的声明，说今后全盘访问会加新限制，用户真想给某个应用这种级别的权限，必须经过非常明确的用户操作。没给时间表，没给界面图，连测试版都没有。TechCrunch 最先报道，这更像先给所有开发者打声招呼。

全盘访问是什么，装过备份软件的都打过交道。系统设置里隐私与安全性那一栏，给了它，应用就能读你整块盘，文件、邮件、短信记录、Safari 历史全在内，macOS 平时那套逐应用的数据管控基本拦不住它。这个权限当年就是为备份软件设计的，备份的活儿决定了它必须看见所有东西，杀毒软件是另一类合法用户。

出事的是第三类。Inc. 专栏作家 Jason Aten 九月初装了 Meta 刚发布的 AI 助手 Muse，他自述从头到尾没同意过它碰自己的短信和日历。几天后 Muse 推通知，建议他写一写刚和播客搭档聊过的话题，还主动提到编辑发来的截稿消息。他问 Muse 怎么知道的，Muse 回答自己只看得到通知流，看不到短信内容。这个回答是假的。他去查了，Mac 本地 Messages 数据库里 18 万 7 千多行记录已经被同步走，而这种同步只有全盘访问开着才做得到。

Meta 的说法是两道开关都得用户手动开，一个是系统的全盘访问，一个是应用里的短信连接器，意思是你自己开的，怪不到我。安全研究员 Patrick Wardle 不认这个账。他说拿到全盘访问的应用，非 root 文件全能读，浏览记录、cookie、聊天记录都一样。Ars Technica 顺势问 Meta，为什么别的应用拿着这个权限什么都读得到，唯独 Muse 读不到，对方只会重复同一句话。

苹果的声明没点任何一家的名，也不用点。声明里说，随着 AI 代理越来越强大和自主，这个级别的访问带来的风险会大幅增长。Engadget 盘点过鼓励用户开全盘访问的桌面代理，ChatGPT Mac 版在列，OpenClaw 也在，玩 agent 的应该都不陌生。

苹果还点了一个容易被忽略的地方。你把全盘访问给了某个应用，暴露的不只是你自己，还有所有给你发消息的人。你的聊天对象从没同意过任何东西。
