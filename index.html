Google just open-sourced the method thousands of its engineers use every

Alex Prompter @alex_prompter

Google just open-sourced the method thousands of its engineers use every day to stop AI doing sloppy work.

It's called the Elephant-Goldfish Model. Google built it for code, and it works for anything you ask an AI to plan or write.

The chat that plans never builds. A second chat that hasn't seen the conversation checks the plan.

How to run it in ChatGPT, Claude or Gemini:

1) The elephant. Open a chat and talk through the thing you want: the trip, the business, the kitchen, the essay. Tell it: "No output yet. Ask me questions until you could write the brief yourself." Give it 20 minutes.

2) The brief. "Write a one-page brief: what I want, why, what's already decided, what's still open, and the steps in order." Read it, fix what's wrong, copy it.

3) The goldfish. Open a new chat with no history (Temporary Chat in ChatGPT). Paste the brief and nothing else, then run three checks:

"Summarise this back to me in five lines, as if you're the one doing it." If it gets it wrong, fix the brief.

"You're the most sceptical person in the room. List every assumption here that isn't proven, and the three places this goes wrong."

"Could someone start step one right now with only this page? If not, what's missing?"

4) Fix the brief with what the goldfish found. Paste it into a chat and say: build it.

The first chat has been talking to you for 20 minutes and fills every gap with what it thinks you meant. The second chat has only the page in front of it, so it can only find gaps that are on the page.

Google's line on the goal: the AI produces what you wanted the first time you press enter.

The plugin is free on GitHub, search elephant-goldfish-model.

想做出 Grok Bot 级别的 AI agent，你需要知道的基本就是下面这些：

1. Agent 分成 router 和 worker 两层。用户跟 router 对话，router 再把活交给 worker，自己从不干活。Grok Bot 的 chief of staff 模式这么好用，就是这个原因。

2. 主动（proactive）是对事件做出反应，而不是对聊天。agent 应该一直盯着各种事件，把进来的每个事件路由给对的 worker 或动作。

3. 消息应该进队列。agent 干活的时候，用户也能继续发消息，每条消息都会排进队列，或者用来调整 agent 的方向。

4. 除了 router 和 worker，还应该有一个 watchdog 层，保证 agent 一直在线，出问题时把它修好。Hermes 成功、OpenClaw 挣扎，原因就在这里：OpenClaw 老是坏，还没法自己修好。

5. 保护人的注意力。只在用户需要采取行动，或者结果能用上的时候才发消息，减轻他们的认知负担。这也是 Grok Bot 做得很好的一点：给它发完消息就可以放心，下一条收到的就是任务完成的通知。

1. 对外通信一律要他点头。邮件、发票、社媒帖文 agent 都不能自己发，只能起草，他批准后才出去。他说这是信任的地基，不会为了省事放松。

3. Notion 当枢纽。会议记录集中放 Notion，决策也留在各 agent 自己的记忆和聊天里，目的是减少事后翻找。

Companies keep asking how to build one place where an agent can read everything the business knows.

I haven't seen one that works the way people imagine. That includes our own company.

The systems of record already hold different parts of the picture. The CRM knows the customers, the billing system knows the invoices, and the ticket system knows what broke.

An agent can do useful work when it can query the right source for the task and someone makes sure the information is current.

A single "company brain" starts going stale as soon as you build it. Documents age. Two versions of a policy sit next to each other. The agent has no clear way to tell which one applies.

Putting those documents into a retrieval index doesn't settle their authority. Retrieval can find a passage. Someone still has to decide whether that passage should govern the work.

For each workflow, I'd answer: 1. Source of truth: which system or document is authoritative for this question? 2. Version and effective date: which policy applies to the case being handled? 3. Permissions: is the agent allowed to retrieve this information for this user? 4. Provenance: can a reviewer trace an answer back to the source it used? 5. Ownership: who updates the material when the business changes? 6. Evaluation: which representative questions will show whether retrieval is returning the right evidence?

We start smaller. Each workflow gets the knowledge it needs and an owner responsible for keeping it accurate.

An onboarding agent needs the onboarding policy and relevant CRM records. Giving it the entire company archive adds more material to search without necessarily adding useful evidence.
