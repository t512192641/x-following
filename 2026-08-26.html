yibie @yibie

yibie：腾讯微信团队开源 WeMM-Embedding，基于 Qwen3.5 的通用多模态 embedding，Apache 2.0（代码+权重全开源，可商用）。三个尺寸 2B / 4B / 9B，把文本、图片、视频、视觉文档（及交错多模态输入）统一到同一个 2048 维 L2 归一化向量空间。不支持音频。视频片段可以直接变成向量，能搜、能聚类、能当 RAG 检索源。

Dao-Skill：比 Codex Skill-creator 强的六步元 Skill

逸尘 @gengdaJ

逸尘：这个创建 Skill 的元 Skill 比 Codex 自带的 Skill-creator 强；六个步骤把一个完整工作流沉淀下来。仓库 https://github.com/gnipbao/dao-skill 。

一、找根问题：用户说「做一个写作 Skill」时，先判断核心目的，避免核心模糊——要的是提炼文风、选题判断、文章生产，还是一整套内容创作系统。

二、找核心张力：用户总是既要又要，结果 Agent 执行后输出很差。例如写作自由发挥 vs 输出稳定、调研覆盖全面 vs 证据可靠、回答速度快 vs 核验充分。Dao-Skill 找出张力平衡点，避免盲目塞功能。

三、天地人三层：天=最高原则和不能违反的边界；地=适用/不适用场景、环境和路由；人=Agent 如何提问、判断、执行和输出。

四、四种生产模式：1 单一流程 Skill（一种明确任务）；2 工程工作流包（开发/调试/TDD/架构等多个小 Skill）；3 方法论工具箱（主路由＋多个诊断子 Skill）；4 认知提炼 Skill（把人物、作者、公司或思想体系提炼为思考框架）。

五、真正生成文件：Codex 根据前面的设计写出 SKILL.md、references、scripts、examples 等文件。

六、根据失败进化：失败经验必须沉淀成规则、测试、示例、脚本或评分标准，保证复用稳定性。

给 Agent 看见的界面参照：要组件页，不要堆形容词

泊舟 @bozhou_ai

泊舟：功能已经能跑，页面却总像默认模板。先别继续给 AI 编程 Agent 堆「简洁、高级、科技感」——它缺的往往是一份看得见的界面参照。形容词只说了气氛，没有告诉它按钮多大、内容怎么分层、弹窗怎样出现。具体组件页面会把结构、层级和交互摆出来。给 Agent 看链接，就像给装修师傅看参考图。

六个站点：1 shadcn/ui 基础表单/按钮/弹窗，组件代码放进自己项目再改；2 Origin UI 沿用同一复制修改方式，给常见控件补样式；3 21st.dev 面向 React + Tailwind 的社区组件目录；4 Magic UI 偏动画和视觉效果；5 Aceternity UI 偏互动动画的 React/Next.js 组件；6 Motion Primitives 开源动效集合，适合文字/切换/反馈等细小交互。

两种用法：一、先自选组件，确认 Agent 能访问该页，再把准链、页面目标和想借鉴的部分交给它适配；二、Agent 能上网时，把候选站点、目标和项目技术栈交给它自己筛再实现。不能浏览网页的 Agent 做不了第二步，别只丢一个站点首页让它猜。开始前先确认组件适合当前技术栈；借鉴结构、层级和交互，再换成自己的文案、颜色和间距。参考可以具体，别做像素级照搬。

宝玉：用 PID 做进程级取证（vmmap 23870 / 2.3–2.7GB / GPU 73MB）

宝玉 @dotey

宝玉问 AI 怎么定位的：用 PID 做进程级取证，再结合项目规模、线程状态和源码完成因果定位。昨天 Activity Monitor 截图像不算写完，新的一天再出现一次。

推断链：vmmap -summary 23870 显示物理 footprint 约 2.3 GB、峰值约 2.7 GB；大头在 MALLOC_SMALL，IOSurface 只有约 14 MB，GPU 图形约 73 MB，所以视频帧池不是主因。Activity Monitor 显示 439 个线程，源码中每个缩略图都 std::thread::spawn、随后等待 2 路信号量。项目时长约 24,278 秒，波形代码会生成完整的 16 kHz 单声道 Vec<f32>：24,278 × 16,000 × 4 bytes ≈ 1.55 GB，和实际内存峰值高度吻合。属于「系统取证 + 源码验证」，不是单纯看 PID 猜出来的。

Kevin：独立开发尽量做红海，谨慎碰蓝海

Kevin Ma @kevinma_dev_zh

Kevin：独立开发做产品几个月，有阶段性小成果。踩过坑后越来越确定的 6 点：

1. 尽量做红海需求，谨慎碰蓝海。红海意味着需求已被验证、用户已被教育，还有竞品可研究；可以切更具体人群、把核心体验做极致，或提供更简单更便宜的方案。一个人成本结构不同，小而精是优势。

2. 做之前先找成功案例。最好已有人靠它赚到钱；看竞品定价、评价、Reddit、App Store、社媒，看用户为什么付钱、抱怨什么。独立开发没有资本用半年验证想象中的需求。

3. 谨慎做开发者工具。开发者爱试新东西，付费意愿往往没想象中高；中文个人开发者市场商业化通常更难。例外是海外，或面向小团队/小公司帮他们省时间、降成本、提高收入的 To 小 B。

4. 独立开发本质是创业，每天都在取舍。功能和增长都可以无限优化，但时间和精力有限。先知道产品靠什么产生价值，别为审美和技术洁癖把时间花在用户不在乎的地方。

5. 判断需求真假最好看有没有人愿意付钱。「很好」「以后一定支持」和掏钱之间还很远；已付钱的人为什么付、最看重什么，比一百条「看起来不错」更有价值。

6. 一开始就要敢于收费。不认可先堆大量免费用户再商业化；核心体验可以试，持续产生价值的部分就该收费。从第一天收费，用户从一开始就知道这是一门生意。

Pi AgentHarness：prune 永久丢失 vs spill 可恢复；issue #128 五场景

yibie @yibie

yibie 写 Pi（libGDX 作者 Mario Zechner 主导的开源编码 agent）官方开发笔记：工具执行前先落盘 intent，执行后再落盘结果，崩溃后靠归约日志恢复现场。仓库公开 packages/agent/docs/agent-harness.md 和配套 issue #128（修复压缩不足）。模型与自家 harness 绑定越来越深。

prune 分两种。永久丢失型：把工具输出从上下文删掉，删了就找不回（例如 3 万字符测试日志里错误在第 12000 字，压缩完就消失）。可恢复型（spill）：context 只放一小段，完整工具结果落到磁盘，context 里留文件路径和 offset，模型需要时自己 grep / sed / read 回去。官方实现里 shell output capture 走 ExecutionEnv，full-output spill 用 appendFile()——spill 不是丢，是换地方放。

issue #128 先定义 Turn（从用户输入到最终 assistant 响应、不再有工具调用的整个循环）和 Step（turn 内 prompt → LLM → 工具执行）。分析了五种溢出场景：① prompt 本身就超过窗口（比如往 200k 窗口粘 300k 字符）——不可恢复，没有东西可压缩，只能向用户报错；② 累积上下文溢出，但最后一 turn 放得下——可恢复，压缩旧内容，保留最后一 turn（摘要 + 50k 拟合）；③ turn 中途溢出，工具结果逐步累积到第 N 个 step 超了——可恢复，保留本 turn 的全部 step；④ 单个 turn 超过上下文窗口——不可恢复，压缩保留的最后一 turn 本身就超，压缩完下次还溢出，卡死循环，需要 turn 内修剪；⑤ 孤儿工具结果——调查过，正常 abort 流程下不可能发生。场景 4 是关键：compaction 只会总结旧的、保留新的，最新一 turn 本身超窗口就无能为力。

解决方案分三层。Layer 1 截断：settings.json 配 toolOutputLimits——bash 30KB、read 100KB、edit 50KB、默认 30KB；截断时给模型附加 notice「...(truncated, output exceeded {limit} character limit)」。Layer 2 错误处理：溢出时向 UI 报错。Layer 3 turn 内修剪：当保留的最后一 turn 仍超窗口，从 turn 内部剪掉旧的工具结果，重复直到放下。

issue 点名参考：OpenCode 的 prune() 在 turn 结束后移除旧的工具输出；Codex 在 compaction 溢出时修剪最老的 history 条目。Pi 把各家摆在一起比，称 OpenCode / Codex / DSH 这类「剪掉就找不回」为 permanently-lossy pruner。DSH 的 tool result pruner 保留开头一段和结尾一段、中间直接裁掉（这个评价出自配套社区 PR，不是官方文档原文）。Pi 自己走 spill + appendFile。社区自报（非官方）：19 个真实 session 上 context 占用降低 26%～35%，uncached prefill 降低 72%～88%。

笔记还记：新一代 Claude 在第三方 harness 上更容易调错工具。Pi 的 edit tool schema 写得很清楚，模型却会自己生成 requireUnique、matchCase、oldText2 这种 Pi 根本不存在的参数。猜测是 Claude 后训练越来越适配 Claude Code 自己的 harness / tool schema。推论：评测 coding model 要连同 harness 一起评。

AgentHarness 把状态分成四类：① Harness config（model / thinking / tools / resources / stream options / system prompt；getter 返回最新配置，setter 立即生效但只影响下一个 turn，绝不改正在跑的 provider request）；② Turn snapshot，由 createTurnState() 创建；③ Session，只含持久化条目，读时不包括排队中的写；④ Pending session writes，操作中的写排队，save point / 结算 / 失败清理时按确定顺序 flush，abort 也不丢。intent 先落盘（QueueEnqueued、OperationStarted、ToolCallStarted），执行结束再写结果（ToolCallFinished）。崩溃后靠归约 session 日志重建状态。

崩溃恢复保守：未完成的 agent turn 标记 interrupted，保留 durable queues / pending writes，回到 idle；未完成的 provider request 标记 interrupted，不自动重试；未完成的 tool call 追加 interrupted/error tool result，只有工具声明 retry-safe / 幂等才重试——崩溃后外部副作用可能已经发生，默认不重跑；未完成的 compaction 没有对应 entry 就重跑。crash 在 queue_enqueued 之前 = 消息从未被接受；之后 = 消息恢复。

姚金刚：早期创业把广义管理成本压到总成本 20% 以内

姚金刚 @yaojingang

姚金刚：创业公司早期很重要的经营原则，是尽可能降低管理成本。这里的管理成本用广义视角：管理人员，HR / 行政 / 财务 / 项目管理等中后台，以及会议、汇报、审批、协调、绩效管理和信息传递消耗的时间。它们主要用于维持组织自身运转，并不直接创造客户价值。

创业公司真正稀缺的是钱、人和时间。如果只有 20 个人却有 5 个人主要负责管理、协调、汇报和支持，就意味着 25% 的组织能力没有直接投入产品、销售和交付。关注两个指标：广义管理成本 ÷ 总成本，早期希望尽可能控制在 20% 以内；一线价值创造人员 ÷ 总人数，最好达到 80% 以上。一线就是直接参与产品、研发、销售、交付的人。离客户越近，人应该越多；离客户越远，人应该越少。

业务出问题就加管理岗、信息不透明就加汇报、执行不到位就加审批，组织会越来越完整、成本越来越高。管理该解决的是用更少的管理动作，让更多人高效创造价值。目标、责任、标准清楚，反馈及时，大量会议、汇报和中间协调都可以减少。AI 时代更明显：过去需要专门岗位完成的统计、分析、信息整理、项目跟踪、知识同步、流程提醒，逐渐被自动化系统和 AI Agent 替代。少数高能力的人，加上大量 AI 能力，再配合极简管理机制，就可以完成过去需要几十人甚至上百人的工作。
